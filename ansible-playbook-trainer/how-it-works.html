Ansible Playbook Trainer — How It's Built

Write twenty playbooks from an empty file, with a reason for the indentation of every line.

Overview

Most playbook errors a beginner hits are not Ansible errors. They are placement errors: a key two spaces too deep, a missing dash, a task keyword tucked under the module. This trainer drills placement on its own. Each exercise is a plain-language work order; the learner types the playbook in a Vim-style editor, and every finished line is marked correct or not, with the reason. Nothing runs on a server, and no playbook is executed.

Tech Stack

HTML CSS JavaScript modules js-yaml Node test runner
  • HTML and CSS — one page: the layout guide, the work order, and the editor. The panes stack on a narrow screen.
  • JavaScript modules — the editor and the checker have no screen access, so the same code runs in the browser and in the tests.
  • js-yaml — a YAML parser, copied into the repository at a pinned version with its checksum recorded. Nothing loads from a content delivery network.
  • Node test runner — Node's built-in node --test. No packages to install.

How Each Part Works

editor.js — a small modal editor

The subset of Vim needed to write a playbook: normal, insert and command modes, the common motions, dd, yy, p, undo, and :w to check. It is a state object and one function that takes a key and changes the state. Tab inserts spaces to the next 2-space step and Enter keeps the current indentation, which is how Vim is normally set up for YAML. A real tab character can never reach the file. 

// One key in, one state change out. The page only draws the result.
export function handleKey(state, key) {
  state.message = '';
  if (state.mode === 'insert') return insertKey(state, key);
  if (state.mode === 'command') return commandKey(state, key);
  return normalKey(state, key);
}

checker.js — judging one line at a time

A YAML parser can only say whether a finished file is valid. A learner needs to know which line is wrong while the file is still half written. So the checker reads the buffer top to bottom and keeps a stack of the levels that are open: the playbook, a play, its vars, a task list, a task, a module's arguments. Each line is matched to the level its indentation selects, and that level decides what the line is allowed to be.

The same walk gives every line a path into the data, such as play 1, tasks, item 2, ansible.builtin.copy, mode. Comparing the value at that path with the exercise gives three verdicts: correct, wrong place, or right place with the wrong value. Because the comparison is by path and not by line number, the keys of a play or a task may be written in any order. 

// A dedent closes every level deeper than the line.
while (parsed.indent < top().indent) stack.pop();

// Stepping in is only legal straight after a key with no value.
if (parsed.indent > top().indent) { /* red: nothing opened this level */ }

// A task keyword under the module is valid YAML but wrong Ansible, so it is named.
if (container.kind === 'args' && TASK_ONLY.has(key)) { /* red: when belongs at 6 */ }

Two checks must agree before an exercise passes

A hand-written line reader could disagree with real YAML. So passing needs two things: the line checker reports nothing wrong and nothing missing, and js-yaml parses the whole buffer to exactly the data the exercise expects. If the two ever disagree, the exercise does not pass. 

const passed = bad === 0 && warn === 0 && missing.length === 0
  && docSeen && deepEqual(load(text), expected);

exercises.js and model.js — one source for three outputs

An exercise is only data: the playbook to produce. The work order shown to the learner, the model answer and the hints are all generated from it, so a work order can never ask for something the checker does not accept. The work order is written in words, not YAML, so the learner has to decide the columns and dashes. 

{
  id: 'task-when',
  level: 4,
  title: 'A condition with when',
  plays: [{
    name: 'Install the web server', hosts: 'servera', become: true, gather_facts: true,
    tasks: [{
      name: 'Install httpd on Red Hat systems',
      'ansible.builtin.dnf': { name: 'httpd', state: 'present' },
      when: "ansible_facts['os_family'] == 'RedHat'",
    }],
  }],
}

Tests

Every exercise is tested four ways. The model answer must pass with every line marked correct. The same answer with all keys in reverse order must also pass. Moving any single line in or out by one level must fail. And typing the model one line at a time must never show an error, with the hint always naming the next line. The editor has its own tests for each key. 

node --test 'ansible-playbook-trainer/tests/*.test.mjs'

Security

  • Content-Security-Policy — script-src 'self': no inline script and nothing from another site.
  • No innerHTML — everything the learner types is put on the page as text, never as markup.
  • No network calls — progress is kept in the browser's local storage and nowhere else.
  • Pinned dependency — the one library is vendored with its checksum.

Limits

  • Structure only — it checks where lines go and what they hold. It does not run Ansible or check that a module accepts an argument.
  • One layout — it enforces 2 spaces per level with list items indented under their key, the style of the Ansible documentation. YAML itself allows others.
  • A subset of Vim — no visual mode, counts or search.
  • Keyboard needed — the editor is built for a physical keyboard.
