Ansible Playbook Trainer

Learn where every line of a playbook goes by writing twenty of them from an empty file. Each line you type is checked, and each one comes with the reason for its indentation. The host names and values are arbitrary practice data; nothing is run on a real machine.

Read first: how a playbook is laid out

A playbook is a list of plays. Each play is a dictionary of keys such as hosts and tasks. Two marks carry all of the structure: a dash and a space (- ) starts an item in a list, and key: starts an entry in a dictionary. Indentation says what belongs to what, and every level is exactly 2 spaces.

---                                          # ← column 1, line 1: a YAML document starts here
- name: Deploy a hardened web server         # ← dash at column 1 opens PLAY 1; name is its label in the output
  hosts: servera                             # ← 2 spaces: belongs to the play. WHO to run on. The only required play key
  become: true                               # ← 2 spaces: escalate to root with sudo, for every task in this play
  gather_facts: true                         # ← 2 spaces: collect facts first so ansible_facts is populated
  vars:                                      # ← 2 spaces: opens a dictionary of variables for this play
    web_packages:                            # ← 4 spaces: one variable; nothing after the colon means "value is below"
      - httpd                                # ← 6 spaces + dash: first item in the list
      - mod_ssl                              # ← same column as httpd, so it is a sibling item
    web_service: httpd                       # ← 4 spaces: back out one level, so this is a second variable
  tasks:                                     # ← 2 spaces: opens the LIST of work. Order in here is execution order
    - name: Install web packages             # ← 4 spaces + dash: opens TASK 1
      ansible.builtin.dnf:                   # ← 6 spaces: the module. Exactly one per task. WHAT to do
        name: "{{ web_packages }}"           # ← 8 spaces: argument to the module; quotes are required when a value starts with {{
        state: present                       # ← 8 spaces: the desired state, not a command
      when: ansible_facts['os_family'] == 'RedHat'   # ← 6 spaces: belongs to the TASK, not the module. No {{ }} in when

    - name: Hide the Apache version banner   # ← dash at 4 spaces again: TASK 1 is closed, TASK 2 opens
      ansible.builtin.copy:
        dest: /etc/httpd/conf.d/security.conf
        content: |                           # ← pipe: keep the following lines exactly, line breaks included
          ServerTokens Prod
          ServerSignature Off
        owner: root
        group: root
        mode: '0644'                         # ← quoted so YAML keeps it as text and the leading zero survives
      notify: Restart web service            # ← 6 spaces: task level. Runs the handler ONLY if this task reports a change

    - name: Start and enable the web service
      ansible.builtin.service:
        name: "{{ web_service }}"
        state: started
        enabled: true

  handlers:                                  # ← 2 spaces: sibling of tasks, so it belongs to the play
    - name: Restart web service              # ← must match the notify text character for character
      ansible.builtin.service:
        name: "{{ web_service }}"
        state: restarted

The placement chart

ElementSpaces before itWhat it isWhy you need it
---0, on line 1YAML document markerOptional to the parser, but expected by convention and by linters
- name: (play)0, then the dashOpens one playThe dash makes the play a list item; the name labels it in the output
hosts:2Play keyMaps the play to inventory hosts. Without it the play is invalid
become:2Play keyPrivilege escalation. Omit it and package installs fail as a normal user
gather_facts:2Play keyControls whether ansible_facts is populated
vars:2Play key, holds a dictionaryKeeps values out of the tasks so you change them in one place
tasks:2Play key, holds a listThe work itself
- name: (task)4, then the dashOpens one taskEach dash is a new task; the name is what you read when it fails
Module line6Task keyThe action. One module per task, written with its full name
Module arguments8Dictionary under the moduleParameters for that module only
when: loop: register: notify:6Task keywordsThey modify the task, so they line up with the module, not under it
handlers:2Play key, holds a listTasks that run only when notified, once, after the tasks finish

What can move, and what cannot

  • Keys can come in any order. A play is a dictionary, so Ansible looks each key up by name. tasks above hosts works. Ansible runs the sections in its own fixed order regardless: variables, facts, tasks, then handlers.
  • List items cannot be reordered. Tasks run top to bottom, so swapping two tasks changes what happens.
  • Indentation cannot change. It is how YAML knows what a line belongs to. Put when at 8 spaces instead of 6 and it becomes an argument to the module, which rejects it.
  • Spaces only, never tabs. YAML rejects a tab used for indentation.

The usual order (name, hosts, become, vars, tasks, handlers) is a convention for the reader. The trainer accepts any order, so try it.

Using the editor

The editor works like Vim, the editor you get on a Red Hat exam. It has two main modes. In normal mode keys are commands; in insert mode keys type text. It starts in normal mode.

KeysWhat they do
i a A IStart typing: before the cursor, after it, at the end of the line, at the first character
o OOpen a new line below or above, at the same indentation, and start typing
EscBack to normal mode
h j k l or arrowsMove left, down, up, right
0 ^ $ w b gg GStart of line, first character, end of line, next word, previous word, first line, last line
x dd DDelete a character, a whole line, or the rest of the line
yy p PCopy a line; paste below or above
uUndo
:w EnterCheck the playbook
:n :prev :%d :12Next exercise, previous exercise, clear the file, go to line 12
  • Tab types 2 spaces, and Enter starts the new line at the same indentation as the one above. Backspace inside the indentation removes one level.
  • Leading spaces are drawn as dots (··) so you can count them. They are still spaces.
  • The lit row and the lit column cross at the cursor, as with Vim's cursorline and cursorcolumn settings. Follow the column up the file to see which lines yours lines up with.
  • Each finished line gets a mark: a green ✓ is correct, a red ✗ is in the wrong place, an amber ! is in a valid place but does not match the brief. Move the cursor to any line to read the reason.
