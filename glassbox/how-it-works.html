Glassbox — How It's Built

A pure-static Python memory visualizer: authored traces, a pure layout engine, and zero dependencies.

Overview

Glassbox is a beginner-focused tool that makes Python's memory model visible. It steps through five hand-authored lessons — each a short snippet with narrated frames — showing how names point to values, how lists live on the heap, and how two names can share one object. The goal is the "aha" moment when a student watches b = a copy an arrow, not a list, and then sees both names reflect a mutation.

There is no Python interpreter, no build step, and no server. Lessons are authored as ES module trace objects and validated at development time by a Node test suite. The app runs directly from file:// via native ES module imports in the browser.

Tech Stack

HTML CSS Vanilla JS (ES2022) SVG Node --test
  • HTML — static shell with two layout panels (Code, Memory), narration bar, controls, and a lesson rail <nav>. Semantic landmarks and aria-live regions for accessibility.
  • CSS — custom-property dark theme, CSS Grid two-column stage, prefers-reduced-motion guard on pulse animation, responsive breakpoint at 720 px.
  • Vanilla JS (ES2022) — ES modules throughout: pure engine (formatValue, computeLayout, stepReducer), DOM layer (render.js, controls.js, main.js), and authored lesson data.
  • SVG — inline <svg> with createElementNS draws arrows from variable boxes to heap object boxes using measured getBoundingClientRect positions after each frame paint.
  • Node --test — built-in Node.js test runner; 25 tests cover the four pure modules and validate all five real lessons through the author-time validateTrace guardrail.

How Each Part Works

src/layout.js — the pure engine

computeLayout(step) is the heart of Glassbox. It receives one execution step (a plain data object with frames, heap, and highlight) and returns a structural model — no pixel coordinates, no DOM. The three output arrays (frames, objects, arrows) are consumed by the renderer. 

// Each arrow: { from: "globals.a", to: "#1", highlighted: false }
// "from" matches the data-endpoint on a var box; "to" matches a heap box.
const arrows = step.frames.flatMap((frame) =>
  Object.entries(frame.vars).map(([name, id]) => ({
    from: `${frame.name}.${name}`,
    to: id,
    highlighted: highlightVars.has(name) || highlightObjs.has(id),
  })),
);

src/render.js — DOM painter

renderStep(els, trace, stepIndex) calls computeLayout, then writes the DOM using createElement / textContent / replaceChildren — never innerHTML. This keeps the renderer XSS-proof even though lesson content is authored data. Arrows are drawn in a requestAnimationFrame callback so box positions are measured after the browser has laid out the updated frames and heap. 

// data-endpoint on var boxes: "globals.a"
// data-endpoint on heap boxes: "#1"
// renderArrows() queries both and draws SVG lines between them.
box.dataset.endpoint = `${frame.name}.${v.name}`; // var box
box.dataset.endpoint = obj.id;                     // heap box

src/controls.js — wiring

initControls owns the step integer and all input sources: Prev / Next / Reset buttons, Play autoplay (1.5 s interval), and keyboard arrow keys. A pure stepReducer handles all transitions. The function returns a { destroy } handle so main.js can tear down keyboard listeners when the user switches lessons. 

// Autoplay: advance every 1500 ms, stop on last step.
timer = setInterval(() => dispatch({ type: "next" }), AUTOPLAY_MS);
if (timer !== null && step === total - 1) stopPlay();

src/main.js — bootstrap

Builds the lesson rail, reads localStorage for a saved position, then calls selectLesson. Each lesson switch calls active.destroy() then clones-and-replaces the four control buttons with freshButton(id) so click listeners never stack across selections. 

function freshButton(id) {
  // Clone-and-replace drops all previously-bound click listeners.
  const old = $(id);
  const clone = old.cloneNode(true);
  old.replaceWith(clone);
  return clone;
}

src/validateTrace.js — author-time guardrail

Every authored lesson is run through validateTrace by lessons.test.js at commit time. It catches dangling heap references, out-of-range line numbers, missing narration, and unknown highlight ids before they can silently break the renderer. 

// Checks every variable reference resolves in the heap.
for (const [varName, id] of Object.entries(vars)) {
  if (!(id in heap)) {
    errors.push(`step ${i}: var "${varName}" points at missing heap id ${id}`);
  }
}

Replicate It Yourself

  1. Design the trace data model. A trace is a plain JS object with id, title, code (array of source lines), and steps. Each step holds frames (named scopes with variable-to-heap-id mappings), a heap object, optional highlight, and output. Keep it serializable — no functions, no classes. Reference: MDN destructuring.
  2. Write the pure engine first. computeLayout(step) maps the trace data to a renderer-friendly model. Because it is a pure function with no DOM dependency, you can test it with Node's built-in test runner (node --test) before touching the browser. Reference: Node.js Test Runner.
  3. Build the DOM renderer with createElement only. Attach data-endpoint attributes to var and heap boxes so renderArrows can query them by the same strings the layout engine produces. Draw SVG arrows inside a requestAnimationFrame callback so box positions are final. Reference: MDN createElementNS.
  4. Wire controls with a pure reducer. A stepReducer(step, action, total) function handles all state transitions. initControls owns the step integer and calls the reducer on every input event. Return a { destroy } handle so you can clean up keyboard listeners when the user switches lessons without reloading the page.
  5. Deploy to GitHub Pages: push to main, then go to repo Settings → Pages → Source: Deploy from branch → main / (root). Reference: GitHub Pages docs.
