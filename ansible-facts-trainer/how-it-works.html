Ansible Facts Trainer — How It's Built

Look the fact up in a terminal, edit the playbook, and run it, the way you would on the exam.

Overview

Ansible gathers facts about every host it manages: hostname, addresses, memory, operating system. Using them correctly takes three skills at once: finding the right fact, reaching into nested data, and writing valid YAML with Jinja2 braces. This trainer drills all three against a real ansible -m setup capture from a CentOS Stream 9 lab host. Nothing runs on a server; every answer is checked in the browser.

Tech Stack

HTML CSS JavaScript modules js-yaml Node test runner Python
  • HTML and CSS — a practice terminal beside a playbook editor with line numbers and syntax color. The panes stack on a phone.
  • JavaScript modules — the validator is a separate file with no screen access, so the same code runs in the browser and in the tests.
  • js-yaml — a YAML parser, copied into the repository at a pinned version with its checksum recorded. Nothing loads from a content delivery network.
  • Node test runner — 189 tests using Node's built-in node --test. No packages to install.
  • Python — a one-off script that sanitizes the raw capture before it is published.

How Each Part Works

validator.js — the resolver

The core of the app. It reads a fact lookup one step at a time and walks the capture. It never calls eval(). It mirrors one Ansible quirk exactly: every fact loses its ansible_ prefix inside ansible_facts except ansible_local. Because it walks real data, every correct spelling passes: bracket notation, dot notation, and the legacy ansible_hostname form. 

// One step is .key, ['key'], "key" in brackets, or [0]
const STEP_RE = /^\s*(?:\.([A-Za-z_][A-Za-z0-9_]*|\d+)|\[\s*(?:'([^']*)'|"([^"]*)"|(\d+))\s*\])/;

// Object.hasOwn keeps inherited names such as "constructor" from resolving.
if (!Object.hasOwn(current, key)) {
  const hint = suggest(key, Object.keys(current));
  return fail('UNDEFINED_FACT', `No fact named '${key}' ... Did you mean '${hint}'?`);
}

validator.js — the task check

An answer passes through a pipeline: size guard, YAML parse, shape check, fact resolution, verdict. Each stage fails with its own named error, so the feedback says what is wrong and how to fix it. A passing answer shows the line a real run would print. 

// Pass rule: every fact the challenge requires was actually read.

shell.js and pager.js — the practice terminal

There is no facts cheat sheet. You look facts up the way you do at a control node: ansible servera -m setup, piped to less or grep. The output is the real capture, line for line, in the exact format Ansible prints. Nothing is executed: each command is parsed into words and answered from fixed text. The -a 'filter=...' argument slices the stored text into fact blocks instead of re-serializing it, so spacing and number formatting stay as Ansible wrote them. less is a small state machine with no screen access, which is what makes paging and searching testable. 

// Basic grep treats + ? | ( ) { } as plain characters unless -E is given.
return flags.E ? pattern : pattern.replace(/[+?|(){}]/g, '\\$&');

// pager.js: one key in, one new state out.
case ' ': case 'f': case 'PageDown':
  return { state: clamp(state, state.top + state.page), quit: false };

jinja.js — an expression evaluator, checked against real Ansible

The exam-style scenarios need conditions, loops, arithmetic, and filters, so the trainer has its own Jinja2 expression evaluator: a tokenizer, a parser with Jinja2's precedence, and a tree walker. It never calls eval(). It follows Python's rules, not JavaScript's: 1 == '1' is false, 7 / 2 is 3.5, round(2.5) is 2.0, and a missing key stays "undefined" until something uses it, which is what makes | default('NONE') work.

An evaluator that disagrees with Ansible would teach wrong answers, so a test renders 240 expressions with both this code and the real Ansible templating engine and fails on any difference. The first run of that test found eight. Two were not obvious: Ansible keeps backslashes in string literals exactly as written, and Python rounds from a number's exact binary value, so round(2.675, 2) is 2.67. 

// tests/jinja-differential.test.mjs
// Rule: if Ansible renders it, the trainer renders the same text, or says plainly
// that the construct is outside its scope. If Ansible fails, the trainer fails too.
if (real.ok !== mine.ok || (real.ok && real.text !== mine.text)) mismatches.push(expression);

executor.js and exam-challenges.js — graded by end state

An exam task describes a required end state, not a syntax. So the scenarios run every task against a small model of the host (packages, files, services) and then check what is left: is httpd installed, does /root/hwreport.txt hold the right lines. Each playbook is also run silently against a second, differently configured host. A playbook that installs httpd unconditionally passes on servera and fails on the Debian host, which is exactly how a hard-coded answer fails on a real exam. 

variants: [{
  label: 'a Debian-family host',
  patch: { os_family: 'Debian', distribution: 'Ubuntu', pkg_mgr: 'apt' },
  expect: [{ type: 'package', name: 'httpd', installed: false, label: 'httpd is not installed' }],
}],

difficulty.js — the scaffolding comes off as you improve

The first challenge gives you the whole playbook with one blank. Each challenge you pass without help removes one more pre-written row from the next one: first the msg: line, then the module, then the task name, then tasks:, hosts:, and the play line, until you start from an empty file, as on the exam. Using Show answer gives one row back. The prompt always lists what is missing. 

// Rows come off from the bottom up: the ones nearest your own work go first.
const kept = rows.slice(0, rows.length - applied);
const removed = rows.slice(rows.length - applied).reverse();

runner.js — the simulated run

You edit a whole playbook file, not a fragment. The runner checks the play (hosts, tasks, gather_facts), hands the task to the validator, and then writes what ansible-playbook would print: the PLAY and TASK banners, the result, and the recap. An undefined fact fails the way it does on a real host, with a fatal line and failed=1, in Ansible's own wording and colors: green for ok, red for failures and load errors. Piped output is uncolored, as it is in a real shell. The terminal is labelled "simulated" because the text is produced in the browser, not by Ansible. 

// The terminal shows what Ansible would do. The coach line gives the verdict.
// A task can run cleanly and still read the wrong fact.
if (verdict.ok || verdict.code === 'WRONG_FACT') {
  return stop(verdict, ...opening, ...taskBanner, verdict.rendered, ...closing(gathered + 1, 0));
}

validator.js — three filters, on purpose

The capstone needs the address on the lab network, which is not the default-route address. So the resolver supports exactly select('match', ...), first, and list. It mirrors two Jinja2 behaviors that catch people out: match is anchored at the start of the string, and select alone returns a generator that cannot be printed. 

// match is anchored at the start of the string, like Python's re.match.
pattern = new RegExp(args[0] === 'match' ? `^(?:${args[1]})` : args[1]);

highlight.js — syntax color without a library

A textarea cannot color its own text. The editor stacks a transparent textarea on a colored copy of the same text, with identical font metrics. The tokenizer is lossless: joining its tokens reproduces the input exactly, which is what keeps the colors aligned with the characters you type. A test checks that property on awkward inputs. 

test('tokenizing is lossless for every input', () => {
  assert.equal(tokenizeYaml(text).map((t) => t.text).join(''), text);
});

tools/sanitize_facts.py and the leak gate

The capture came from a real machine, so it held real identifiers. The sanitizer replaces MAC addresses, the IPv6 addresses derived from them, the machine ID, SSH host keys, the public resolver address, and the account name. A test then checks the published file against an allowlist. The test describes what clean data looks like, so it holds no real value itself. 

// tests/sanitization.test.mjs
test('every MAC address is in the documentation range', () => {
  for (const mac of macs) {
    assert.ok(/^00:00:5e:00:53:/i.test(mac) || mac === '00:00:00:00:00:00');
  }
});

app.js

Screen logic only: it draws the terminal and its pager, keeps the editor's color layer and line numbers in step with the text, sends the playbook to the runner, and saves progress in the browser. All output is written as text, never as HTML, so nothing typed into the editor can inject markup. 

// textContent, never innerHTML
$('terminal').textContent = terminal;

Replicate It Yourself

  1. Capture the facts from a host you manage: ansible servera -m ansible.builtin.setup > raw.json. Keep the raw file out of your repository. Reference: the setup module.
  2. Sanitize it before publishing. Replace hardware addresses, machine IDs, host keys, public addresses, and account names, then write a test that fails if any of them come back.
  3. Parse answers with a real YAML parser, not regular expressions, and resolve fact lookups by walking the data. Reference: Ansible facts and magic variables.
  4. Keep the checking logic in a file with no screen access and test it with node --test. Reference: Node.js test runner.
  5. Set a strict Content-Security-Policy and write output with textContent. Reference: MDN Content Security Policy.
