Ansible Facts Trainer

Work the way you will on the exam: look the fact up with ansible servera -m setup, edit the playbook, and run it. The facts are a real capture from servera, a CentOS Stream 9 lab host, with identifying values replaced.

How to read the setup output

A dictionary starts at the { that follows its key and ends at the matching } that sits at the same indentation as that key. In servera's output, ansible_device_links opens on one line and closes at the }, directly above "ansible_devices".

That fact, every line of it, with notes:

"ansible_device_links": {                 ← opens (8 spaces in the real output)
    "ids": {                              ← child dictionary opens
        "dm-0": [                         ← list opens
            "dm-name-cs-root",            ← item [0]: the value the playbook example below reaches
            "dm-uuid-LVM-PLACEHOLDER01"   ← item [1]; no comma: last item in the list
        ],                                ← "dm-0" closes; comma means a sibling follows
        "dm-1": [
            "dm-name-cs-swap",
            "dm-uuid-LVM-PLACEHOLDER02"
        ],
        "sda3": [
            "lvm-pv-uuid-PLACEHOLDER01"   ← a list with one item is still a list
        ]                                 ← no comma: last item in "ids"
    },                                    ← "ids" closes; comma means a sibling follows
    "labels": {},                         ← empty dictionary, opens and closes on one line
    "masters": {
        "sda3": [
            "dm-0",                       ← a value here, not a key: plain text inside a list
            "dm-1"
        ]
    },
    "uuids": {
        "dm-0": [
            "00000000-0000-4000-8000-000000000002"
        ],
        "dm-1": [
            "00000000-0000-4000-8000-000000000003"
        ],
        "sda1": [
            "0000-0001"
        ],
        "sda2": [
            "00000000-0000-4000-8000-000000000004"
        ]
    }                                     ← no comma: last item in ansible_device_links
},                                        ← ansible_device_links closes; comma means a sibling follows
"ansible_devices": {                      ← next fact, same indentation, so it is a sibling

Four rules that cover nearly all of it

  • Braces { } are a dictionary; square brackets [ ] are a list. That tells you whether the next step in your path is a key name or a position number.
  • The closer lines up with the line that opened it. Find the key, note its column, and scan straight down for the first } in that same column.
  • A comma after the closer means a sibling follows. No comma means that was the last item in its parent.
  • Same indentation means same level. ansible_devices is level with ansible_device_links, so it is a separate fact, not part of it. The ids inside ansible_devices['dm-0']['links'] is a different ids that happens to share the name.

So this fact has exactly four keys: ids, labels, masters, uuids.

Let the tool draw the boundary for you

Counting braces by eye fails on long output. Ask for only the one fact. The reply is that fact alone inside the ansible_facts wrapper, followed by discovered_interpreter_python, which Ansible always reports.

Use the same filter to find what you are looking for

The filter takes any fact name. To see only the date and time on servera:

  • Less to read. The full output is close to 800 lines. This reply is under 30, so the whole fact fits on one screen with no paging.
  • It shows the exact key names. You do not have to remember whether the key is weekday or day_of_week. Read it off the reply, then write ansible_facts['date_time']['weekday'].
  • It shows the type of each value. Every value in this fact is in quotes, so "day": "09" is text, not a number. Add | int before you compare it with a number.
  • A wrong name gives an empty reply, not an error. If only discovered_interpreter_python comes back, the name matched nothing. Check the spelling.

From the output to a playbook

Each level you step down in the output becomes one pair of square brackets in the expression. To reach the first id of dm-0:

Line in the outputWhat it isWhat you write
"ansible_device_links": {the fact, a dictionaryansible_facts['device_links']
"ids": {a key, a dictionary['ids']
"dm-0": [a key, a list['dm-0']
"dm-name-cs-root",the first item in the list[0]
 
- name: Show the first id of dm-0
  ansible.builtin.debug:
    msg: "{{ ansible_facts['device_links']['ids']['dm-0'][0] }}"   # "msg": "dm-name-cs-root"
  • Inside ansible_facts the key loses its ansible_ prefix: ansible_device_links becomes device_links.
  • Braces took a key name in quotes; the brackets took a position number, and counting starts at 0.
  • Write ['dm-0'], not .dm-0. With a dot, Jinja2 reads the hyphen as a minus sign.

Compare a fact with a number

The quotes in the output tell you the type. A value in quotes is text. A value without quotes is a number.

The major version comes back as "9", in quotes, so it is text and has to be converted before it is compared with a number:

when: ansible_facts['distribution_major_version'] | int >= 9
  • | int is a filter. The pipe hands the value on its left to int, which turns the text "9" into the number 9. The filter runs before the comparison, so no parentheses are needed.
  • Text cannot be compared with a number. Without the filter, "9" >= 9 is an error and the task fails.
  • Text is compared with text one character at a time. "10" >= "9" is false, because 1 comes before 9.
  • Take the operator from the words of the task. "9 or higher" and "at least 9" include 9, so write >= 9. "Higher than 9" leaves 9 out, so write > 9.
  • Values are case-sensitive. The output says "CentOS", so == 'Centos' is false on every host. Copy the value from the output instead of typing it from memory.
  • | int never reports an error. Text that is not a number becomes 0, silently.

A value with no quotes, such as ansible_memtotal_mb, is a number already and needs no filter.

When a task needs root

The play connects to servera as student, an ordinary user. That is enough to read facts and print messages. It is not enough to install a package, manage a service, or write a file outside /home/student. Those tasks need become: true:

- name: Exam-style task
  hosts: all
  become: true      # run the tasks as root, through sudo
  tasks:
  • Put it at the play level, in line with hosts, to cover every task. It can also go on a single task.
  • Without it, dnf stops with This command has to be run under the root user. and a file under /root or /etc stops with Destination /root not writable.
  • A task that is skipped by its when: never asks for root, so a missing become can hide on one host and fail on the next.
