Kube Harbor — How It's Built

A Kubernetes cluster simulated in the browser: real control loops, real kubectl output, 19 missions from first get pods to a broken control plane.

Overview

Kube Harbor teaches Kubernetes by making you operate one. A three-node cluster (one control plane, two workers) runs a small app, "Harbor Watch", with web, api, worker and postgres tiers. Each mission explains a concept, plants a realistic fault, and checks the cluster's state, not your keystrokes, to decide whether you fixed it. Any correct fix counts, including one I didn't think of.

The missions follow a four-session workshop arc. Session 2 meets the cluster: RBAC, self-healing, ImagePullBackOff, CrashLoopBackOff. Session 3 deploys the whole app: Secrets, Service selectors, DNS, NodePort, probes, node-local storage. Session 4 operates it: OOMKilled, Pending, rollouts, rollback, Ingress, LoadBalancer. An Expert tier covers Secret exposure, a drain blocked by a PodDisruptionBudget, and a crashed kube-scheduler.

Tech Stack

JavaScript (ES modules) HTML CSS node:test
  • No framework and no dependencies. The YAML parser, kubectl, and the controllers are all hand-written, so the page runs under a strict script-src 'self' CSP.
  • Shared code with Cold Case Server: the pipe filters (grep, sort, awk …) are imported from ../cold-case/shell.js.
  • 51 tests replay every mission's solution against a fresh cluster.

How Each Part Works

cluster.js: the reconcile loop

Kubernetes is declarative: you change the desired state and controllers converge reality toward it. The simulator runs the same loop. Every kubectl command lets 10 simulated seconds pass, and each tick runs the controllers in order: 

tick() {
  this.deploymentController();   // template hash → ReplicaSet; rolling update with maxSurge / maxUnavailable
  this.replicaSetController();   // create or delete Pods until count == spec.replicas
  this.scheduler();              // taints, nodeSelector, requests vs allocatable, PV node affinity
  this.kubelet();                // image pull, config refs, start, crash back-off, OOM, probes
  this.endpointsController();    // Ready Pods matching each Service selector
}

Behavior emerges from the loop instead of being scripted. A bad image tag produces ErrImagePull → ImagePullBackOff. A missing environment variable produces a crash with exponential back-off. A memory limit below the app's usage produces OOMKilled with exit code 137. A crashing rollout stalls while the old ReplicaSet keeps serving, because maxUnavailable protects it. Relabeling a Pod makes its ReplicaSet release it and create a replacement, just as the real controller does.

kubectl.js: output a real operator recognizes

Column layouts, error strings and events copy real kubectl v1.33. That includes RBAC Forbidden errors naming the ServiceAccount and scope, FailedScheduling censuses ("0/3 nodes are available: 2 Insufficient cpu, 1 node(s) had untolerated taint…"), event counters like (x6 over 50s), and RESTARTS like 4 (40s ago). Supported verbs: get / describe / logs / exec / apply / create / delete / edit / patch (strategic merge by container name) / label / set image|env|resources / scale / rollout / expose / auth / top / cordon / drain. Output formats are -o wide|yaml|json|name|jsonpath, plus -w, -l, $(…) and pipes. 

$ kubectl get secret harbor-db -o jsonpath='{.data.DB_PASSWORD}' | base64 -d
tide-7Kq2-harbor          ← the Expert lesson: base64 is an encoding, not encryption

missions.js: goals are predicates on state

goal: (c) => { const s = c.get('Service', NS, 'api'); const d = dep(c, 'api');
  return eps(c, 'api') >= 2 &&
    Object.entries(s.spec.selector).every(([k, v]) => d.spec.template.metadata.labels[k] === v); }

The second clause makes the fix durable. Hand-labeling the running Pods fills the endpoints for a moment, but it doesn't count, because the next rollout would break it again.

yaml.js: a YAML subset for kubectl edit

kubectl edit and nano FILE open an in-page editor. Saving parses the YAML (block maps, lists, list-of-maps, quoted scalars, | blocks) and applies it. A test round-trips every manifest the game ships: load(dump(x)) must equal x.

Honest simulation limits

This is a model of Kubernetes, not Kubernetes. There is one container per Pod, no StatefulSets/DaemonSets/Jobs, no HPA and no NetworkPolicy, and HTTP is simulated per image. Time advances per command instead of continuously. Every mission ends with a command to run on a real cluster (kind in Podman), because the simulator is the map, not the territory.

Replicate It Yourself

  1. Store objects as plain JSON keyed by kind/namespace/name, with the same shape the real API uses. Then -o yaml is just a serializer.
  2. Write controllers as pure functions over the store, and run them in a fixed order on every tick. Make the kubelet a per-Pod state machine (creating → running → back-off).
  3. Express each mission's win condition as a predicate on cluster state, and make a test replay the reference solution against it.
  4. Validate realism against a real cluster: kind create cluster in Podman, break the same things, and diff the output. Reference: Kubernetes controllers.
