AWS Lambda

The compute service you don't run. Upload a function, point an event source at it, and AWS executes your code on demand — billed per millisecond — without a server in sight. Most modern AWS architectures bottom out in Lambda somewhere.

01 What is Lambda?

Lambda is the AWS service that runs your code in response to an event — without you provisioning, patching, or scaling a server. You hand AWS a small bundle of code, tell it what should trigger the function, and pay only for the milliseconds it actually runs.

Behind the curtain Lambda runs your function inside a Firecracker microVM that AWS spins up, reuses for a while, and eventually retires. You never log into it, never patch it, never see its IP. The trade-off: your code has to be quick (15-minute hard limit), stateless between invocations, and small enough (250 MB unzipped, or 10 GB as a container image) to fit the runtime contract.

The four primitives

  • Function — your code plus its runtime (Python, Node, Java, Go, .NET, Ruby, or a custom runtime). The unit you deploy and version.
  • Execution role — the IAM role Lambda assumes when it runs. Determines which AWS APIs your code can call. The most important security knob in the entire service.
  • Event source — what wakes the function up: S3 PutObject, API Gateway request, EventBridge cron, SQS message, DynamoDB Stream, manual invoke, Function URL, and ~200 more.
  • Concurrency — how many copies of your function may run at once. Default 1,000 per region per account; can be reserved (cap) or provisioned (pre-warmed).
In one sentence

Lambda is "run my code when something happens, scale automatically, charge me by the millisecond" — and the bill stops the instant the event queue empties.

02 A vibrant example: FINRA's 75-billion-events-a-day surveillance

The Financial Industry Regulatory Authority (FINRA) runs market-surveillance analytics on roughly 75 billion stock-market events per day — every quote, trade, and order from every U.S. equity and options exchange — and the platform is built on Lambda. It's one of the largest publicly documented Lambda deployments on AWS.

The pattern: market events land in S3 throughout the trading day. Lambda functions, fanned out to thousands of concurrent invocations, parse and enrich each batch, write structured output to other S3 prefixes, and publish anomaly findings to downstream surveillance jobs. There are no servers to scale up before market open or scale down after close — concurrency tracks demand automatically. FINRA's own writeup quotes a roughly 50% cost reduction versus the cluster-of-servers architecture they replaced. FINRA on AWS →

What makes it a useful Lambda lesson, not just a war story: the workload is bursty, embarrassingly parallel, security-regulated, and event-driven — exactly the shape Lambda was built for. The same pattern applied to log enrichment, fraud detection, or compliance sweeps in your own account is a perfectly reasonable reach for a junior cloud-security engineer. That's Lambda in production.

03 Who uses Lambda — and why

Lambda is everywhere because the price-per-invocation is hard to beat and the operational cost is essentially zero. A few publicly documented examples:

🤖 iRobot

Connected vacuums emit telemetry at scale; iRobot processes it through Lambda + IoT Core, scaling to millions of devices without managing fleet servers. iRobot AWS case study →

🥤 Coca-Cola Freestyle

Every drink poured at a Freestyle vending machine fires a Lambda — for inventory, recipe analytics, and the loyalty app. Deeply transactional, very bursty. Coca-Cola AWS case study →

📓 Notion / modern SaaS

Image resizing, file conversion, and notification fan-out run on Lambda across most "modern SaaS" you use every day. The unsexy backbone of the contemporary web.

🎬 Netflix

Event-driven encoding pipelines, file validation, and security tooling all use Lambda. Netflix's Security Monkey and Repokid lineages helped popularize "compliance as code in Lambda."

🛂 Defense / cleared workloads

AWS GovCloud customers use Lambda for event-driven security automation — rotate credentials, quarantine resources, respond to GuardDuty findings — without standing up always-on infrastructure on a regulated network.

🚀 Startups (the 2 a.m. cron job)

Every startup runs at least one Lambda by year two: nightly DB backup, Slack-bot, GitHub webhook, billing-alert handler. It's the "free tier of running anything ever again" service.

Common reasons Lambda gets called out specifically

  • Event-driven architectures — S3 PutObject → Lambda is the canonical "do something when a file lands" pattern. EventBridge rules + Lambda is how AWS itself wires automation.
  • Glue between AWS services — when two AWS services need to talk and there's no built-in integration, the answer is almost always "a small Lambda."
  • Cost-sensitive workloads with idle time — anything that runs a few minutes a day costs cents on Lambda versus dollars on an always-on instance.
  • Serverless web backends — API Gateway + Lambda + DynamoDB is a complete production stack with no servers to patch.
  • Security automation — GuardDuty finding → Lambda → quarantine the IAM principal is a one-page answer to "how do we respond to incidents at 3 a.m. without a human?"

04 Competitors & market share

Lambda invented the modern function-as-a-service category in 2014. The other major clouds and a few independents have shipped credible alternatives since. Honest framing: the model differences are real, and "which one wins" depends on what you're optimizing for.

AWS Lambda ~30% Largest event-source catalog (200+ AWS services + EventBridge), best-in-class concurrency model, ARM/Graviton cost wins, deepest IaC tooling.

The honest "why AWS Lambda"

Lambda's pricing is the sharpest of any major cloud — 1M free invocations/month, 400,000 GB-seconds free, then sub-cent rates. Combine that with the AWS event-source catalog (every service emits events Lambda can consume) and the gravitational pull is hard to escape once you're already in AWS. On a greenfield project Cloud Run or Cloudflare Workers may genuinely fit better.

Where Lambda doesn't always win

  • Cold-start sensitive workloads: first-invocation latency in the 100 ms–2 s range depending on runtime and VPC config. Cloudflare Workers and Cloud Run's second-gen runtime are faster. Provisioned concurrency closes the gap on Lambda but at a cost.
  • Long-running jobs: 15-minute hard wall-clock limit. Anything longer needs Step Functions, Fargate, or AWS Batch.
  • Container-first teams: Cloud Run / ECS Fargate let you ship the same Dockerfile you already build, with no special-casing for the Lambda runtime contract.
  • Heavily stateful workloads: Lambda is stateless between invocations. Anything needing in-memory state across requests usually wants a container.

05 Who actually runs it for you?

Lambda's "shared responsibility" line is unusually customer-friendly: AWS runs the host, the runtime, the patches, the autoscaler. You own the function code, the dependencies, the execution-role policy, the event-source wiring, and the secrets. Misconfigurations and supply-chain issues stay entirely on you.

👤 Self-managed (startup / solo)

You write the function, you write its IAM role, you wire up the event source. Easy to attach AWSLambdaBasicExecutionRole + AmazonS3FullAccess "to make it work." Don't.

🏢 Cloud platform team

Owns the Lambda baseline: standard runtimes, signed-layer policy, code-signing config, default tags, log retention, default reserved concurrency. Developers ship via PR-driven IaC, not Console clicks.

🛡 Cloud security engineering

Owns dependency scanning (Snyk, Dependabot, ECR scanning for container images), secrets-out-of-env enforcement, code-signing roots of trust, and incident response when a Lambda's role gets used badly.

🤝 Third-party serverless platforms

Serverless Framework, AWS SAM, Terraform, Pulumi, SST — toolchains that wrap Lambda and its event sources into a deploy pipeline. Most production teams use one.

🤖 Automated tooling

AWS Lambda Powertools (logging, tracing, metrics), Cloudsplaining for execution-role audits, OWASP Serverless Top 10 scanners. Increasingly run inside CI to gate every deploy.

🛂 Compliance / GRC

FedRAMP, SOC 2, PCI assessors look at execution roles, code-signing, log retention, and dependency provenance. Serverless makes some controls easier (no host patching) and others harder (proving artifact integrity).

⚠️ Startup gotcha

First-time Lambda builders often paste secrets into Environment Variables in the Console. Those values are visible in CloudTrail, in error reports, and to anyone with lambda:GetFunctionConfiguration. Lambda env vars are config, not secrets. Use Secrets Manager or Parameter Store (SecureString) and pull at cold start.

06 Security mindset

Most Lambda incidents aren't novel — they're recycled web-app and supply-chain vulnerabilities with a serverless flavor. Internalize five things and you're already ahead of most production Lambda code in the wild.

Five things to internalize before you ship your first function

  • One execution role per function, scoped tight. Resist the urge to share a single LambdaBasicExecutionRole across every function. The blast radius if a function is compromised is its execution role's permissions.
  • Env vars are NOT secrets. They're surfaced in CloudTrail, X-Ray traces, error reports, and to anyone with lambda:GetFunctionConfiguration. Real secrets live in Secrets Manager or Parameter Store and get pulled on cold start.
  • Reserved concurrency is a safety brake. A runaway loop or a misfiring event source can scale your function to thousands of concurrent invocations — and the bill that follows. Cap concurrency on anything that doesn't genuinely need to burst.
  • VPC config is a tradeoff, not a default. Attaching a Lambda to a VPC adds cold-start cost and ENI overhead; only do it when the function genuinely needs private-subnet egress (e.g., to reach an RDS instance). Don't VPC-attach reflexively.
  • Supply chain is the new perimeter. Codecov 2021, the npm colors incident, the PyPI typo-squat parade — a Lambda is only as trustworthy as its dependencies. Pin versions, scan layers, sign artifacts, prefer container images you build over zip uploads.
For your career

Lambda hardening shows up on the AWS Security Specialty (SCS-C02) and in every real audit: execution-role least privilege, code signing, log retention, secrets handling, supply-chain provenance. Get fluent at deploying one function with all the knobs set correctly — Console, CLI, and Terraform — and you can bring that muscle memory to the largest Lambda fleet you'll ever see.
