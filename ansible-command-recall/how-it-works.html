Ansible Command Recall — How It's Built

Type the command from memory; the checker decides whether it means the same thing.

Overview

Recognising a command on a page is easier than producing it at an empty prompt. Each card asks one question, such as "What is the command to open your Vim config file?", and you type the answer. The hard part is the checker. A plain string comparison would mark ansible webservers -m ping -i inventory wrong because the answer key puts -i first, which teaches the wrong lesson. Ansible does not care about that order, so the checker does not either. It does care about the mistakes that break a real shell: curly quotes pasted from a notes app, an en dash in place of --, and capital letters.

Tech Stack

HTML CSS JavaScript modules Node test runner
  • HTML and CSS — one page with three views: the decks, the card being asked, and the end of the round.
  • JavaScript modules — checker.js and game.js have no screen access, so the same code runs in the browser and in the tests.
  • Node test runner — Node's built-in node --test. No packages to install.

How Each Part Works

cards.js — the question bank

Each card has a question, the answer, a one-line explanation, and for longer commands a table of what each flag means. Cards are grouped in four decks: control node prep, ansible.cfg, the inventory, and ad hoc commands. Adding a card means copying an entry; a test checks every field, rejects duplicate ids, and rejects any answer containing a curly quote or dash.

checker.js — comparing by meaning

The typed line is split into words the way bash does it: quotes group words and are removed, and a backslash escapes the next character, except inside single quotes. For ansible and ansible-inventory the words are then rebuilt in a fixed order: the host pattern, the options sorted, then any > redirection. Long and short options are treated as one (--become is -b), ansible.builtin.user is user, and leaving out -m command is the same as writing it, because command is the default module. The -a string is split into key=value pairs and sorted, with yes, true and on treated alike. Free-form modules such as command keep their string as typed.

Config and inventory cards are read as INI: each line is filed under its section, and the set of lines is compared, so sections and lines may come in any order and key=value spacing is ignored. Host-list cards compare a set of names, which is also the lesson: serverb is in two groups but all lists it once.

When the answer is wrong for a reason the checker can name, it says so: curly quotes, an en dash, a capital letter, or an unclosed quote. When it cannot name one, the player may count the answer anyway with "mine does the same thing", because there is more than one right way to write most commands.

game.js — the round

A round shuffles the chosen deck. A missed card goes back into the queue three cards later, so it is asked again before the round ends, and it does not count toward the first-try score. Progress per card is kept as right, wrong and current streak; a card is known after three right answers in a row and a miss resets the streak.

Security

  • Content-Security-Policy — script-src 'self': no inline script and nothing from another site.
  • No innerHTML — everything typed is put on the page as text, never as markup, and nothing typed is executed. A test enforces this.
  • No network calls — progress is kept in the browser's local storage only, and entries that do not match the expected shape are dropped when read back.
  • Safe defaults in the answers — the sudoers card says to validate the file with visudo -cf, and the host_key_checking card says why it belongs in a lab and not in production.

Limits

  • Nothing is executed — run the commands on a lab afterwards; that is the step that counts.
  • Not a full shell parser — variables, globs and command substitution are not expanded, and for commands other than ansible the words must match in order.
  • One model answer per card — option order is free, but the values must match the question.
