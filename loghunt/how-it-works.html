LOGHUNT — How It's Built

A real Linux system in a browser tab, one invented break-in, and every answer checked against the real tools.

Overview

Most command-line tutorials show a command and its output, and the learner nods along. LOGHUNT makes you type the command yourself, at a real bash prompt, against logs that look like the ones on a RHEL server: Apache access logs with a compressed rotation, /var/log/secure, auditd records with epoch timestamps, firewall key=value lines, a metrics CSV with broken rows, and sar output on a 12-hour clock. One attacker runs through all of them: a scan, an SSH brute force, a login, sudo to a root shell, a dropper, and data leaving on an unusual port.

Ten levels teach one tool each, from find to comm and join. The last level asks for a single line: who, as which account, since when, and where the data went. The first sighting is a single request, 26 hours before the scan, in the one log file that plain grep cannot read.

Tech Stack

v86 (x86 emulator in WebAssembly) Alpine Linux + GNU tools xterm.js JavaScript modules Node test runner Podman (image build)
  • v86 — emulates a 32-bit PC in WebAssembly and boots a real Linux kernel. Chosen over CheerpX/WebVM because GitHub Pages cannot send the cross-origin isolation headers CheerpX needs, and v86 is BSD-licensed.
  • Alpine Linux with GNU coreutils, grep, sed, gawk, findutils and gzip — real GNU behaviour and real error messages. The page restores a saved snapshot of the booted machine, so there is no boot wait.
  • xterm.js — the terminal on the page, connected to the VM's first serial port.
  • Node test runner — the same snapshot boots under Node, so the tests and the selftest run the exact machine the page runs.
  • Podman — builds the guest image from a Containerfile; v86 runs it from that root filesystem.

How Each Part Works

story.js and generator.js — the incident

story.js holds every fact of the campaign: the attacker's address, the victim account, and a timeline from the first probe to the end of the exfil. generator.js turns it into about 20,000 log lines across 37 files, in about 25 milliseconds, from a fixed seed. Each log source draws from its own random stream, so adding noise to the firewall log never shifts an answer in the web log. A test pins a SHA-256 of the whole archive, so any change to the data is a deliberate one.

The arena is built in JavaScript and handed to the guest as one tar file, because tar headers carry modification times and find -mtime answers depend on them. The compressed rotation is gzipped inside the guest with gzip -n, so its bytes, and so its size, never vary between browsers.

levels/*.json — the content

Each level is a JSON file: briefing, lesson, three to five worked examples on small training files, one challenge, three hints, and a debrief with a reference solution, an alternative, and why it matters on a real host. A new level needs no code. A validator checks every file when the page loads, in the lint step, and in the tests.

tools/selftest.mjs — no answer written by hand

Every example output and every answer was taken from the real guest. The selftest boots the snapshot, seeds the arena, runs every worked example and compares its output byte for byte, then runs both the reference solution and the alternative and checks that each one hashes to the stored answer. Two pipelines built from different evidence have to agree. Writing them this way caught real mistakes: GNU zgrep rejects -r, and this VM has no locale data, so the sort-order lesson had to become a note instead of a demo.

checker.js and progress.js — answers and score

Answers are trimmed, lowercased, and whitespace is collapsed, then hashed with the level id: sha256("loghunt:v1:<id>:<answer>"). The page stores only the hash. Each level is worth 100 points, minus 10, 20 or 35 for each hint tier; wrong attempts cost nothing. Progress stays in the browser's local storage, with a two-click reset.

live.js — the side quest that writes while you watch

The tail -f side quest needs a log that grows. A level names a setup by key only ("setup": "live-feed"); the shell that runs is fixed in live.js, never read from a level file. It starts a writer as the learner's user, a few lines at once and then one every few seconds. The seed script stops it on every reset.

Security

  • Commands never leave the tab — everything typed runs inside the emulated machine in your browser. There is no server, and the VM has no network interface except loopback; the snapshot build fails if a network request from the guest succeeds.
  • No root for the learner — the shell runs as analyst. Root's password is locked, BusyBox's setuid helper is disabled, and there is no sudo; the build checks that su cannot reach uid 0.
  • Content-Security-Policy — script-src 'self' 'wasm-unsafe-eval' (v86 compiles guest code to WebAssembly at run time) and worker-src blob: (v86's helper workers). Nothing loads from another site; a test pins the exact policy.
  • Integrity — the snapshot's SHA-256 is checked before it runs; third-party code (v86, xterm.js) is vendored with recorded hashes, not loaded from a CDN.
  • No innerHTML, no eval — level text is put on the page as text only. A fork bomb hits a 128-process cap, and output floods are throttled, so the page stays responsive; Restart terminal throws the machine away and restores the snapshot in under a second.
  • Invented data only — documentation IP ranges (RFC 5737), example.com, and made-up account names.

Limits

  • A 14 MB download — the saved machine has to be fetched once; on a phone the lessons load first and the terminal only on request.
  • Answers can be found in the source — the generator runs in the browser and the code is public. Hashing only stops a casual peek; this is a learning game, not a competition.
  • Alpine, not RHEL — the tools are GNU, but there is no journalctl, ausearch or sar to run. The debriefs say where each step differs on a real RHEL host.
