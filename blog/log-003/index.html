A Home Lab for Kubernetes and Terraform on macOS: Free First, Cheap Second

A free local cluster, Terraform managing it, short cloud sessions that cost a few dollars, the organizations that run these tools in production, and what the related jobs pay.

The Short Version

You can learn Kubernetes and Terraform to a professional standard on one Mac, and most of it costs nothing. Build the lab in three tiers: a multi-node cluster on the laptop, Terraform managing that cluster, then short cloud sessions you destroy the same day.

The first two tiers are free. The third costs roughly one to three dollars per session if you tear everything down before you close the laptop. This entry walks through the tiers in order, then covers who runs these tools in production and what the related jobs pay.

The commands assume an Apple silicon Mac with Homebrew installed and 16 GB of memory.

The Model Before the Tools

Kubernetes and Terraform are both declarative systems. You describe the end state you want, and the tool works out the steps to reach it. Kubernetes does this continuously with control loops. Terraform does it on demand with a plan followed by an apply.

Each keeps a record of what it believes exists. For Terraform that record is the state file. For Kubernetes it is the API server, backed by a database called etcd. The gap between what is declared and what is actually running is called drift, and most of the daily work with either tool is finding and closing that gap.

Who Runs This in Production

Kubernetes makes servers interchangeable: any machine in the cluster can run any workload, so a failed machine is replaced instead of repaired. Terraform makes infrastructure reviewable: a change to a network or a permission arrives as a code change that someone can read before it happens.

Kubernetes

OrganizationWhat it runs on Kubernetes
Spotify Its backend services. Spotify replaced a homegrown orchestrator called Helios, and reported that creating a new service dropped from about an hour to seconds.
CERN Physics data processing. Batch workloads make up more than 80 percent of its resource usage.
Chick-fil-A A small cluster inside each restaurant, on three low-power computers, so ordering and kitchen systems do not depend on a distant data center.
United States Air Force Flight software experiments. Kubernetes ran on an F-16 in 2019 and flew on a U-2 in September 2020, running machine learning code alongside the aircraft's existing computers.
OpenAI Machine learning training. It published how it scaled a single cluster to 7,500 nodes.
Mercedes-Benz Close to 1,000 clusters that serve its internal software teams.

Terraform

OrganizationWhat it manages with Terraform
Slack Infrastructure across several cloud providers. Slack chose Terraform so that one tool and one syntax would cover all of them.
cloud.gov The network and infrastructure layer of the United States government's application platform, kept in a public repository.
Helvetia Insurance A move of about 200 applications to the cloud in one year, with new cloud accounts provisioned in minutes instead of days.
Skechers Provisioning workflows that went from days or weeks to hours.

The pattern is the same in every row. Terraform builds the platform, Kubernetes runs the workloads, and both are changed through reviewed code.

Step 0: Set the Budget

TierWhat runsCost
Local cluster A three-node Kubernetes cluster inside a virtual machine on the Mac Free
Local Terraform Terraform managing that same cluster Free
Cloud sessions Short-lived cloud resources, destroyed the same day About one to three dollars per session

Two charges surprise people in the cloud tier, so learn them before Step 5:

  • The managed Kubernetes control plane. On Amazon Web Services (AWS), Elastic Kubernetes Service (EKS) bills about ten cents an hour for the control plane alone. Forgotten for a month, that is roughly 73 dollars.
  • The NAT gateway. A network address translation gateway bills by the hour even when no traffic passes through it.

Step 1: Install the Tools

brew install podman kind kubectl helm trivy
brew tap hashicorp/tap
brew install hashicorp/tap/terraform
  • podman runs containers, inside a small Linux virtual machine it manages for you.
  • kind builds a Kubernetes cluster where each node is a container.
  • kubectl is the command-line client for any Kubernetes cluster.
  • helm installs packaged applications into a cluster.
  • trivy scans configuration and container images for security problems.
  • brew tap hashicorp/tap adds the publisher's own package source, which carries current Terraform releases.

Terraform's license changed in 2023 from open source to the Business Source License. OpenTofu is the open-source fork, and its syntax is almost identical. Everything in this entry works with either.

Step 2: Build a Multi-Node Cluster

Create and start the virtual machine that will hold the cluster:

podman machine init --cpus 4 --memory 8192 --disk-size 60 --rootful
podman machine start
  • --cpus 4 gives the virtual machine four processor cores.
  • --memory 8192 gives it 8 GB of memory, written in megabytes.
  • --disk-size 60 gives it a 60 GB disk.
  • --rootful runs containers as root inside the virtual machine, which the cluster's node containers need in order to manage resource limits reliably.

Describe the cluster in a file named kind-lab.yaml:

kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
  - role: worker

Then create it and confirm the nodes are healthy:

KIND_EXPERIMENTAL_PROVIDER=podman kind create cluster --name lab --config kind-lab.yaml
kubectl get nodes -o wide
  • KIND_EXPERIMENTAL_PROVIDER=podman tells kind to use Podman instead of Docker.
  • --name lab names the cluster. kubectl will know it as kind-lab.
  • --config points to the file that lists the nodes.
  • -o wide adds each node's address, operating system, and container runtime to the output.

All three nodes should report Ready. Three nodes matter because scheduling, draining a node for maintenance, and spreading copies of an application across machines cannot be seen on a single node.

Step 3: Work the Cluster by Hand

Spend the first week driving the cluster with kubectl and nothing else. You cannot debug what automation builds until you can build it yourself. Practice in this order:

  1. Pods, Deployments, and Services
  2. ConfigMaps and Secrets
  3. Health probes and resource limits
  4. Role-based access control

Three commands explain most failures:

kubectl describe pod POD_NAME
kubectl logs POD_NAME --previous
kubectl get events --sort-by=.lastTimestamp
  • describe shows scheduling decisions, image downloads, and failed health checks.
  • --previous prints the logs of the container that crashed, not the one that replaced it.
  • --sort-by=.lastTimestamp puts events in time order, so the cause appears before the effect.

Step 4: Let Terraform Manage the Cluster

Save the following as main.tf in an empty directory. It creates a namespace that enforces the strictest built-in security standard, a hardened web server with two copies, and a network rule that blocks all incoming traffic by default. 

terraform {
  required_version = ">= 1.6"
  required_providers {
    kubernetes = {
      source  = "hashicorp/kubernetes"
      version = ">= 2.30"
    }
  }
}

provider "kubernetes" {
  config_path    = "~/.kube/config"
  config_context = "kind-lab"
}

resource "kubernetes_namespace_v1" "web" {
  metadata {
    name = "web"
    labels = {
      "pod-security.kubernetes.io/enforce" = "restricted"
    }
  }
}

resource "kubernetes_deployment_v1" "web" {
  metadata {
    name      = "web"
    namespace = kubernetes_namespace_v1.web.metadata[0].name
  }
  spec {
    replicas = 2
    selector {
      match_labels = { app = "web" }
    }
    template {
      metadata {
        labels = { app = "web" }
      }
      spec {
        automount_service_account_token = false
        security_context {
          run_as_non_root = true
          seccomp_profile {
            type = "RuntimeDefault"
          }
        }
        container {
          name  = "nginx"
          image = "nginxinc/nginx-unprivileged:1.27-alpine"
          port {
            container_port = 8080
          }
          security_context {
            allow_privilege_escalation = false
            read_only_root_filesystem  = true
            capabilities {
              drop = ["ALL"]
            }
          }
          resources {
            requests = { cpu = "50m", memory = "64Mi" }
            limits   = { cpu = "200m", memory = "128Mi" }
          }
          volume_mount {
            name       = "tmp"
            mount_path = "/tmp"
          }
        }
        volume {
          name = "tmp"
          empty_dir {}
        }
      }
    }
  }
}

resource "kubernetes_network_policy_v1" "default_deny" {
  metadata {
    name      = "default-deny-ingress"
    namespace = kubernetes_namespace_v1.web.metadata[0].name
  }
  spec {
    pod_selector {}
    policy_types = ["Ingress"]
  }
}
terraform init
terraform plan -out=tfplan
terraform apply tfplan
  • init downloads the Kubernetes provider and writes a lock file that pins its checksums. Keep that file in version control.
  • plan -out=tfplan saves the exact set of changes Terraform intends to make.
  • apply tfplan carries out the saved plan and nothing else, so what runs is what you reviewed.

Check the security controls, not just the deployment

kubectl -n web get pods
kubectl -n web run bad --image=nginx --privileged
trivy config .
  • -n web points the command at the web namespace.
  • --privileged asks for a container with full access to the host. The namespace should refuse it, and that refusal is the passing result.
  • trivy config . scans the Terraform in the current directory for insecure settings.

Why it is written this way

  • Least privilege. The container runs as a normal user, cannot gain new privileges, has every Linux capability removed, and can write only to a temporary directory. A compromised container has very little to work with.
  • State is sensitive. A local state file is fine for a lab. In production it can contain secrets in plain text, so it belongs in encrypted remote storage with locking and narrow access.
  • See drift for yourself. Change the number of copies by hand with kubectl -n web scale deploy web --replicas=5, then run terraform plan. Terraform proposes putting it back to two.
  • A real disagreement. Many teams use Terraform to build the cluster and a different tool, such as Helm or Argo CD, for what runs inside it. Managing workloads with Terraform is a good way to learn both, and it is worth knowing why teams draw that line.

Step 5: Add the Cloud Without the Invoice

A local cluster teaches Kubernetes. It cannot teach cloud identity and permissions, cloud networking, or managed node groups. Those need a real account, used carefully.

  1. Create a budget alarm first. Before any other resource, define an alert at ten dollars, in Terraform.
  2. Set up remote state second. Use a storage bucket with versioning and encryption turned on and public access blocked.
  3. Practice on what is free. Networks, firewall rules, permission roles, and storage policies cost little or nothing to create.
  4. Treat managed Kubernetes as a timed session. Build the cluster, practice for two hours, and run terraform destroy before you stop.

Verify the teardown. After every session, open the billing console and confirm that no gateway, load balancer, or storage volume survived. Use an account protected by multi-factor authentication, and never create access keys for the root user.

Step 6: The Order of Study

WeeksFocus
1 and 2Steps 1 to 3. Rebuild the cluster from memory until it is boring.
3 and 4Step 4. Then add Helm, Terraform modules, and variables.
5 and 6Break things on purpose: stop a node, corrupt a configuration file, remove an entry from the state file, and recover each time.
7 and 8Step 5, as two or three timed cloud sessions.

Two certifications measure this material: the Certified Kubernetes Administrator exam and the Terraform Associate exam. Both are easier after the lab than before it.

What the Market Pays

"Kubernetes engineer" is rarely a posted job title. Kubernetes and Terraform appear as required skills inside the titles below, which are the ones employers actually advertise. Figures are United States base salaries from 2026 sources. Bonuses and stock are extra.

Job titleReported base paySource
DevOps engineer Average of 125,000 dollars with Kubernetes skills. Most fall between 82,000 and 173,000. Payscale
DevSecOps engineer Median of 131,000 dollars. The top tenth earn 161,000 or more. Salary.com
Cloud engineer 110,000 to 155,000 dollars. Robert Half
Cloud security engineer Average of 136,000 dollars. A second source reports 94,000. Payscale, Salary.com

The highest-paying titles at mid-career

Job titleReported base payWhy it pays more
Site reliability engineer Median of 140,000 dollars, ranging from 110,000 to 180,000. Owns production uptime, carries on-call duty, and usually writes real code.
Platform engineer 115,000 to 155,000 dollars at mid-level. Average of 166,000 with Kubernetes skills. Builds the internal platform other engineers deploy onto, so one hire speeds up many teams.
Cloud security architect Mid-career average of 157,000 dollars. Owns security design across accounts and networks, not single controls.
Cloud architect About 193,000 dollars in one self-reported comparison. Owns the overall design. The title rarely goes to anyone with fewer than five years of experience.

Read these numbers as rough bands, not quotes. Salary sites measure different things, some rely on self-reported pay, and two sources can differ by 40,000 dollars for the same title. The steadier lesson is in the last column: the better-paid titles own an outcome, such as uptime, a platform, or a design, where the others operate a tool.

Verdict

  • The lab is free where it matters. A three-node cluster and Terraform both run on one laptop at no cost.
  • Work by hand before you automate. Terraform is far easier to debug once you can build the same thing with kubectl.
  • Spend money only on what a laptop cannot teach, and destroy it the same day.
  • The skill is prediction. You know a tool when you can say what it will do before you press Enter, and explain the difference when it does something else.
