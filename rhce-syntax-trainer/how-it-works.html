RHCE Syntax Trainer — How It's Built

A type-the-answer trainer for the EX294 Ansible exam: 39 chained tasks, a vim-faithful editor, and per-requirement checking that never fakes a pass.

Overview

The RHCE Syntax Trainer turns a full EX294 practice exam (questions Q1–Q8) into a typing game. Instead of picking from multiple choice, you type the real artifact the exam asks for — the playbook, the Galaxy requirements file, the ad hoc command — inside a simulated RHEL controller terminal with managed nodes serverb, serverc, and serverd. Every question chains the way the real exam does: set up, write the file, run it, then verify the result. A question only counts as passed when every one of its requirements checks out. A hint button nudges you with structure, and a reveal button shows the reference answer — but revealing never marks the question passed. Finishing a question unlocks its full explanation: what the step does, how it changes the Ansible environment, the technology underneath it, and how it connects to the questions around it.

Tech Stack

HTML CSS JavaScript

How Each Part Works

One check per requirement

Each question carries a list of independent checks — one per thing the exam actually grades. A YAML question might check the play name, the target hosts, the exact module arguments, and a task-level when guard as four separate tests run against your normalized text. All of them must pass; an empty editor passes none. That granularity is what makes the feedback useful: you see exactly which requirement you missed instead of a bare wrong/right. 

// One question = a list of small, honest tests
checks: [
  { label: "hosts: webservers",        test: t => /^hosts:\s*webservers\s*$/m.test(t) },
  { label: "become: true on the play",  test: t => /^become:\s*true\s*$/m.test(t) },
  { label: "template src + dest set",   test: t => /src:\s*index\.html\.j2/.test(t) && /dest:\s*\/var\/www\/html\/index\.html/.test(t) },
]

An editor that behaves like your vim

File questions open in an editor that mimics the exact .vimrc from question Q0: 2-space expandtab steps, autoindent, line numbers, cursor line and column, and a vim-style status line. Tab moves to the next 2-space stop (and indents a selection like >>), Backspace over pure indentation deletes one step, and Enter follows YAML's indent rules. A highlighting layer colors YAML keys, colons, quoted strings, booleans, numbers, and {{ }} Jinja expressions as you type, so the file reads the way it would in your real lab.

Chains, not flashcards

The 39 steps follow the exam's dependency chain — the Galaxy requirements file you write in Q4 is the one you install in Q4.2 and list in Q4.3; the role you scaffold in Q7 is the one you run in Q7.6 and curl in Q7.7. Command questions are checked when you press Enter, like a shell. Nothing is locked: the sidebar lets you jump to any question in any order, and the score counts only questions you genuinely passed.

Hints and reveals that keep score honest

The hint button describes the structure of the answer — the keys, the order, the shape — without giving the answer text. The reveal button asks for a confirming second click, then shows the reference. Revealing deliberately does not mark the question passed: the point of the trainer is muscle memory, and the score stays meaningful only if every pass was typed.

Replicate It Yourself

  1. Start from reference answers. Write the exact file or command each question should produce first. The trainer is only as good as its references — every checker is derived from one.
  2. Write one check per graded requirement. Resist the urge to compare whole files. Small tests over normalized text (trimmed, consistent line endings) accept harmless variation and pinpoint real mistakes.
  3. Verify the references against the checkers. Every reference answer must pass its own question's checks, and an empty answer must pass none. Automate both assertions before you ship.
  4. Keep the score honest. Let learners peek — but never let peeking count as passing.
  5. Deploy to GitHub Pages. Push to main, go to repo Settings → Pages → Source: Deploy from branch → main / (root). Reference: GitHub Pages docs.
