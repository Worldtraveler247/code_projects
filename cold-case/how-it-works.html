Cold Case Server — How It's Built

A lateral-thinking Linux triage game: characterize undocumented servers on a command budget, read-only.

Overview

Each case drops you onto a simulated server with a brief and a hidden truth. You investigate in a terminal, and every command that reads the server costs budget (a whole pipeline counts as one). Then you file a verdict: purpose, load, errors and risk, plus which findings belong in the report. The game trains the habit that separates seniors from juniors: survey, then target, then conclude from evidence, without changing anything.

The lateral part comes from constraints. Case 2 removes ss, netstat and lsof, so you have to walk /proc/net/tcp → socket inode → /proc/PID/fd yourself. Case 3 punishes trusting a healthy snapshot. Case 4 makes you prove effective config (sshd -T) rather than read the file. Case 5 is RHEL, where Debian habits fail and "Permission denied" means SELinux.

Tech Stack

HTML CSS JavaScript (ES modules) node:test
  • HTML: four views (case list, investigation, verdict, debrief) in one page, with no framework.
  • CSS: the App Hub design tokens, a sticky case file beside the terminal, and a single-column layout on phones.
  • JavaScript: a pure shell engine (shell.js) with no DOM access, case data (cases.js), and a thin DOM layer (game.js).
  • node:test: 29 tests that prove every case can be solved and that every tool agrees with every other tool.

How Each Part Works

shell.js: one world model, many views

The core design rule: tools are views of one kernel state. A case declares its sockets once. ss, netstat, lsof, /proc/net/tcp, /proc/PID/fd/* symlinks and curl are all rendered from that one list, so two tools can never disagree, which is exactly how the real kernel behaves. File descriptors and inodes are assigned at build time and reused everywhere. 

// /proc/net/tcp: IPv4 little-endian hex, port big-endian hex, same inode ss would report
`${String(i).padStart(4)}: ${ipToHex(s.laddr)}:${hex4(s.lport)} ${ipToHex(s.raddr)}:${hex4(s.rport)} ${st} … ${s.inode}`

// /proc/PID/fd/N: a symlink to socket:[inode], readable only by the owner or root
put(`${base}/fd/${s.fd}`, { type: 'link', target: `socket:[${s.inode}]`, procPriv: true, … });

Privilege is modeled too. ss -p hides other users' processes without sudo, dmesg is restricted on Debian/Ubuntu, docker needs root or the docker group, and /proc/PID/cwd of another user is unreadable. Pipelines, quoting, 2>/dev/null, $(…) and $((16#1F40)) are parsed by a small tokenizer, and the classic ps aux | grep x self-match (and the [x] trick that avoids it) happens just as it does on a real box.

shell.js: the read-only rule

Every pipeline segment is checked before it runs. A change does not execute; it is logged as a violation and costs 25 points.

[/^systemctl\s+(.*\s)?(stop|restart|kill|…)\b/, 'You changed a service state with no ticket and no rollback plan.'],
[/^setenforce\b/, 'You switched SELinux mode. …'],
// plus kill, rm/mv/chmod, package installs, firewall edits, and any > redirect to a real file

cases.js: the case file format

Each case is data: host facts, processes, sockets, systemd units, files, journal entries, plus the hidden truth. Evidence markers are strings or regexes. When a command's output contains one, that clue lights up on the case board, so the board rewards what you actually displayed, not what you typed. 

{ id: 'inode', label: 'Socket inode 48213 → PID 4127 (fd 3)',
  markers: ['/proc/4127/fd/3 -> socket:[48213]', '/proc/4127/fd/3\n'] }

Scoring

60 for verdict accuracy (questions, plus each finding correctly reported or rejected), 20 for evidence actually seen, and 20 for efficiency against par. Par is the budget the expert route spends, computed by running it, so free calculators such as printf don't inflate it. Efficiency is multiplied by the evidence fraction, so guessing with zero commands can't farm points. Answer options are shuffled every run.

tests/cases.test.mjs: proving the puzzles are fair

A deduction game with a contradictory clue is broken. The test suite guarantees, for every case:

✔ the expert route runs with no errors, stays in budget, and lights every clue
✔ /proc/net/tcp decodes back to exactly the socket list; ss agrees; find -lname maps every inode to its PID
✔ a perfect run scores 100; pure guessing scores ≤ 60
✔ destructive commands are blocked, free, and logged; strict budgets lock the shell

Honest simulation limits

This is a renderer, not a kernel. About 40 commands are modeled with the flags real triage uses. Anything else gets a realistic usage error. Globs expand with the privilege of the command, so sudo ls /proc/*/fd/* works here, while on a real box the unprivileged shell expands the glob first; the portable answer is sudo find /proc/[0-9]*/fd -lname …, which is the expert route. top and tail -f run in batch mode only.

Replicate It Yourself

  1. Model the state first. Write one list of processes and one list of sockets, and give every socket a PID, an fd and an inode. Every tool you add is just a renderer over that list.
  2. Build a tokenizer that respects quotes, then split on | outside quotes. Make the first segment a "producer" (reads the world) and the rest "filters" (text → text: grep, sort, uniq, awk, cut, tr).
  3. Write a case as data, and make the test suite replay its expert route. If the expert can't light every clue within budget, the case doesn't ship.
  4. Validate realism against a real box: run the same commands on a RHEL or Debian VM and diff the column layouts. Reference: proc(5) for /proc/net/tcp and /proc/PID/fd.
  5. Ship as static files. ES modules plus a strict CSP need no build step and no server. Run it locally with python3 -m http.server --bind 127.0.0.1 8000 from the repo root. Note the --bind: without it you have just built case 2, then push to GitHub Pages.
