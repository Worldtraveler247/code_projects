Current Events

The Original runc Container Breakout

A container is supposed to be a locked room inside your server. This vulnerability let a process inside that room walk out, rewrite the lock on the front door, and come back in as root on the host itself. This is CVE-2019-5736 — the original runc container breakout — and it's the incident most people mean, without realizing it, when they say "a container escape."

Here's what runc actually is. It's the low-level tool that Docker, and most of the container world underneath it, actually uses to create and start a container — the thing that does the actual work of putting a process in its own isolated namespace. In February 2019, runc's own maintainer, Aleksa Sarai, publicly disclosed a flaw he and other researchers had found: a malicious container image could overwrite the runc binary on the host machine itself.

Here's the chain, step by step. First, an attacker builds a malicious container image — nothing unusual yet, container registries are full of images from people you don't personally know. Second, someone with access to the host runs that container, or execs into it, as root — a completely routine administrative action. Third, during that exec operation, runc briefly opens a file handle to its own binary on the host, by path, through /proc/self/exe. The malicious process inside the container was able to race that exact moment, replacing what that file handle pointed to with its own payload. Once runc's own host binary was overwritten, every single container start or exec on that host afterward ran the attacker's code instead — as root.

Root cause, in one sentence: runc trusted a file-descriptor-and-path operation it assumed was safe because the container boundary was supposed to make it safe, and a malicious container used a race condition to break that assumption from the inside.

Here's what's worth saying plainly: exploitation required a privileged, interactive action — someone actually running or exec-ing into the malicious container as root. A container that just sat there running on its own, never exec'd into by an administrator, couldn't trigger this on its own. That's not a reason to shrug it off — plenty of automated pipelines routinely exec into containers as root — but it's the detail that separates this from a zero-click disaster.

What held: because this was caught and disclosed by the project's own maintainer rather than exploited first, there was no customer-zero scramble — Sarai coordinated a fix with Docker and the major Linux distributions before going public, and patches landed the same day as disclosure.

My read: this incident is the reason every container security conversation eventually arrives at "don't treat the container boundary as a security boundary you can fully trust." A senior engineer auditing a host doesn't just ask whether containers are isolated from each other — they ask what happens the moment a human or an automated job execs into one of those containers as root, because that's exactly the privileged seam this bug lived in.

What Held

The flaw was found and disclosed by the runc project's own maintainer and collaborating researchers, not discovered first by an attacker exploiting it in the wild — coordinated disclosure meant Docker and every major Linux distribution had a tested patch ready the same day CVE-2019-5736 became public, with no "zero-day" window of mass exploitation to manage. Exploitation also required an administrator to actively exec into or run the malicious container as root, which meant hosts that restricted who could run untrusted images, or who could exec into running containers at all, reduced their exposure even before patching. Naming that combination — coordinated disclosure plus a privileged-action precondition — in an interview signals that you understand why some critical-sounding CVEs never produce a mass-exploitation event, which is just as useful a judgment as being able to recite the CVE number.

Senior Security Advice

Enforce Default-Deny Egress Filtering at Every Network Boundary

The Advice

Configure every network boundary to deny all outbound traffic by default and allow only the specific destinations and ports a system actually needs.

Why It Matters

Most firewall programs put all their effort into keeping attackers out and almost none into controlling what talks its way back out. That gap is exactly what attackers rely on once they're already inside. After an initial compromise - a phished laptop, a vulnerable web app, a malicious package pulled into a build - the next step is almost always a callback: the malware reaches out to a command-and-control server, or an attacker starts quietly pushing data to an external host. If outbound traffic is wide open, that connection just works, and nobody notices until the data is already gone. This is the incident class ransomware and data-theft operations depend on - encryption or exfiltration both need a live outbound channel. NIST's control catalog addresses this directly: SP 800-53's SC-7(5), "Deny by Default / Allow by Exception," requires boundary devices to block all network traffic by default and permit only the connections an organization has explicitly approved, and SP 800-171 ties the same requirement to the plain rationale that a deny-all, permit-by-exception policy ensures only essential, approved connections are allowed. DISA's Firewall Security Requirements Guide enforces this as an auditable finding: a firewall that doesn't deny all traffic by default at a managed interface, inbound or outbound, fails the check.

How to Implement It

  1. Map what each system segment actually needs to talk to on the way out - specific IPs, domains, and ports - before touching any firewall rule, so the allow-list reflects real traffic instead of guesswork.
  2. Flip the default outbound rule on every boundary device and security group to deny, then add narrow allow rules only for the mapped destinations.
  3. Roll it out zone by zone, starting with the segments that hold the most sensitive data or the least business justification for broad internet access, rather than flipping the whole network at once.
  4. Verify the control is actually working, not just configured: from inside each segment, attempt a connection to an unapproved external destination and confirm it's blocked, and check the firewall logs to confirm the attempt was logged as denied, not silently dropped with no record.
  5. Review the exception list on a set schedule and remove any allowed destination that no longer has a current business or mission need, which is the same ongoing-review requirement NIST's SC-7 control calls for.

The Pushback You'll Hear

"This is going to break things we don't even know depend on outbound access." The senior rebuttal: that risk is real, which is exactly why step one is mapping real traffic before changing any rule, and why rollout happens zone by zone with logging turned on first. A short monitor-only period - logging what would be denied without actually blocking it yet - surfaces those hidden dependencies safely before the rule goes live. The alternative, leaving outbound traffic wide open indefinitely because an unknown dependency might exist somewhere, guarantees that the day a breach happens, the attacker's exit door is standing wide open too.

Senior Talk Tracks

Why SELinux Contexts Break Copied Files

Here's a moment almost every Linux admin hits at least once: you copy a config file to a new location, the permissions look completely fine, and the service still refuses to read it. Nine times out of ten on a Red Hat system, that's not a permissions problem at all — it's SELinux, and today I want you to actually understand why.

SELinux stands for Security-Enhanced Linux, and it's a second layer of access control sitting on top of the regular Linux permissions you already know — the read, write, and execute bits owned by a user and a group. Here's the part that trips people up: every single file on an SELinux-enabled system also carries an invisible label called a security context, and it's that label — not the file's owner or its permission bits — that decides whether a given process is actually allowed to touch it.

So here's why copying breaks things. When you copy a file into a new directory, Linux generally gives that new file the SELinux context that's "correct" for wherever it landed — often inherited from the parent directory. But when you move a file instead of copying it, the file keeps its original context from wherever it used to live. That's the trap: moving a web server's config file into the right directory can leave it carrying the wrong label, even though the regular permissions look completely correct, and the regular owner and group look completely correct too.

Here's the senior take. A junior engineer sees "permission denied," checks ls -l, sees the right owner and the right mode bits, and gets stuck — because they're only looking at one of the two access-control systems actually running. A senior engineer immediately also runs a command to check the SELinux context itself, and treats a mismatched label as just as likely a cause as a wrong permission bit, especially right after a file got copied or moved from somewhere else.

Think of it like a building that has a keycard lock on every door, in addition to the regular physical lock. Your key might fit the physical lock perfectly, but if your keycard is coded for the wrong floor, the door still won't open — and if you only ever check whether your key fits, you'll stand there confused, convinced the lock must be broken.

So here's a good line to use at work the next time someone says "the permissions are definitely right, I don't get it": "Permissions aren't the only lock on that door — have we actually checked the SELinux context?"

Key Takeaways

  1. SELinux is a second, independent access-control layer on top of normal Linux permissions, and it can deny access even when the regular owner, group, and mode bits all look correct.
  2. Copying a file into a new location usually gives it the destination's SELinux context; moving a file can carry its old context along instead, which is a common, confusing source of "permission denied" errors after a file relocation.
  3. Disabling SELinux entirely to fix one mislabeled file removes a whole security layer system-wide — the targeted fix is relabeling the file, not turning the system off.
