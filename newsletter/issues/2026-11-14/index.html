Current Events

The Leaky Vessels runc Container Breakout

If you've ever told a teammate "it's in a container, so it's isolated," this one's for you. In January 2024, researchers at Snyk found four separate bugs in the software that actually starts and runs containers -- not a misconfigured app sitting inside one, the plumbing underneath every container on the host. They called the group "Leaky Vessels." Here's how the worst of the four actually works.

runc is the low-level tool that does the real work of creating a container -- Docker, Kubernetes, and most other container platforms all call down into it. According to Snyk's own advisory and Red Hat's security bulletin, CVE-2024-21626 is an order-of-operations bug: during container startup, runc briefly leaks an open file descriptor pointing at the host filesystem into the new container's working directory, before it's supposed to be sealed off. If an attacker controls the image being built or run -- a malicious Dockerfile, or a crafted WORKDIR instruction -- they can use that leaked file descriptor to break out of the container and get command execution on the host itself, as root.

Root cause, in one sentence: a brief timing gap between when runc opens a reference to the host and when it actually isolates the container let a malicious image reach straight through the isolation boundary it was supposed to never touch.

What makes this one worth knowing cold for an interview isn't just the CVE -- it's the blast radius. runc sits underneath Docker Engine, containerd, and Kubernetes alike, so this wasn't a Docker bug or a Kubernetes bug, it was a container-runtime bug that showed up everywhere at once. Snyk and the maintainers coordinated disclosure and shipped runc 1.1.12 the same day the advisory went public, and Red Hat, Docker, and the major cloud providers pushed their own patched builds alongside it.

So here's what a senior engineer takes from this. First, patching "Docker" isn't the same as patching every layer underneath it -- Kubernetes nodes, CI runners, and build servers all embed their own copy of runc, and each one needs its own update. Second, don't build images from untrusted Dockerfiles on a host you actually trust; treat an image build step itself as code execution, because this bug proves it can be. On a Podman or Kubernetes lab, that's concrete: check your installed runc version against 1.1.12 before you assume a patched Docker Engine means a patched container runtime underneath it.

What Held

  • Coordinated, same-day disclosure and patch. Snyk worked with the runc maintainers before going public, so a fixed version (1.1.12) was available the moment the advisory and the CVE went live — defenders never faced a public zero-day window with no fix to apply.
  • The research was proactive, not incident-driven. Leaky Vessels was found through deliberate security research into container-runtime internals, not discovered because someone was already exploiting it in the wild — meaning organizations got to patch ahead of active abuse rather than in response to it.
  • Defense-in-depth at the orchestration layer. On systems running containers with reduced privileges, read-only root filesystems, or without build-time access to untrusted Dockerfiles, the practical exploitation path was narrower even before patching — a reminder that "don't build untrusted images on a trusted host" is a real control, not just advice.

Senior Security Advice

Stop Tailgating Through Badge-Access Doors

The Advice

Never let a single valid badge swipe open a secure door for more than one person: pair every high-sensitivity entry point with a physical control that enforces it, and train staff to challenge anyone who follows them in without badging themselves.

Why It Matters

A badge reader only proves that one valid credential touched the door; it says nothing about how many people walked through behind it. Tailgating, letting someone in on your badge swipe out of politeness, habit, or pressure, turns every other physical control in the building into theater. Once an unauthorized person is inside, they can plug into an open network jack, walk out with a laptop, photograph a whiteboard, or plant a rogue device, all without ever touching an access log that shows their name. This is the incident class security assessors and real intruders both rely on: physical penetration testers have walked into data centers, server rooms, and even classified-adjacent facilities by simply following an employee through a propped or badge-held door, dressed to blend in and carrying something that makes holding the door look natural. No malware, no phishing email, just a held door.

How to Implement It

  1. Install access control vestibules, mantraps, or turnstiles at entry points protecting your most sensitive spaces (data centers, server rooms, SCIFs), so the door physically cannot admit a second person on one badge.
  2. Where vestibules aren't feasible, write and train a "challenge culture" policy: every employee is expected to stop and question anyone in a secure area who didn't badge in, with management backing them up even when it's awkward.
  3. Turn on anti-passback on your access control system so a badge that already opened a door can't be used again until it logs an exit, which surfaces shared or cloned credentials.
  4. Require visitors to be escorted and logged for the duration of their visit, not just signed in at the front desk.
  5. Verify the control is actually working, don't just trust that it's enforced: run unannounced physical social-engineering tests (internal team or a contracted red team) that specifically attempt tailgating, and track how many attempts succeed per quarter. Audit access logs for anti-passback violations and badge-in counts that don't match headcount.

The Pushback You'll Hear

"We're not a bank vault, we don't need mantraps, and challenging a coworker feels rude." The rebuttal: you don't need a vestibule on every door, only the ones protecting your crown jewels, and the cheapest fix here isn't hardware, it's culture. A senior engineer makes challenging a stranger the socially acceptable default, not the awkward exception, because the alternative is an unlogged person standing next to your core switch.

Tech News

A security researcher dropped working exploit code for a zero-day on LinkedIn Thursday, and attackers had it weaponized within hours — against servers that were already patched. If you manage remote-monitoring tools for client networks, or you're running a firewall from one of the biggest names in the business, tonight's two stories are for you. First, the remote-management platform that got hit right after its own emergency fix. Second, a firewall flaw that turns a low-level account into root.

Start with N-able N-central. It's remote monitoring and management software — the kind of tool managed service providers use to reach into hundreds of client networks from one console, which is exactly why a flaw in it matters so much. According to SecurityWeek and The Hacker News, independent researcher Sean Bales published proof-of-concept code on November 12th for an exploit chain he called "4EverAble2Shell," showing how an unauthenticated attacker could run commands as root on an on-premises N-central server — and it still worked against servers running the hotfix N-able had shipped just two days earlier. Huntress and multiple outlets reported attackers using that code within hours to install cryptocurrency miners on dozens of affected systems, some of them already on the newest build. N-able's response was to disable the Legacy API mode the exploit depends on and pull back certain integrations. My take: "patched" isn't a status you check once and file away. When a vendor ships a hotfix under pressure, you verify the specific attack path is actually closed, not just that a new version number is installed.

Next up — sticking with root access, but on hardware a lot of networks sit behind every day. Check Point disclosed CVE-2026-123039 this week, a flaw in Gaia OS, the operating system running its firewalls and security management servers. Here's the chain: attackers first used a separate flaw nicknamed "PHP2Shell" to reach the Mobile Access portal, then pivoted to this new bug — a root-level process called dynamic_server that listens on a socket without checking who's asking — to escalate straight to root. Check Point says it's seen active exploitation against roughly two dozen customers since late October. My read: a single CVE rarely tells the whole story. This was a two-step chain, and the lesson for a senior engineer is to always ask what a vulnerability connects to, not just what it does by itself.

So here's tonight's through-line: a patch closes the vulnerability you know about — it's your job to confirm it closes the path attackers are actually using.
