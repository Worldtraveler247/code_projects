Current Events

The XZ Utils Backdoor

Imagine a single volunteer, working patiently for over two years to earn the trust of an open-source project, so that one day he could quietly slip a backdoor into a piece of software installed on practically every Linux server on Earth -- and the only thing that stopped him was one engineer noticing his own laptop felt fifty milliseconds slower than it should. That's not a hypothetical. That's the XZ Utils backdoor, and it's one of the closest calls in the history of open-source software. Here's how it actually happened.

XZ Utils is a compression library -- it shrinks files -- and it's so widely used that it's quietly baked into almost every major Linux distribution. According to the oss-security mailing list post that broke this open, a contributor using the name "Jia Tan" started submitting code to the project back in 2021. Over roughly two years, through patient, legitimate-looking contributions, and -- according to independent analysis of the project's mailing list -- some help from other accounts pressuring the original, overworked maintainer to hand over control, "Jia Tan" became XZ Utils's primary maintainer. Nobody voted on that. It just happened gradually, the way trust in open source usually does.

Then, in February and March of 2024, that access got used. Versions 5.6.0 and 5.6.1 of XZ Utils shipped with malicious code hidden inside them. Here's the clever part: the backdoor was never visible in the project's public source-code repository at all. It only existed inside the official release tarballs -- the pre-packaged download files most Linux distributions actually build from instead of the raw repository. Hidden test files, combined with obfuscated build scripts, quietly patched the compiled library during the build process itself. Once installed, that tampered library could hook into OpenSSH's login process on affected systems and give a remote attacker holding the right private key a hidden way to run commands as that system's own user -- no valid password required.

Root cause, in one sentence: a project with enormous reach had, in practice, a single burned-out volunteer maintainer, and a patient attacker spent two years turning that single point of trust into a single point of failure.

Here's what held, and it's the detail worth remembering cold. A Microsoft engineer and PostgreSQL contributor named Andres Freund noticed that SSH logins on a Debian testing system were using more CPU than they should and taking about half a second longer than normal. Out of simple curiosity, he investigated -- and found the backdoor. Reporting differs on exactly how close this came to wider exposure, but it's well established that the backdoor had only reached rolling and testing branches of a handful of distributions, never a stable release of Debian, Ubuntu, or Red Hat Enterprise Linux. Catching it there, before it reached long-term-support distributions, is the whole reason this is a famous near miss and not a famous breach.

So what does that mean for you? A senior engineer treats "who maintains this dependency, and how many of them are there" as an actual supply-chain question, not a footnote -- because this incident proves that a healthy-looking project with thousands of users can still be, underneath, one tired person away from being taken over.

What Held

  • Rolling-release exposure limited the blast radius. The backdoor only reached testing and unstable branches — Debian Sid, Fedora Rawhide-adjacent builds, and similar — because that's where bleeding-edge package versions land first. It never reached a stable release of Debian, Ubuntu LTS, or Red Hat Enterprise Linux, which is the entire reason this is remembered as a near miss.
  • One engineer's manual curiosity, backed by a transparent ecosystem. Freund's discovery wasn't the product of an automated control — it was a person noticing something felt wrong and being able to dig into open, inspectable source and build logs to prove it. Naming that distinction — a lucky catch, not a designed one — is the senior move, rather than claiming the system worked as intended.

Senior Security Advice

Keep Offline, Immutable Backups and Prove You Can Restore From Them

The Advice

Keep at least one backup copy offline or immutable and logically separate from your production credentials, and schedule a real restore test on a calendar — a backup nobody has restored from is just an unverified hope.

Why It Matters

A backup's entire job is to survive the day production doesn't. If every backup lives on the same network, behind the same domain admin credentials, as the systems it's protecting, it isn't a separate safety net — it's just another folder the attacker can reach. This is the exact failure mode behind modern ransomware: the intrusion isn't "encrypt some files," it's "get domain admin, find the backup server, and encrypt or delete the backups first," so the victim has no option but to pay. CISA's #StopRansomware Guide, built with the FBI and NSA, calls out maintaining offline, encrypted backups as a core prevention measure for exactly this reason. NIST SP 800-53's CP-9 control goes further than "have a backup" — it requires protecting the confidentiality and integrity of that backup data, and its CP-9(3) enhancement calls for storing critical backup copies in a separate facility from the operational system. None of that matters if nobody ever tries to restore from it; CP-10, System Recovery and Reconstitution, exists because a backup that silently stopped working six months ago is discovered at the worst possible time — mid-incident, under pressure, with no fallback left.

How to Implement It

  1. Map what's actually being backed up against what the business can't lose — user data, system state, configuration, and security-relevant documentation all count, not just the obvious file shares.
  2. Put at least one copy somewhere a compromised domain admin account can't touch: offline media, a separate cloud account with its own credentials, or an immutable/object-lock storage tier that can't be altered or deleted within its retention window.
  3. Protect the backups themselves — encrypt at rest, and limit who holds the credentials or keys that can delete or overwrite them. The backup's access list should be shorter than production's, not the same list.
  4. Schedule restore tests on a calendar, not "whenever someone remembers" — restore a real system or dataset to a clean environment and confirm the business can actually run on what came back.
  5. Verify the control, don't just trust the green checkmark: confirm the backup job is restoring the data it claims to, time how long a full restore actually takes against your recovery time objective, and check that the credentials protecting the backup are genuinely distinct from the ones an attacker would steal first.

The Pushback You'll Hear

"We already have nightly backups running, this is solved." Running jobs and recoverable data are not the same thing. A backup job can report success for months while quietly backing up corrupted files, or sit reachable by the same compromised admin account as production — and you won't find out until the moment you need it most. The fix isn't more backup jobs, it's proof: an isolated copy and a restore that was actually timed and verified.

Tech News

Citrix just patched a flaw that scores 9.5 out of 10 in its NetScaler boxes — the same product line that's had exploited zero-days twice already this year. If your organization runs NetScaler for remote access or single sign-on, tonight's lead story is yours. Two stories: that Citrix patch, and attackers already breaking into backup servers through a flaw the vendor hasn't actually fixed yet.

Start with Citrix. According to Citrix's own security bulletin, CTX697191, published October 8th, the company disclosed CVE-2026-107406: a critical memory-overflow flaw in NetScaler ADC and NetScaler Gateway that can let an unauthenticated attacker run arbitrary code or crash the appliance outright. It hits any instance configured as a SAML service provider or identity provider — a common setup for single sign-on. Citrix says it has no evidence of exploitation yet. Here's why that's thin comfort: this is the third NetScaler flaw disclosed in roughly six weeks, after two other zero-days, tracked as CVE-2026-88771 and CVE-2026-88772, were already being exploited before patches even existed back in September. My read: when a vendor's authentication appliance has that kind of track record, you don't wait for "actively exploited" to show up in the next bulletin. You check today whether SAML is even enabled on boxes that don't need it, and you patch on the vendor's clock, not your change board's.

Next up, backup servers. According to Huntress's own incident research, attackers started chaining two flaws in Ahsay's cloud backup software, AhsayCBS, on October 7th — an authentication bypass, CVE-2026-105133, paired with a command-injection bug in its replication component, CVE-2026-105134, which scores 9.3. Chain them together and an attacker walks in with no valid login and runs their own commands. Huntress had already confirmed five organizations hit within a day, with attackers dropping webshells and a cryptocurrency miner disguised as Microsoft Edge. Here's the part that should bother you most: Ahsay's own advisory says the issue is fixed in version 10.3.4. Huntress tested 10.3.4 and found it's still vulnerable. There is no real patch available right now — only Huntress's advice to lock down the management interface and go hunting for compromise. My take: backup infrastructure is the one system you're counting on to recover from everything else that goes wrong, which makes an unauthenticated path into it one of the worst possible places for an unpatched flaw to sit.

Same thread both stories tonight: the system protecting your identity and the system protecting your data both deserve a second look at exactly who can reach them right now.
