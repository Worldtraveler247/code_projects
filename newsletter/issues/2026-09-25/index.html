Current Events

The EchoLeak Zero-Click Prompt Injection in Microsoft 365 Copilot

In June 2025, researchers showed that Microsoft 365 Copilot could be robbed of your data by a single email you never even opened. No click, no attachment, no link. Here's how it actually happened.

Researchers at Aim Security found a flaw they named EchoLeak. An attacker sends a normal-looking email to a target inside an organization running Copilot. Buried in that email is a set of instructions written in plain English, worded to look like it's addressed to the human reader, not to an AI. Later, when that same person asks Copilot an unrelated question, Copilot's retrieval system pulls in relevant context to answer -- and that poisoned email gets swept in along with everything else. Copilot can't tell the difference between an instruction from its actual user and an instruction hiding inside a document it just retrieved. It follows the hidden instruction, gathers sensitive data the user already had access to, and sends it out through a rendering trick that quietly reaches out to an attacker-controlled server. No click required anywhere in the chain.

Root cause, in one sentence: Copilot's retrieval pipeline let untrusted, attacker-controlled content sit in the exact same instruction channel as trusted commands from the actual user, with nothing enforcing a hard line between the two.

Microsoft did have a defense in place -- a classifier built specifically to catch prompt injection attempts. The researchers defeated it by writing the hidden instructions so they never mentioned an AI or Copilot at all, phrasing everything as if it were meant for the human recipient. That's the part worth sitting with: the control existed, and it was still routed around by careful wording alone.

Here's what held. Aim Security reported this privately and gave Microsoft time to fix it before anything went public. Microsoft shipped a server-side fix, confirmed no evidence of exploitation in the wild, and didn't need a single customer to take any action -- because the fix lived in the service itself, not in something every tenant had to go patch individually.

Here's what a senior engineer, or a senior ISSO, would change in how they work. Any system that feeds retrieved, external content into an AI model's instruction context needs a real trust boundary between "data to read" and "commands to follow" -- not just a classifier hoping to catch bad phrasing. In a lab with a local model and a simple retrieval script, that means feeding it a document with a hidden instruction, watching it get followed anyway, and then fixing it by separating retrieved content from the instruction channel entirely -- because that gap is the whole incident.

Control Failures

# Failure NIST SP 800-53 Rev 5 family
1 Retrieved, untrusted external content (the email) was ingested into the same instruction channel Copilot used for trusted user commands, with no enforced separation between "data" and "instructions." AC-4 — Information Flow Enforcement
2 The Cross-Prompt Injection Attack (XPIA) classifier meant to detect and block injected instructions was bypassed by phrasing the payload as if addressed to a human, not an AI. SI-10 — Information Input Validation
3 The exfiltration path let data leave the tenant boundary via an automatically rendered reference to an external server, without a network-layer check on the destination. SC-7 — Boundary Protection
4 The Copilot session operated with the full scope of data the signed-in user could already access, so a single successful injection could reach anything in that scope. AC-6 — Least Privilege
5 The flaw required an external security research team, not internal detection, to first surface the exploitable chain. SI-4 — System Monitoring

What Held

  • Aim Security's coordinated disclosure gave Microsoft a real head start. The researchers reported privately and held public details until a fix was live, which is exactly why Microsoft could say there was no evidence of in-the-wild exploitation.
  • Microsoft fixed the platform, not the tenant. Because the remediation lived server-side, every existing customer got the fix automatically — no patch cycle, no per-tenant configuration change required.
  • A layered defense existed, even though it was bypassed. The XPIA classifier being defeated is a real gap, but its presence — and Microsoft's own account of the fix — shows defense-in-depth thinking was already part of the design, which is a different failure than having no control at all.

Senior Security Advice

Enforce Application Allowlisting on Critical Systems

The Advice

Put your critical servers and endpoints on application allowlisting so only explicitly approved software can execute, and route every exception through change management instead of a quiet one-off click.

Why It Matters

Antivirus and endpoint detection tools mostly work by recognizing something bad. Allowlisting flips that logic: nothing runs unless it's already on the approved list, known-bad or not. That matters because a lot of real intrusions don't use custom malware at all — they use a legitimate admin tool, a renamed executable, or a scripting engine that's already sitting on the box. Signature-based tools can miss that entirely, especially when the file is packed, encrypted, or just never seen before. Ransomware operators count on being able to drop and run a payload once they've landed. On a host where only approved binaries execute, that payload never gets the chance, no matter how new or well-disguised it is. That's exactly why CISA's own ransomware prevention guidance names application allowlisting, alongside EDR, as a baseline control for every asset.

How to Implement It

  1. Start with your highest-value systems first — domain controllers, build and CI servers, systems handling sensitive data — using an OS-native tool (Windows Defender Application Control or AppLocker, Linux fapolicyd or SELinux) or a dedicated allowlisting product.
  2. Build the baseline from a clean, known-good image, then run in audit/log-only mode before enforcing. Review what actually tries to run for a real business cycle (patch days, month-end jobs, backup windows) so you're not blind-blocking legitimate software.
  3. Flip from audit to enforce/deny once the baseline is stable, and require a change ticket with an approver and a reason for every new binary added afterward — no ad hoc additions.
  4. Extend beyond raw executables to scripts and libraries over time. Once .exe files are locked down, attackers pivot to PowerShell, DLL side-loading, and living-off-the-land binaries, so a policy that only covers one layer gets bypassed.
  5. Verify it's actually enforcing, not just enabled: push an unauthorized test binary to an allowlisted host and confirm it's blocked and the block is logged and alerted on. A policy that's "on" but silently fails open is worse than no policy, because it gives you false confidence.

The Pushback You'll Hear

"This is going to break things and flood the help desk with tickets." The senior-engineer rebuttal: that's what the audit-mode period is for. Running in log-only mode first surfaces the real software inventory on a system before anything gets blocked, so enforcement day isn't a surprise. Once the baseline is right, a mature allowlist mostly runs itself, and it stops the one class of attack — running an unapproved payload — that a lot of other controls simply aren't designed to catch.

Senior Talk Tracks

The Shared Responsibility Line in Practice

Here's a sentence that sounds simple and gets people in real trouble: "AWS is responsible for security." No. AWS is responsible for security OF the cloud. You're responsible for security IN the cloud. That one preposition is the whole ballgame.

Let's make it plain. AWS's job is the stuff you can't see and usually can't touch: the physical data centers, the hardware, the hypervisor, the global network. They patch that. They guard that. That's "security of the cloud." Everything you configure on top of it -- who can access your S3 buckets, whether your database is publicly reachable, whether your servers are patched, how you set up your permissions -- that's "security in the cloud," and it's on you, completely, regardless of how good AWS's side is.

Here's why that matters in production, and the senior take: most cloud breaches people blame on "the cloud" are actually a customer misconfiguration sitting entirely on their side of that line. AWS didn't leave an S3 bucket public -- somebody's IAM policy or bucket setting did. A junior engineer hears "AWS security" and pictures one big shared fortress. A senior engineer knows the fortress has a property line running straight through the middle of it, and their entire job lives on one specific side of that line.

Think of it like renting an apartment. The building's foundation, the fire escapes, the locks on the main entrance -- that's the landlord's job, the "of the building" part. But if you leave your own apartment door unlocked, the landlord's rock-solid foundation doesn't save you. Nobody blames "the building" for that break-in.

A good way to open this at work: "Before we assume AWS is handling that, let's check -- is this actually on our side of the shared responsibility line?"

Key Takeaways

  1. The shared responsibility model splits cloud security into "security of the cloud," which the provider owns, and "security in the cloud," which the customer owns — and the exact line moves depending on the service.
  2. The large majority of publicized cloud security incidents trace back to customer-side misconfiguration, not a failure in the provider's own infrastructure.
  3. Using a more managed service, like a managed database instead of a self-run one on a virtual machine, shifts more of the line toward the provider, but it never erases the customer's side of it entirely.

Reader Question

"If the shared responsibility line moves depending on the service, how would you figure out exactly where it falls for a specific AWS service you'd never used before?"

I'd start with AWS's own documentation for that specific service, because the shared responsibility line isn't uniform — it shifts based on how much AWS manages versus how much the customer configures, and a fully managed service like a serverless database pushes more responsibility toward AWS than a self-managed virtual machine does. My answer would be that I never assume the line based on another service I've used before; I verify it service by service, because assuming it stayed the same as the last service is exactly the kind of gap that leads to an unpatched or misconfigured resource nobody thought was theirs to fix.

Tech News

A single flaw in the way the Linux kernel cleans up old socket connections just handed researchers root access on the host — from inside a completely default, unprivileged Docker container, no special settings required. If you run anything in containers, this is the story to know today. Two stories: a Linux container-escape exploit with no patch yet on the most common Ubuntu releases, and a technique that lets an attacker silently hijack the exact cloud storage bucket your logs or backups are pointed at.

Start with the container escape. Security firm DepthFirst published working exploit code on September 22nd for a flaw now tracked as CVE-2026-80521 — a use-after-free bug in how the Linux kernel garbage-collects AF_UNIX sockets, the connections programs use to pass file descriptors to each other. The bug lets a process inside a plain, unprivileged container — no extra capabilities, no relaxed security settings — walk out to root on the host itself. The fix already exists upstream and landed back in early August, but Ubuntu hasn't shipped it yet for its 22.04, 24.04, or 26.04 releases, including the kernel packages a lot of teams run on AWS, Azure, and Google Cloud. Here's the takeaway: a container boundary is a kernel feature, not a wall — a senior engineer treats every unpatched kernel CVE as a potential escape route, not just a local annoyance, and patches the host kernel instead of trusting the container alone to hold.

Next up, a cloud storage trick that doesn't even need a vulnerability. Researchers at Unit 42 detailed a technique called bucket namespace hijacking: because bucket names have to be globally unique across an entire cloud provider, an attacker who can delete your storage bucket — or simply waits for one you retire — can immediately register a bucket with that exact same name under their own account. Anything still pointed at that name — a logging pipeline, a backup job, a data-transfer sink — quietly starts shipping data straight to the attacker, and no IAM alert fires, because as far as the cloud provider is concerned, a bucket by that name legitimately exists again. My take: this only works because most teams treat a bucket name like a fixed address instead of a resource someone else can claim the moment it's released — worth auditing what your pipelines still point at, on AWS, Azure, and Google Cloud alike.

Both stories point at the same blind spot: the trust boundary you assume is there — a container wall, a storage name — is exactly what needs to be verified, not assumed.
