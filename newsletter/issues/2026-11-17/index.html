Current Events

The Capital One Cloud Breach

A hundred and six million people. One misconfigured firewall. Zero exotic exploits. That's the Capital One breach, and if you work with AWS, this is the single incident you need to be able to explain cold. Here's how it actually happened.

Capital One ran a web application firewall in front of one of its AWS-hosted applications. According to the Treasury Department's Office of the Comptroller of the Currency, which later fined the bank over this, that firewall was misconfigured, and it also carried far more permission than it needed. A former Amazon Web Services employee named Paige Thompson found a server-side request forgery flaw in it -- a bug that lets an attacker trick a server into making requests on its own behalf. She used that flaw to make the firewall ask Amazon's instance metadata service for its temporary security credentials. At the time, that service -- now called IMDS version one -- handed those credentials to any process that asked, no extra proof required. Because the firewall's role was over-permissioned, those stolen credentials could list and read far more than that one application's own data. They reached into more than 700 storage buckets. Court records say she pulled the personal information of roughly 106 million people, along with about 140,000 Social Security numbers.

Root cause, in one sentence: one overly broad permission, attached to one vulnerable service, met a metadata endpoint that handed over the keys to anyone who asked.

Here's the part that should bother you more than the hack itself. Capital One didn't find this on its own. According to the Justice Department, the data sat exposed for about four months until an outside tipster emailed the company's own responsible-disclosure address, flagging what looked like leaked data on a public GitHub page. Capital One confirmed it within two days and called the FBI. Thompson was arrested in July 2019, convicted by a jury in June 2022, and sentenced to time served and five years of probation that October. The OCC fined Capital One 80 million dollars, and the bank separately agreed to a 190 million dollar class-action settlement.

So what should a senior engineer take from this? Least privilege isn't a checkbox -- it's the only thing standing between "one component has a bug" and "one component has a bug, so now everything in the account is exposed." A senior engineer auditing a cloud environment wouldn't just confirm a service is patched. They'd ask what that service's IAM role can actually reach, and whether a single compromised component could pivot sideways into data it was never supposed to touch.

That's Capital One: one misconfigured firewall, one over-permissioned role, and a hundred million people's data walked out the door.

What Held

  • The responsible-disclosure channel worked. Capital One had a public email address for exactly this kind of report, and an anonymous tipster used it — without that channel, there's no indication the company would have found the exposure on its own.
  • Confirmation and law-enforcement handoff were fast once flagged. Capital One verified the intrusion within two days of the tip and brought in the FBI immediately, which is the reason Thompson was identified and arrested within about two weeks of the tip reaching the company.
  • No evidence of further sale or distribution. The Department of Justice stated it found no indication Thompson sold or disseminated the stolen data beyond her own possession, which limited the breach's downstream fraud impact relative to its sheer size.

Senior Security Advice

Enable Secret Scanning with Push Protection on Every Repository

The Advice

Turn on secret scanning with push protection on every code repository so a leaked API key, password, or token is blocked before it ever reaches the remote, instead of being discovered after the fact.

Why It Matters

A hardcoded credential in a repository is not a style problem, it is a live key sitting in plain text. Once a secret is pushed, anyone with read access to that repository, including automated scanners run by outside parties against public code, can find it and use it immediately. The damage is not theoretical: a cloud access key or database password committed to source control gives an attacker the same access a legitimate service would have, often with no further exploitation needed. This is the well-documented incident class behind many cloud account takeovers: a developer commits a working credential, usually by accident, and it is abused long before anyone notices it in a code review. Deleting the commit afterward does not help, because the secret was exposed the moment it left a developer's machine, and git history keeps a copy regardless.

How to Implement It

  1. Enable secret scanning org-wide, not repository by repository, and set policy so individual repository admins cannot turn it off.
  2. Turn on push protection specifically, which checks for secrets at push time and rejects the push, rather than only scanning after the fact and raising an alert on something that is already exposed.
  3. Add custom detection patterns for your organization's internal token and API key formats, since built-in patterns only cover well-known providers.
  4. Verify the control is actually working, don't just trust the toggle: push a documented test secret in a scratch branch and confirm the push is rejected, then confirm a real alert fires if someone uses the logged bypass path.
  5. Treat every alert as a live incident, not cleanup: rotate or revoke the credential immediately. A secret that touched a remote repository, even briefly, must be treated as compromised, never just removed from the file.

The Pushback You'll Hear

"This will slow the team down with blocked pushes." The senior response: a legitimate push is never permanently stuck, since push protection lets someone bypass it with a logged reason, and that bypass itself creates an auditable alert for review. The friction is the point. It is far cheaper to have a developer pause for ten seconds and justify a bypass than to rotate a production database password after it sat in a public repository for a week.

Senior Talk Tracks

Why Rollback Beats Hotfix

It's two in the morning, production is broken, and someone on the call says "I can push a quick fix." That sentence is where a lot of outages turn into two outages instead of one. Here's the senior instinct: when something is actively on fire, you roll back first and you debug second, almost every time.

Plain English first. A hotfix means writing new code, right now, under pressure, to patch whatever just broke, and shipping it straight to production. A rollback means undoing that step — going back to the last version that you already know worked, the one that was running fine an hour ago. Both get you out of the incident. Only one of them is safe to do while your hands are shaking and the dashboards are red.

Here's why it matters in production. A hotfix is new code you have never run in production before, written under the worst possible conditions for careful thinking, during the one moment you have the least margin for a second mistake. A rollback is just running code you already trust. So the senior take is this: a junior engineer sees rollback as giving up, like you failed to fix the real problem. A senior engineer sees rollback as stopping the bleeding so the room can calm down enough to find the real problem safely, with time, tests, and without an audience of angry customers.

Think of it like a kitchen fire. If a pan catches fire, you don't stop to figure out the perfect recipe fix mid-blaze — you pull the pan off the heat first. You can absolutely improve the recipe later, once nothing is burning. Cooking under fire and debugging under outage pressure produce the same kind of mistake: a change nobody fully thought through, made worse by adrenaline.

So here's a natural way to bring this up at work: "Before we write a fix, is there a version we can just roll back to first?"

Key Takeaways

  1. A rollback returns you to a version that already proved itself in production; a hotfix asks brand-new code to work correctly on its very first run, under the worst conditions for careful thinking.
  2. Treating rollback as the default first move during an incident is what keeps one outage from turning into two.
  3. Rollback isn't abandoning the real fix — it buys the time and calm needed to diagnose and fix the root cause properly, outside the pressure of a live incident.

Reader Question

Question a senior engineer might ask: "If rollback is so much safer, why do teams still reach for a hotfix during an incident?"

Tech News

It's open-source software that's been running quietly on servers for decades — and this week its own maintainers said attackers are actively exploiting the worst bug the project has seen in fifteen years. Two stories tonight, and both come down to the same question: who do you actually trust to run commands on your systems? First, a chat-server bug that lets a regular user act like an administrator. Second, a cloud breach that shows what happens when you trust a vendor's vendor a little too much.

Start with UnrealIRCd — open-source server software that still powers a lot of internet relay chat networks, the kind of software that's been quietly running on Linux boxes for decades. According to the project's own security disclosure and corroborated by Red Hat's bug tracker, the flaw — tracked as CVE-2026-114713 — sits in how the server handles a message tag called a "label." The server fails to properly escape that tag before echoing it back, and that's a classic command injection bug: user-supplied input gets treated as a command instead of plain data. An ordinary, unprivileged user can exploit it to run privileged operator commands — kicking users, banning entire networks — without ever having admin rights. CISA confirmed active exploitation and added it to the Known Exploited Vulnerabilities catalog on November 13th. The fix landed in version 6.2.7.1. My take: this is a fifteen-year-old codebase getting hit by one of the oldest bug classes there is. Age and maturity don't inoculate software against a missed escape character — they just mean more systems are exposed when someone finally finds it.

Next up — turning from a server bug to a trust problem in the cloud. Security firm Wiz published research showing an attacker got hold of AWS credentials belonging to Qubole, a big-data platform, and used them to assume IAM roles inside more than a dozen customer AWS accounts. Here's the mechanic: when a customer connects Qubole to their AWS environment, they create a role that trusts Qubole's account to assume it. Wiz found that many of those roles were years old and no longer even in active use — but the trust relationship never expired, so the stolen credentials still worked. The attacker pulled customer secrets, access keys, and environment variables straight out of those accounts. My read: a trust policy you set up once and never revisit isn't a control anymore, it's a liability sitting quietly in your account. A senior engineer treats cross-account trust the same way they treat an open port — reviewed on a schedule, scoped tight, and deleted the moment it's not in active use.

So here's tonight's through-line: whether it's a chat server or an AWS account, the systems that get hit hardest are the ones where somebody trusted an input, or a role, and then stopped checking.
