Current Events

Azurescape: The Cross-Tenant Container Escape in Azure Container Instances

In September 2021, security researchers proved something no one had publicly demonstrated before on a major public cloud: that a customer running a completely ordinary container could break out and reach other customers' workloads on the very same platform. Here's how it actually happened.

Researchers at Unit 42, Palo Alto Networks' threat intelligence arm, were testing Azure Container Instances -- Microsoft's pay-as-you-go service for spinning up containers without managing any servers yourself. They found the platform was still running a container runtime called runc, version 1.0.0-release-candidate-2 -- already two years out of date, and vulnerable to a previously disclosed flaw, CVE-2019-5736. That bug let a container escape its own boundary and get code execution as root on the host machine underneath it. From there, the researchers found something worse waiting on that host: a live, privileged Kubernetes service-account token. With it, they could reach the Kubernetes API server controlling the entire multi-tenant cluster -- the same cluster running containers that belonged to other Azure customers, not just them.

Root cause, in one sentence: a known, two-year-old vulnerability was left unpatched in a shared, multi-tenant runtime, and the blast radius of exploiting it wasn't one customer's container -- it was every customer sharing that cluster.

Here's what happened next, and it's the part worth knowing cold. The researchers reported the flaw to the Microsoft Security Response Center under coordinated disclosure, and Microsoft moved fast -- patched by the end of August 2021, before any public detail went out. Microsoft's own investigation found no evidence any other customer's data was actually accessed. Out of caution, Microsoft still notified every customer who'd had a container running on the same clusters the researchers had touched, through Azure's own Service Health Notifications, and recommended they rotate any privileged credential deployed before August 31st -- treating possible exposure as real even without proof anyone else had exploited it.

Here's what a senior engineer, or a senior ISSO, would change in how they work. A multi-tenant platform's promise -- that your container is isolated from every other customer's -- is only as strong as the oldest unpatched component underneath it. In a lab with Podman on RHEL 9, that means picking one shared-runtime component, checking its version against the latest known CVE for it, and proving to yourself what an unpatched flaw in that layer would actually expose -- because "it's just a container" was never the real boundary; the host underneath it always was.

Control Failures

# Failure NIST SP 800-53 Rev 5 Control Family
1 Azure Container Instances ran a roughly two-year-outdated version of runc with a known, already-disclosed vulnerability (CVE-2019-5736) still exploitable in production. SI-2 — Flaw Remediation
2 Once a container escaped to host root, a live, privileged Kubernetes service-account token was reachable from that same host, handing the attacker a path to the cluster's control plane. AC-6 — Least Privilege
3 No boundary stopped a single host-level compromise from reaching the Kubernetes API server governing every other customer's containers sharing that multi-tenant cluster. SC-7 — Boundary Protection
4 The outdated runtime version and the escalation path were found by an external research team, not by Microsoft's own internal detection or inventory processes. SI-4 — System Monitoring

What Held

  • Coordinated disclosure worked as designed. Unit 42 reported privately, and Microsoft had a fix live before any exploit detail became public — no malicious actor is known to have used this chain.
  • Microsoft's own investigation found no unauthorized access to customer data. The theoretical blast radius was severe, but containment held in practice.
  • Microsoft treated "no evidence of misuse" as different from "no possible exposure." Even without proof of harm, it proactively notified every customer who'd shared a cluster with the researchers and recommended credential rotation — the more conservative and correct posture.

Senior Security Advice

Run Incident Response Tabletop Exercises Before You Need Them

The Advice

Run a full incident response tabletop exercise at least twice a year, walking your actual team through a realistic breach scenario before a real one forces everyone to improvise.

Why It Matters

An incident response plan that has never been rehearsed is a hypothesis, not a capability. Most organizations have a written plan sitting in a shared drive, but the first time anyone actually acts it out is during a live breach, under pressure, with customers or regulators already asking questions. That is when the plan's gaps surface: nobody has legal's after-hours number, no one is sure who can authorize taking a system offline, and the person who was supposed to draft the customer notification is on vacation. In real incidents, the technical containment is often fine; what costs organizations the most time is confusion over decision authority, escalation paths, and who talks to whom. A tabletop exercise finds those gaps on a Tuesday afternoon with coffee instead of during an actual breach at 2 a.m. NIST's incident response guidance and CISA's own exercise programs both treat this kind of rehearsal as a core preparation activity, not an optional add-on.

How to Implement It

  1. Schedule at least two tabletop exercises a year, built around scenarios that match your actual risk profile (ransomware, cloud credential compromise, insider data exfiltration). CISA's free Tabletop Exercise Packages (CTEPs) provide ready-made, customizable scenarios and discussion questions you can adapt instead of writing one from scratch.
  2. Pull in people beyond IT and security: legal, communications, an executive who can actually authorize decisions, and whoever owns customer or regulator notification. Real incidents touch all of them, so the exercise should too.
  3. Run it as a facilitated, discussion-based walkthrough with a timeline of injects, forcing each participant to say out loud what they would do and who they would call. This is where you find the gaps: unclear on-call escalation, no owner for the press statement, no defined threshold for "notify customers."
  4. Produce an After-Action Report every time listing the specific gaps found, with an owner and a date attached to each fix, and update the written IR plan accordingly.
  5. Verify the control is actually working, not just performed: in the next exercise, deliberately reuse a gap flagged in the prior After-Action Report and confirm it is now closed. If the same gap resurfaces, the "fix" was paperwork, not a real change.

The Pushback You'll Hear

"We already have an incident response plan, we don't need to rehearse it." The senior-engineer rebuttal: a plan nobody has acted out is untested code. You don't know it works until you run it. A tabletop exercise is the cheapest possible way to find out that the escalation contact list is stale or that no one actually has authority to pull a server offline, before that gap costs you hours during a real breach.

Senior Talk Tracks

Least Privilege as a Process, Not a Setting

Here's a phrase you'll hear in every security interview: "least privilege." Most people treat it like a setting you configure once. It's not. It's a process you have to keep running, or it quietly stops being true.

Let's make it plain. Least privilege means giving a person or a system only the access it actually needs to do its job -- nothing more. Sounds simple. The problem is what happens after day one. Someone joins a project, gets access to a database. Three months later they roll off that project. Does anyone remove the access? Usually not. Multiply that by every employee, every system account, every integration, over years, and you get what security people call permission creep -- access nobody's using, that nobody remembers granting, sitting there as pure risk with zero upside.

Here's why that matters in production, and the senior take: a junior engineer treats least privilege as something you get right at setup -- configure the IAM policy correctly once, move on. A senior engineer treats it as a recurring process: who has access, do they still need it, and can we prove that on demand. Because every one of those forgotten permissions is a door an attacker doesn't need to pick a lock for -- it's already unlocked, just nobody's checking it anymore.

Think of it like handing out keys to a building. On day one, it's easy to make sure only the right people get the right keys. But if you never collect a key back when someone changes departments or leaves the company, five years later half the keys in circulation belong to people who don't even work there. The lock was never broken. Nobody ever checked who still had a copy.

A good way to open this at work: "Before we grant this, do we have a process for reviewing and removing it later -- or are we about to create another permission nobody's going to remember in a year?"

Key Takeaways

  1. Least privilege is a process of granting and then actively removing access, not a one-time configuration step — the removal half is where most organizations fail.
  2. Permission creep is the accumulation of unused, forgotten access over time, and it's dangerous precisely because it's invisible until an attacker finds it first.
  3. A senior engineer treats "can we prove who has access to this, right now" as a standing requirement, not a question you scramble to answer during an audit.

Reader Question

"If least privilege is supposed to be a process, how would you actually catch permission creep before an audit forces you to?"

I'd build a recurring access review into the calendar, not just wait for an audit to trigger one — quarterly for most systems, tighter for anything sensitive — where I'm pulling a report of who has access to what and confirming it against who actually still needs it for their current role. My answer would be that the review has to be owned by someone specific with a recurring reminder, because "we'll get to it eventually" is exactly how permission creep accumulates in the first place; the process only works if removing access is as routine as granting it.

Tech News

A ransomware crew doesn't need to steal your source code to hold your software supply chain hostage — they just need an unpatched build server they can reach over the network, and CISA says that's happening right now to one of the most widely used CI/CD platforms on the internet. Two stories today: a critical flaw in JetBrains TeamCity now confirmed in active ransomware attacks, and a $351 million cryptocurrency heist that never touched a single private key.

Start with TeamCity. The Cybersecurity and Infrastructure Security Agency warned this week that ransomware groups are actively exploiting CVE-2026-63077, a critical authentication-bypass flaw in TeamCity On-Premises that lets an attacker with nothing more than network access run arbitrary operating-system commands on the server. JetBrains patched it back on July 25th, and CISA added it to its Known Exploited Vulnerabilities catalog in early August — but researchers say more than 160 internet-facing TeamCity servers are still running the vulnerable version today. Here's why that matters more than a typical unpatched web server: TeamCity is a continuous-integration and continuous-delivery pipeline, the automated system that builds and ships your code. Compromise it, and an attacker isn't just on one box — they can tamper with stored credentials, configurations, and the build artifacts feeding every downstream deployment. My take: a two-month-old patch for a maximum-severity flaw sitting unapplied on a system with pipeline-wide trust is exactly the kind of gap a senior engineer flags in a risk review before it becomes someone else's incident report.

Next up, the Bitget hack. The cryptocurrency exchange confirmed Thursday that attackers made off with $351.6 million, and the mechanism is the interesting part: investigators say the private keys protecting the wallets never left the vault. Instead, someone compromised the backend system that tells Bitget's wallets what to sign — spoofing transfer instructions and triggering the exchange's own authorization workflow to move the funds out the front door. Bitget says preliminary evidence, including IP addresses tied to infrastructure used before, points toward North Korea's Lazarus Group. My read: this is a reminder that the strongest cryptography in the world doesn't help you if the system deciding what gets signed is the thing that gets popped — access control on that decision layer matters just as much as the keys themselves.

Both stories land on the same principle: patch what's reachable from the internet, and audit not just who holds your keys, but what's allowed to tell them what to sign.
