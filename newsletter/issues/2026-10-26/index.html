Current Events

Microsoft Midnight Blizzard Corporate Email Breach

A Russian state-sponsored hacking group got into Microsoft's own corporate email system - not through a zero-day, not through some exotic exploit, but by guessing passwords against a test account nobody had bothered to retire. From there, they read the inboxes of Microsoft's own senior leadership and security team for weeks. Here's how it actually happened.

Microsoft's own account, published by its Security Response Center, says the group it tracks as Midnight Blizzard - also known as Nobelium, and linked by the US government to Russia's foreign intelligence service - used a technique called password spraying. That means trying a small number of common passwords across a large number of accounts, rather than hammering one account repeatedly. They aimed it at a legacy, non-production test tenant account. One that was never meant to hold real access to anything that mattered.

Here's the chain, step by step. The attackers got into that low-value test account in late November 2023. But that account had been granted an OAuth application role - a permission called "full access as app" inside Exchange Online, Microsoft's own hosted email service. Security researchers who later analyzed the incident describe the attackers using that foothold to create new malicious applications and grant them the same sweeping mailbox-access permission, then using those applications to read corporate email accounts, including Microsoft's own senior leadership and staff in its cybersecurity and legal teams. Microsoft detected the intrusion on January 12th, 2024, and disclosed it publicly a week later.

Root cause, in one sentence: a forgotten test account, with a leftover permission far more powerful than its purpose ever required, became the hinge that swung open access to real corporate email.

What actually limited the damage, and this is the senior-level detail worth naming: Microsoft said at the time it found no evidence the attackers reached customer-facing production systems. The blast radius stayed inside Microsoft's corporate environment - serious, but bounded. A March update complicated that picture, when Microsoft disclosed the same attackers had gone on to use information stolen from that corporate email to reach some of its source code repositories and internal systems too. So containment was real, but it was not the end of the story.

So what does that mean for the kind of system a senior engineer is responsible for? A senior engineer treats every test or non-production account as a real attack surface, not an exception, and audits exactly what permissions legacy accounts and legacy OAuth applications were ever granted - because this breach shows that kind of leftover access is worth more to an attacker than any password. On a RHEL, AWS, or Kubernetes lab, that means an engineer would regularly enumerate every service account, IAM role, and OAuth application grant across an environment and flag anything with privileges wider than its stated purpose, instead of assuming an account is harmless just because it is old or unused.

What Held

  • Segmentation between corporate and customer-facing production environments. Microsoft stated it found no evidence the attackers reached Microsoft-hosted customer-facing systems during the initial corporate-email phase of the intrusion — the boundary between corporate IT and production customer infrastructure did its job even while the corporate side was thoroughly compromised.
  • Eventual detection and public disclosure. Microsoft did detect the activity, moved to disclose it within about a week, and continued updating the public record in March as its investigation uncovered more — including the less flattering source-code finding. A senior engineer credits that transparency honestly, while also naming that detection still took roughly six weeks.
  • Scoped damage despite a powerful foothold. Even with an Exchange Online-wide mailbox-access permission in hand, the publicly described impact stayed within corporate email and, later, certain source repositories — not a full enterprise-wide compromise of Microsoft's entire production estate, as far as has been publicly disclosed.

Senior Security Advice

Enforce IMDSv2 on Every EC2 Instance

The Advice

Require IMDSv2 on every EC2 instance, account-wide, so no workload can ever fall back to the unauthenticated version of the instance metadata service.

Why It Matters

Every EC2 instance can reach a local, unauthenticated-by-default endpoint that hands back its temporary IAM credentials. In the original version of this service (IMDSv1), any request an attacker can trick the box into making on its own behalf gets those credentials with nothing more than a plain GET. That trick is server-side request forgery, or SSRF: a vulnerable web app or proxy is coerced into fetching an internal URL, and if that URL is the metadata endpoint, the attacker walks away with the instance's IAM credentials without touching a password. A well-known breach class works exactly this way — an SSRF flaw in a misconfigured application reached the metadata service and pulled credentials that led to a large-scale cloud data exposure. IMDSv2 closes that door: it requires a PUT request to fetch a session token before any metadata can be read, and SSRF bugs can almost never send a PUT. AWS's own EC2 documentation confirms that once an instance requires tokens, IMDSv1-style credential retrieval is no longer available at all.

How to Implement It

  1. Set the account-level default so every newly launched instance requires IMDSv2 automatically, instead of relying on each team to configure it.
  2. Audit existing instances with aws ec2 describe-instances, checking each MetadataOptions.HttpTokens value — anything other than required is still exposed to IMDSv1.
  3. Remediate with aws ec2 modify-instance-metadata-options --http-tokens required --http-endpoint enabled, and bake the setting into launch templates and Infrastructure-as-Code so it can't drift back.
  4. Set a sane hop limit — AWS flags a hop limit of 1 as a known problem for containerized workloads behind a proxy — so you don't break legitimate calls while locking down tokens.
  5. Verify it's actually enforced, not just configured: try an IMDSv1-style GET against the endpoint and confirm it's rejected, and track it continuously with the CIS AWS Foundations Benchmark control that audits IMDSv2 account-wide.

The Pushback You'll Hear

"We have legacy agents that only speak IMDSv1 — this will break production." The senior-engineer rebuttal: that's a reason to inventory and upgrade those specific agents, not a reason to leave every instance exposed. Most modern SDKs already speak IMDSv2 by default. Roll the change out class by class, starting with anything internet-facing or taking untrusted input — exactly the workloads an SSRF bug would target — and fix the stragglers instead of leaving the fleet on a mode designed to be phased out.

Tech News

If you run a self-hosted Plex media server on a Linux box, or a self-managed GitLab instance at work, both of tonight's stories are about you. Attackers are already using one of them to mine cryptocurrency on other people's hardware. Two stories: a federal patch deadline tied to real in-the-wild attacks, and a software vendor that's had to patch the exact same class of maximum-severity bug twice in nine days.

Start with Plex. According to CISA's own Known Exploited Vulnerabilities catalog, hackers are chaining four flaws in Plex Media Server — nicknamed Plex2Shell — to get unauthenticated remote code execution on self-hosted servers. BleepingComputer and The Hacker News both report that researchers first spotted in-the-wild exploitation around October 17th, with attackers planting cryptocurrency miners and proxy malware on compromised boxes. CISA added the flaws to its catalog on October 20th and ordered federal agencies to patch three of the four by October 23rd — that deadline has already passed — with the rest due November 3rd. The fix itself has existed since early August. My read: when a patch sits unapplied for two and a half months, the gap stops being a technology problem and becomes an asset-inventory problem. You can't patch a server you don't know you're running, and a self-hosted media server is exactly the kind of box that falls outside most organizations' formal patch cycle.

Next up, turning from one patch gap to a vendor that keeps finding the same hole twice. GitLab has now shipped fixes for two separate maximum-severity flaws — both rated a perfect ten out of ten, both unauthenticated remote code execution, both sitting inside the same regular-expression compiler — in the span of nine days. Per GitLab's own advisories, corroborated by Help Net Security and Canada's Cyber Centre, the first fix landed October 12th as CVE-2026-97229; the second, CVE-2026-110264, followed October 21st. Here's the detail worth knowing cold: if you patched after the first advisory and stopped there, you are still exposed. The second flaw lives in the same component and was not closed by the October 12th update. My take: finding two bugs that fast in one subsystem usually means someone went back and audited the whole component after the first one turned up — that's good vendor follow-through. But it also means "I already patched this" is a sentence worth double-checking against the actual CVE ID, not just the component name.

Tonight's thread: a patch that exists and a patch that's actually running on your systems are two different facts, whether the gap is two months wide or nine days.
