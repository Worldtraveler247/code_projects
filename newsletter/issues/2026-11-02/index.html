Current Events

The Cloudflare November 2025 Outage

A single database permissions change at one company briefly took a meaningful slice of the internet offline -- not because anyone attacked it, but because of what that change did to a file nobody was watching closely enough. Here's how one config file turned into a global outage, and what the company actually did about it afterward.

On November 18th, 2025, Cloudflare -- a company that sits in front of a massive share of the web, handling traffic so sites load faster and survive attacks -- went down hard for several hours. According to Cloudflare's own incident report, the trigger was almost absurdly small: an engineering team made a permissions change to one of the company's internal database systems, called ClickHouse, meant to make data access more explicit and secure. That change had a side effect nobody caught before it shipped -- a routine query that builds a configuration file for Cloudflare's bot-detection system started returning duplicate rows, which more than doubled the size of that file.

Here's the chain. That bot-management configuration file gets regenerated and pushed out across Cloudflare's entire global network every few minutes. The oversized file blew past a hard-coded limit of two hundred entries built into the core proxy software -- a limit that was never meant to be approached, let alone exceeded. The proxy's own code, written in Rust, hit that oversized file and triggered an unhandled error, a panic, which crashed the service outright. Because the bad file wasn't generated on every single cycle, the proxy would crash, recover when a good file came through, and then crash again minutes later when the bad one regenerated -- which is part of why Cloudflare's own engineers initially suspected they were looking at a massive attack rather than an internal mistake.

Root cause, in one sentence: an internal permissions change altered a database query's behavior in a way nobody tested against the hard limit a downstream system depended on, and that downstream system had no graceful way to fail once the limit was breached.

What actually held: Cloudflare's own team correctly ruled out an attack, traced the fault to the bot-management file specifically, stopped the automatic deployment pipeline that kept pushing the bad file out, and rolled back to a last-known-good version -- the fix that actually ended the outage. The company was also transparent fast, publishing a detailed root-cause writeup with exact timestamps within about a day, rather than leaving customers guessing.

So what does this mean for a senior engineer's own environment? A senior engineer treats any auto-regenerated configuration file the same way they'd treat untrusted input -- validated before it ships, with a hard limit that fails safely instead of panicking, and a kill switch that can disable a feature globally without a full redeployment. On a RHEL or Podman lab, that means practicing exactly that: writing a config consumer that checks a size or schema limit before loading a file, instead of trusting that upstream will never produce something malformed.

What Held

  • Correct, fast triage ruled out an attack. Cloudflare's team traced the intermittent crash pattern to the Bot Management file specifically rather than chasing an attack theory past the point it was useful.
  • Stopping the pipeline before fully understanding it bought time. Halting automatic configuration deployment at 14:24 prevented the bad file from continuing to propagate while the root cause was still being confirmed.
  • Rollback to last-known-good is what actually ended the outage. Not a code fix, not a redesign — reverting to a configuration that was already known to work.
  • Fast, detailed public disclosure. Publishing a timestamped root-cause writeup within about a day gave customers and the industry a real postmortem to learn from instead of a vague statement.

Senior Security Advice

Block Legacy Authentication Protocols That Bypass MFA

The Advice

Block every legacy authentication protocol — POP, IMAP, SMTP AUTH, and older basic-auth sign-ins — at the identity layer, because these protocols cannot carry multi-factor authentication and quietly undo every MFA policy you think you've enforced.

Why It Matters

Rolling out MFA feels like the job is done, but most identity platforms still let older mail and legacy sign-in protocols authenticate with just a username and password, since those protocols were built before MFA existed and have no way to prompt for a second factor. An attacker who steals or guesses a password can skip the MFA prompt entirely just by connecting through one of these old protocols instead of the normal sign-in page.

This is exactly the gap behind password-spray and credential-stuffing campaigns: attackers try a stolen or common password against thousands of accounts, and because the login arrives over a legacy protocol, no MFA challenge ever fires. Microsoft's own Conditional Access documentation states that more than 97% of credential-stuffing attacks use legacy authentication, and CISA issued government-wide guidance directing agencies to retire Basic Authentication in Exchange Online specifically because it does not support MFA. Without this control, "we enforced MFA everywhere" is often false — it just feels true.

How to Implement It

  1. Pull sign-in logs filtered to legacy or basic-auth client types to see which accounts and applications are still using these protocols before touching anything.
  2. Build the blocking policy in report-only (audit) mode first, so you can see exactly who would be blocked without locking anyone out.
  3. Exclude one break-glass emergency account from the policy before enforcing it, so a misconfiguration can't lock out every admin at once.
  4. Switch the policy from report-only to enforced, blocking legacy protocols tenant-wide (or via security defaults if no Conditional Access license is available).
  5. Verify it's actually working: attempt a legacy-protocol sign-in with a test account after enforcement and confirm it's denied, then re-check the sign-in logs a week later to confirm legacy attempts are being blocked, not just logged.

The Pushback You'll Hear

"Some old scripts and devices only support basic auth — we'll break something." The rebuttal: that's exactly why step 1 and step 2 exist. You find those exceptions in the logs before enforcing, migrate them to modern authentication or app passwords scoped to that one use case, and then enforce. Leaving legacy auth open for everyone because one printer scanner needs it is trading a known, exploited attack path for the convenience of a device that can be reconfigured in an afternoon.

Tech News

If you've ever trusted that little padlock icon in your browser without thinking twice, tonight's lead story is exactly why that deserves a second look. A certificate authority just got caught issuing trust from keys that were never properly random in the first place — and fixing it meant emergency surgery on a programming language a huge share of cloud software is built in. Two stories tonight: a certificate authority's weak keys forcing Google, Microsoft, and the Go language itself into emergency action, and an Android flaw that let a zero-permission app quietly steal Microsoft work-account logins.

Start with the certificate authority. According to The Hacker News and Mozilla's own bug tracker, corroborated by Dark Reading, a researcher reported on October 17th that eight intermediate certificate authorities operated by the firm eMudhra were generated with insufficient randomness, the result of what the company itself calls a flawed key ceremony from last year. Chrome and Microsoft both moved within days to stop trusting the affected roots outright. Then Go — the programming language behind a huge share of cloud infrastructure tooling — shipped emergency releases, 1.27.3 and 1.26.10, that reject any certificate chain running through those eight keys, with no setting to turn it off. eMudhra's board has since decided to exit the SSL and TLS certificate business entirely. Here's my read: patching the language isn't the same as fixing the problem — only software actually rebuilt with the new release picks up that protection, so anything still running on a pinned older toolchain, including plenty of containers and CI pipelines, stays exposed until someone goes back and rebuilds it.

Next up, turning to mobile identity. According to Microsoft's own advisory, corroborated by The Hacker News, researchers disclosed CVE-2026-80097, a flaw in the Android version of Microsoft Authenticator that let an app requesting zero permissions impersonate a Teams sign-in prompt and capture a user's work-account token. Microsoft rates it 8.6 and fixed it in Authenticator version 6.2606.4246; it hasn't been seen exploited in the wild, but it does require the victim to actually complete a sign-in step inside the fake prompt. My take: "requests no permissions" tells you nothing about what an app can still talk a user into handing over voluntarily — on any fleet of personal devices touching corporate identity, that's exactly the gap policy has to assume exists.

Tonight's thread: in both stories, the vulnerability wasn't really the headline bug — it was how much of the internet had to actually act before the fix meant anything.
