Current Events

The Okta Support System Breach

A password manager noticed something strange on its own Okta account in late September 2023. That single tip eventually unraveled a breach that let an attacker read customer support files at one of the identity companies half the internet relies on to log its employees in. This is the Okta support-system breach, and it's the case study for why a vendor's "side" systems deserve the same scrutiny as its main product.

Here's what Okta actually is. It's an identity provider — the company behind the login screen a huge number of other companies use so their employees can sign into dozens of internal tools with one account. In October 2023, Okta disclosed that someone had used a stolen credential to get into its support case management system — a separate system from Okta's actual production identity service, built so customers could upload diagnostic files when they needed help troubleshooting.

Here's the chain, step by step. First, an Okta employee had saved the credentials for a sensitive service account into their own personal Google account, on a company laptop, outside any system Okta actually sanctioned for storing secrets. Second, that personal account was compromised, and the attacker used those stolen service-account credentials to get into the support system itself. Third, the attacker spent time viewing the diagnostic files customers had uploaded for support tickets — and some of those were HAR files, HTTP Archive files, which can capture an entire web session including live session tokens if nobody strips them out first. Fourth, the attacker used some of those still-valid session tokens to actually hijack active sessions at a handful of downstream customers, including BeyondTrust and Cloudflare, who separately noticed the suspicious activity and pushed Okta to investigate further.

Root cause, in one sentence: an employee's credentials ended up somewhere Okta never intended them to be stored, and a diagnostic file format that can carry live session tokens was accepted into a support system without anyone requiring those tokens to be stripped out first.

What held: Okta's actual production identity service — the system that was doing the real authentication work for its customers — was never touched. The support case system was a separate, segmented environment, and that segmentation is exactly what kept this from becoming a breach of Okta's core product. Once Okta confirmed the intrusion, it revoked the exposed tokens, which is the only reason the number of customers who actually had sessions hijacked stayed in the single digits instead of matching the much larger number whose files were simply viewed.

My read: this incident isn't really about Okta being careless — it's about how easily "just a diagnostic file" turns into a live credential if nobody treats it like one. A senior engineer auditing any vendor-support workflow asks a specific question: what happens to the sensitive data customers upload to get help, and is anyone actually stripping tokens and credentials out of it before it's stored anywhere.

What Held

Okta's actual production identity service — the multi-tenant system doing the real authentication work for every customer — was segmented from the support case management system and was never touched, which is the single biggest reason this stayed a contained incident rather than a platform-wide compromise. Once Okta confirmed the breach, it revoked the exposed session tokens, directly limiting how many customers actually had sessions hijacked versus simply having files viewed. Downstream customers' own monitoring — specifically 1Password's and BeyondTrust's detection of anomalous activity on their own Okta tenants — is also worth naming explicitly: customer-side detection caught this before Okta's own internal investigation did, which is a defense-in-depth point worth making in an interview, not just a footnote.

Senior Security Advice

Deploy Endpoint Detection and Response on Every Endpoint

The Advice

Deploy a centrally monitored Endpoint Detection and Response (EDR) agent on every endpoint - every server, laptop, and workstation - and route its alerts to a team that actually watches them.

Why It Matters

Signature-based antivirus only catches malware it has already seen before; it matches a known fingerprint. Modern attackers increasingly skip custom malware altogether and instead abuse tools already on the box - legitimate admin utilities, scripting engines, remote access software - a technique called living-off-the-land that a signature scanner has nothing to match against. EDR closes that gap by watching behavior instead of signatures: unusual process chains, credential dumping attempts, and lateral movement get flagged in real time, and a responder can isolate the host over the network before the attacker finishes the job. Without EDR coverage, a compromise looks like silence - no alert fires while the attacker explores the network, and the first sign of trouble is often the ransomware note itself. Ransomware is exactly the incident class this defends against: encryption at scale requires time and access, and EDR is built to interrupt that window before it's too late. The federal government treats this as baseline infrastructure, not an optional upgrade - Executive Order 14028 and the OMB memo implementing it directed civilian agencies to deploy EDR as a core part of federal network defense.

How to Implement It

  1. Inventory every endpoint - servers, laptops, workstations, and any remote or BYOD devices in scope - and confirm the agent is actually installed on all of them. A gap in coverage is the first thing an attacker finds.
  2. Push the agent through existing configuration management or device management tooling so it is enforced at provisioning, not something a user can skip or uninstall.
  3. Route every alert to a monitored queue with a defined on-call response - a SOC, an MSSP, or an internal rotation - never a dashboard nobody is watching.
  4. Verify the control is actually working, not just installed: run a safe, known detection test (a MITRE ATT&CK-based emulation or a vendor-provided test file) and confirm the alert fires, reaches the response queue, and someone acts on it.
  5. Exercise the isolation and containment feature specifically - confirm a responder can remotely isolate a compromised host within your target response time, because that capability is the main thing EDR offers over plain antivirus.

The Pushback You'll Hear

"We already run antivirus, isn't that enough?" The senior rebuttal: antivirus matches known signatures, which structurally cannot catch an attacker using tools already trusted on the system. EDR watches behavior and gives responders a remote isolate-and-contain capability that antivirus never had. On the cost objection, weigh EDR licensing against the cost of undetected dwell time - the incident response, downtime, and recovery cost of a ransomware event that nothing caught in time dwarfs the price of the agent.

Senior Talk Tracks

Why Pods Share a Network Namespace

Here's a Kubernetes fact that trips up almost everyone the first time they hear it: every container inside the same pod shares one IP address. Not similar addresses — the exact same one. Today I want to explain why that's not an accident, it's the entire point of what a pod actually is.

Let's start with what a pod really is, underneath the term. A pod isn't a container — it's a wrapper around one or more containers that are meant to run as a single unit. And the way Kubernetes makes them act like a single unit on the network is by putting them all inside one shared network namespace, which is the Linux mechanism that gives a process its own private view of network interfaces, IP addresses, and ports.

So here's why that sharing actually happens. When a pod starts, Kubernetes quietly creates one tiny infrastructure container first — usually called the pause container — and that container's only job is to own the network namespace. Every other container in that pod then joins that same namespace instead of getting its own. The practical effect: every container in the pod sees the same IP address, and they can reach each other over plain localhost, the same way two programs on your own laptop can talk to each other without going over any real network at all.

Here's the senior take. A junior engineer treats a pod like "basically a container, but Kubernetes's version of one." A senior engineer knows a pod is really a shared network identity with one or more containers hanging off it — and that distinction is exactly why sidecar containers work at all. A logging sidecar, a service-mesh proxy, a metrics exporter — none of that pattern makes any sense unless every container in the pod already shares one network identity to begin with.

Think of it like a shared apartment with one mailing address. Different roommates can have different jobs, different schedules, completely different lives — but mail addressed to that apartment reaches all of them, because they all live behind the same front door. That's a pod: one network address, potentially several processes living behind it, each doing its own job.

So here's a good way to open this one at work: "Remember, containers in the same pod aren't just co-located — they're sharing a network identity. That's the whole reason the sidecar pattern even works."

Key Takeaways

  1. Every container in a Kubernetes pod shares one network namespace, which means they all share one IP address and can reach each other over localhost.
  2. Kubernetes achieves this by creating a hidden infrastructure container, usually called the pause container, whose only job is to own and hold open that shared network namespace.
  3. The sidecar pattern — a logging agent, a service-mesh proxy, running alongside your main application — only works because every container in the pod already shares that one network identity.

Tech News

Four flaws, one government deadline, and a detail that should worry anyone running an AI tool in production: attackers are already exploiting a vulnerability in the open-source gateway that routes traffic to large language models. Here's what you need to know. Two stories today: a federal patch deadline that landed today, spanning everything from a home-office NAS box to an AI gateway, and a quick update on yesterday's AWS trust-relationship breach.

Let's start with the deadline. According to CISA, the agency added four actively exploited vulnerabilities to its Known Exploited Vulnerabilities catalog on November 18th, and federal civilian agencies had until today, November 21st, to fix three of them. The highest-profile one is in LiteLLM — an open-source gateway that sits between an application and the large language model it calls, the kind of component more and more companies are quietly bolting onto their stack as they add AI features. CISA also flagged a flaw in Apache Axis, a SOAP framework so old it's already reached end of life, with no vendor patch coming at all, only a community fix. Round that out with a Synology NAS flaw already tied to ransomware, and a Vanderbilt REDCap bug attackers are using to install cryptominers, and you've got one advisory touching four completely different layers of the stack. Here's my read: the Apache Axis entry is the one worth sitting with. When software is end of life, "patch it" isn't an option on the table — a senior engineer's real choice is migrate it, isolate it, or accept the risk formally, in writing, because "we'll get to it" isn't a real answer for a flaw with a public exploit and no vendor fix behind it.

Which brings us to an update. Yesterday I told you about the Qubole breach — attackers who spent two weeks inside Qubole's AWS account, then rode a trusted cross-account role into its customers' environments. Here's what's new: according to Risky Business, an actor using the handle "non" has claimed responsibility, though investigators haven't confirmed that attribution yet. My take: attribution matters less operationally than the fact that it's still unconfirmed — don't let a name in a headline convince you the investigation is closed.

So here's the through-line: one story is about what you do when a vulnerable system literally cannot be patched, and the other is a reminder that a claimed name isn't the same thing as a confirmed one.
