Current Events

The Ivanti Connect Secure Zero-Day Chain

In January 2024, two chained flaws in one of the most common corporate VPN appliances gave a state-linked espionage group unauthenticated remote command execution -- and by the time it went public, hundreds of organizations had already had months of head start against them. Here's how it actually happened.

Ivanti Connect Secure is an SSL VPN appliance -- the box that sits on the edge of a corporate network and decides who gets in. According to Mandiant's own investigation, a China-nexus threat actor it tracks as UNC5221 began exploiting two vulnerabilities in these appliances as a zero-day starting December 3rd, 2023 -- more than five weeks before Ivanti, Volexity, and CISA jointly disclosed anything in public.

Here's the chain. The first flaw, CVE-2023-46805, is an authentication bypass -- it let an attacker skip the login screen entirely. The second, CVE-2024-21887, is a command injection flaw reachable only once you're past that login screen. Chained together, an unauthenticated attacker on the open internet could run arbitrary commands as root on the appliance itself -- no credentials, no phishing, no user interaction. Volexity had identified well over seventeen hundred compromised appliances carrying a webshell it named GIFTEDVISITOR within days of disclosure.

Here's the root cause in one sentence: two vulnerabilities in the code running on an internet-facing edge appliance combined to erase the authentication boundary that appliance existed to enforce, and no patch existed for either one when exploitation began.

The part that makes this a genuinely senior-level case is what came next. Ivanti's own device shipped with a built-in Integrity Checker Tool meant to detect tampering. Mandiant found the attackers actively defeating it -- disabling the scanner script with a single commented-out line, and tampering with the manifest file it checked against. The tool meant to catch the intrusion was running on the same compromised box the intrusion controlled.

Here's what held. Volexity's own detection work is what surfaced this at all. CISA issued Emergency Directive 24-01 on January 19th, ordering every federal civilian agency to mitigate immediately, then followed up ordering appliances disconnected within 48 hours if they weren't fully patched. And once Ivanti's internal integrity tool was shown to be tamperable, Ivanti shipped a separate external version -- one that doesn't run from inside the box an attacker might already own.

Here's what a senior engineer, or a senior ISSO, would change in how they work because of this. Any integrity or file-monitoring baseline that lives on the same host it's protecting has to be treated as untrustworthy the moment that host might be compromised -- which is exactly why a senior engineer keeps the verification baseline external, on read-only or offline storage the production host can't write back to. In a RHEL and Podman lab, that means standing up AIDE with its database stored outside the monitored host, not inside it, and proving a local root compromise still can't erase the evidence.

What Held

  • Volexity's own detection work surfaced the zero-day at all. Incident-response findings at a customer environment are what led to coordinated disclosure with Ivanti and CISA, rather than the exploitation continuing silently.
  • CISA's Emergency Directive forced fast, mandatory action. ED 24-01, issued January 19, gave every federal civilian agency a hard deadline to mitigate, hunt, and report — and the follow-up supplemental direction forced disconnection of unpatched appliances within 48 hours rather than leaving it to agency discretion.
  • Ivanti shipped an out-of-band verification path once the internal one was shown to be untrustworthy. An external Integrity Checker Tool, run from outside the potentially compromised appliance, is a direct, concrete response to the specific way the internal tool was defeated.
  • Public, detailed threat-intel sharing (Mandiant's "Cutting Edge" series) let the broader defender community detect this, not just Ivanti's own customers — naming specific webshells, file paths, and log event IDs that any organization could hunt for immediately.

Senior Security Advice

Least Privilege via AWS IAM Permission Boundaries

The Advice

Give every IAM user, role, and service account only the permissions it needs to do its job today, and enforce that ceiling with a permission boundary so no one can grant themselves more tomorrow.

Why It Matters

Cloud breaches rarely start with a stolen root credential. They start with one over-permissioned role — a CI/CD pipeline, a Lambda function, a junior engineer's account — that has far more access than its actual job requires. Once an attacker (or a mistaken script) gets that credential, the blast radius is whatever that identity can touch, not just what it was supposed to touch. The incident class this prevents is privilege escalation after initial access: a compromised low-value account pivots into admin-level control because nothing stopped it from creating a new role, attaching a broader policy, or reaching into unrelated resources. Least privilege doesn't stop the initial foothold, but it caps the damage once someone gets in, which is exactly why NIST's access control guidance treats it as a baseline requirement, not an optional hardening step.

How to Implement It

  1. Start every new role or user at zero permissions and add only what's needed, rather than starting broad and trying to trim later — trimming after the fact rarely happens.
  2. Attach a permission boundary to any role that's allowed to create other IAM entities, so even a misconfigured or malicious policy that role writes can never exceed the boundary's ceiling.
  3. Run AWS IAM Access Analyzer against production roles to generate right-sized policies from actual CloudTrail activity, instead of guessing what a role needs.
  4. Verify the control is working, not just present: pull the last-accessed data for each role's attached policies and confirm unused permissions are actually being flagged and removed, not just visible in a report nobody reads.
  5. Put access reviews on a calendar — quarterly at minimum — and revoke anything that can't be justified against a current business need, since permissions granted for a project that ended six months ago are still live risk today.

The Pushback You'll Hear

"We don't have time to scope permissions this tightly — it'll slow the team down." The senior-engineer rebuttal: broad permissions don't save time, they defer cost to incident response. A scoped policy takes an extra hour to write; an over-permissioned role that gets compromised takes days to contain and explain. Tools like IAM Access Analyzer also remove most of the manual guesswork, so the "it's too slow" objection mostly describes doing it the hard way.

Senior Talk Tracks

Agent Tool-Use Is the New Attack Surface

There's a new kind of AI deployment showing up in production right now, and it changes the security conversation in a way most teams haven't caught up to yet: AI agents that don't just answer questions, they take actions. Today's topic is why giving an agent tools to use is really giving it a security boundary to defend.

Plain English first. A basic chatbot reads text and writes text back -- worst case, it says something wrong. An agent is different: it's connected to tools -- it can call an API, run a database query, read or write files, kick off a deployment. The moment you wire up those tools, the agent isn't just talking anymore, it's acting, using whatever permissions you handed it to do the acting.

Here's why that matters in production. Say you build a support agent and give it a tool to look up a customer's account. To avoid managing a pile of separate permission scopes, someone wires that tool to a service account with broad database access -- read and write, across every customer, not just the one ticket in front of it. The agent behaves fine in testing. Then a crafted input from an untrusted user gets it to call that same tool in a way nobody intended -- and now the blast radius isn't "the chatbot said something embarrassing," it's "the chatbot touched data it should never have reached."

The senior take, the part most teams miss early on: the risk was never really about how smart the model is or how well it resists a bad prompt. It's about the permissions sitting behind the tool call. A model confused for one turn is a nuisance. A model confused while holding admin-level database access is an incident. So the real question isn't "can we stop the agent from being tricked" -- you can't fully guarantee that -- it's "if it is tricked, what's the worst it's actually able to do."

Think of it like handing an enthusiastic new intern a master key to the whole building instead of just the one door they need, because cutting individual keys felt like extra work. The intern's judgment isn't the failure point -- the master key is.

A good way to raise this at work: "before we wire this agent up to that tool, what's the actual blast radius if it calls it the wrong way?"

Key Takeaways

  1. Every tool connected to an AI agent should be scoped to the narrowest permission that task actually needs, because that scope becomes the agent's real attack surface.
  2. You can reduce how often an agent gets tricked, but you can't guarantee it never will, so the permissions behind its tools have to assume it eventually will.
  3. Agent security is less about model intelligence and more about blast-radius engineering -- bounding the damage a confused or manipulated action can cause.

Reader Question

"If prompt injection can't be fully solved, why bother building any input-side defenses at all?"

Because input-side defenses and permission scoping aren't competing solutions, they're two different layers, and neither one has to be perfect on its own. Even an imperfect filter that blocks most injection attempts buys real value, as long as the permissions behind the tool assume it will occasionally fail -- that way a rare successful injection becomes a contained mistake instead of a full-blown incident. I'd rather have a decent input filter plus tight permissions than a perfect filter plus no permission boundary at all, because only one of those failure modes is survivable.

Tech News

A Russian military hacking group spent months walking through the front door of Cisco's flagship firewall management platform, using a bug Cisco has now patched for the third time this year. If your firewalls are managed from that console, the system meant to protect your network was the way in. Also today: a maximum-severity GitLab flaw that lets an attacker with zero credentials pull your CI/CD secrets in one request, and an Adobe Commerce zero-day that hit stores before a patch existed. Here's what you need to know.

First, Cisco. CVE-2026-20079 is an authentication bypass in Secure Firewall Management Center's web interface. CISA — the Cybersecurity and Infrastructure Security Agency — added it to its exploited-vulnerabilities catalog with a September 12th federal deadline. Cisco Talos says multiple threat-actor clusters are exploiting it, including Russia's GRU-linked Sandworm group, which chained it with a second bug to deploy Cyclops Blink malware — FMC's third active-exploitation entry this year. This isn't a flaw in the traffic path; it's in the management plane, the layer that configures the firewall. Compromise that, and an attacker doesn't breach your network — they redraw the map. A senior engineer's first move: confirm that interface was never internet-facing, then hunt for Cyclops Blink indicators if it was.

Next up, GitLab. CVE-2026-85706, a perfect-10 path traversal flaw in the commits API, lets one unauthenticated request pull arbitrary files off a self-managed server — SSH keys, database credentials, deploy tokens, CI/CD variables. GitLab shipped fixes September 10th; CISA added it to the catalog the next day, after watchTowr saw scanning within 24 hours of disclosure — GitLab's second critical flaw under active attack in a month. Teams that got this right already treat CI/CD as Tier-Zero infrastructure: patch on the vendor's clock, and rotate anything a credential-bearing flaw exposed instead of closing the ticket at the version bump.

Which brings us to Adobe Commerce, briefly. Researchers call it StyleSmuggler — CVE-2026-75650, unauthenticated remote code execution in Magento. Attackers exploited it from September 4th, three days before Adobe's hotfix landed, planting a Rust-based Linux backdoor and PHP web shells. Adobe's guidance is blunt: patching stops new attacks, not old ones — merchants still have to rotate encryption keys, passwords, and payment credentials. My read: that's the real lesson of a true zero-day — a web application firewall in front of payment data buys you the days a patch can't.

Three vendors, one pattern: the real perimeter now is a management console, an API endpoint, a template engine — not the edge firewall on the whiteboard. Patched doesn't mean clean; it means the door's locked, not that nobody walked through.
