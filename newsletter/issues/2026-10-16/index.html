Current Events

The Hugging Face Malicious ML Models (nullifAI)

Picture a security scanner doing exactly what it was built to do -- checking every file for a known list of dangerous patterns -- and an attacker who wins not by being more dangerous, but by being too broken for the scanner to even read. That's the real trick behind nullifAI, a technique researchers found being used against Hugging Face, the platform where a huge share of the world's publicly shared AI models actually live. Here's how it actually worked.

AI models built with PyTorch are commonly saved using Python's pickle format -- a way of serializing an object, meaning converting a running program's data into a file that can be saved and loaded back later. Pickle's well-known danger is that loading one doesn't just read data, it can execute code, which is exactly why Hugging Face runs a scanner called Picklescan over every uploaded model, checking for known-dangerous function calls before anyone downloads it. According to ReversingLabs' own research, published February 6th, 2025, two models uploaded to the platform beat that scanner with a strange trick: instead of compressing the pickle file the normal way PyTorch expects, the attacker compressed it using a different, 7-zip-based method entirely. That meant the file couldn't even be opened with PyTorch's own standard loading function -- and Picklescan, built to expect a normal, well-formed pickle stream, hit the unusual structure, logged an error, and moved on without flagging the dangerous code sitting earlier in that same broken stream.

Root cause, in one sentence: a security scanner that's built to recognize known-bad patterns inside a well-formed file can be defeated by a file that's simply too malformed for the scanner to finish reading -- even though the exact same brokenness doesn't stop Python's own interpreter from running the dangerous part anyway.

Here's what held. Each malicious model's actual payload was a platform- aware reverse shell -- code that checks whether it landed on Windows, Linux, or Mac, then phones home to a single hardcoded IP address. ReversingLabs assessed this as most likely a proof-of-concept rather than an active, operational campaign, and once the firm reported it, Hugging Face removed both models and shipped an improved version of Picklescan specifically to catch malformed pickle streams like these.

So what does that mean for you? A senior engineer treats a security scanner's clean result as "didn't match my blacklist today," not "proven safe" -- because this incident proves that a scanner built around recognizing known-bad patterns can be beaten by input that just doesn't look like anything the scanner was taught to recognize at all, blacklist or not.

What Held

  • Independent research caught it before this scaled. ReversingLabs found both models through its own research, not because Hugging Face's existing control flagged them — but that research reached the platform fast, and the fix went out specifically targeting the malformed-stream technique that let the original two models through.
  • The payload was narrow and almost certainly a proof-of-concept. A platform-aware reverse shell to one hardcoded IP address is unsophisticated compared to what a resourced, operational actor would typically deploy against a high-value supply-chain target like a widely used model hub.
  • Say the limit of that out loud. "Assessed as likely a proof-of-concept" is ReversingLabs' own characterization based on the payload's simplicity, not a confirmed statement of the attacker's intent — naming that distinction, rather than calling this a fully solved incident, is the senior move, especially since the technique itself, once published, could be reused by someone with sharper intentions.

Senior Security Advice

Deploy Data Loss Prevention to Catch Data Walking Out the Door

The Advice

Deploy a data loss prevention (DLP) tool that watches the channels your sensitive data can actually leave through — email, cloud uploads, USB drives, chat and print — and blocks or flags anything moving through a channel it was never authorized to use.

Why It Matters

Most security budgets go toward keeping attackers out. Far fewer go toward noticing when data is on its way out, and that gap is exactly what gets exploited. CIS's own Control 14 guidance makes the point directly: in many breaches, victims did not realize sensitive data was leaving their systems because they were not monitoring data outflows at all. Without that visibility, a departing employee can zip up a customer database and upload it to a personal cloud drive, or a compromised account can quietly stage files to an external destination for days, and nobody notices until the data shows up somewhere it shouldn't. This is also the mechanic behind modern "double extortion" ransomware: the crew steals the data before they ever encrypt anything, specifically so they still have leverage even if backups restore cleanly. An organization with no egress visibility has no way to know that theft happened until the attacker tells them.

How to Implement It

  1. Classify the data first. DLP policies are worthless without knowing what counts as sensitive — customer PII, source code, credentials, regulated data — so this builds directly on a current data inventory.
  2. Cover the channels data actually leaves through, not just one: endpoint agents for USB and clipboard, the email gateway, and a CASB or SaaS-security layer for uploads to cloud storage and chat tools.
  3. Launch every new policy in monitor-only mode first. Watch what it flags against real business traffic, fix the false positives, and only then flip it to block — a DLP rollout that blocks on day one breaks legitimate work and gets disabled by an angry VP within a week.
  4. Write policies around data patterns and classification labels, not broad guesses — fingerprint known-sensitive files, match on regex for things like SSNs or API keys, and tag by the classification set in step 1.
  5. Verify it's actually catching something: run a controlled exfiltration test, a labeled dummy file with a known sensitive pattern, through each blocked channel on a schedule, and confirm it gets stopped and alerted on. NIST SP 800-53's SC-7(10) control does not just ask you to prevent exfiltration — it explicitly calls for periodic exfiltration testing, because a DLP tool nobody has tried to defeat is a guess, not a control.

The Pushback You'll Hear

"DLP floods us with false positives and slows people down." That is a tuning failure, not a reason to skip the control. The fix is the rollout order in step 3: monitor first, tune against real traffic, then block narrowly by data classification instead of broad keyword rules. The alternative — no visibility at all — is the exact failure CIS called out: entire breaches going unnoticed simply because nobody was watching data leave.

Tech News

Two stories tonight, and they're both about what happens when a security fix doesn't actually fix the thing the first time. If you're running on-premises Exchange or an Ivanti VPN gateway, you need both of these.

Start with Exchange. According to Microsoft's own disclosure, reported by Security Affairs, the company patched CVE-2026-96940 this month — an elevation-of-privilege flaw in on-premises Exchange Server 2016, 2019, and Subscription Edition, where weak authorization lets an attacker who's already authenticated on the network read other users' mailboxes they were never supposed to touch. Here's the part worth knowing: Microsoft's first fix, released October 2nd, reportedly broke some Exchange deployments, and a corrected version shipped October 5th before the flaw was folded into this month's main Patch Tuesday release on October 13th. Microsoft rates exploitation as "more likely," though no outlet is reporting confirmed attacks yet. My read: a patch that breaks the thing it's protecting doesn't just cost you a maintenance window — it buys the vulnerability extra days alive while admins wait to trust the second try. If you're still running the first release, you're not patched; you're exposed and inconvenienced at the same time.

Next up, an update on a story from this week. I told you Ivanti shipped a fix for an authentication bypass in Connect Secure, tracked as CVE-2026-104935. Here's what's new: according to The Register's reporting on Volexity's research, that's not the only hole in that VPN appliance right now. Volexity found a third, separate privilege-escalation flaw in the same product line, and Ivanti says a fix for that one isn't coming for weeks. My take: when a vendor tells you "we patched the headline bug, there's another one, and it's not ready yet," that's not a footnote — that's your cue to tighten compensating controls on that appliance today, not wait for the next advisory to tell you to.

Same thread both stories tonight: a patch announcement is the start of the verification work, not the end of it — check what version you're actually running, not what the vendor says you should be running.
