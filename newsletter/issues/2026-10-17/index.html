Current Events

Fortinet FortiOS SSL-VPN "XORtigate" (CVE-2023-27997)

Before you ever type a username into some VPN gateways, there's a brief window where the appliance is already running code on your behalf -- and in 2023, that window became one of the most exploited flaws on the internet. It's tracked as CVE-2023-27997, nicknamed XORtigate, and it hit FortiOS and FortiProxy, two of the most widely deployed SSL-VPN products on the planet. Here's how it actually worked.

FortiOS's SSL-VPN component has to parse incoming connection data before a user ever authenticates, because that's simply how a VPN gateway functions -- it has to understand what's being asked of it before it can even display a login prompt. According to Fortinet's own security advisory, FG-IR-23-097, published June 12th, 2023, researchers found a heap-based buffer overflow sitting in exactly that pre-authentication parsing code. A heap overflow means the program writes more data into a block of memory than that block was ever sized to hold, and when an attacker controls what spills over the edge, they can often turn that overflow into their own code running on the device -- fully unauthenticated, fully remote. Fortinet rated it 9.8 out of 10.

Root cause, in one sentence: a piece of code that by definition has to run before login even exists has no authentication check standing in front of it, so a memory-safety bug sitting there is a memory-safety bug with the front door already wide open.

Here's what held, and it's worth naming precisely because the exploitation record itself is genuinely mixed. Fortinet's own advisory said the flaw "may have been exploited in a limited number of cases" at disclosure -- not a confirmed mass campaign on day one. Singapore's Cyber Security Agency reported active exploitation around that same window, and researchers have since tied broader abuse of this flaw to state-linked activity over the following two years. The control that actually mattered here is simple: Fortinet shipped patched builds the same day as the advisory, and published disabling SSL-VPN entirely as an official workaround for anyone who couldn't patch immediately. An organization that did either one was never exposed, no matter how the exploitation picture developed afterward.

So what does that mean for you? A senior engineer treats a vendor's pre-authentication code path as inherently higher-risk than anything sitting behind a login, because this incident proves "unauthenticated" isn't a minor caveat on a CVE description -- it's the whole reason a 9.8 is a 9.8. On a RHEL and Podman lab, that means checking which services expose anything at all before login -- SSH with password auth, a web management interface, a VPN gateway -- and treating version currency on exactly those services as the single highest-priority patch item, not just another line in a monthly cycle.

What Held

  • Same-day patch availability. Fortinet shipped fixed builds the same day as the advisory — the fastest realistic path to closing exposure for anyone actively watching the vendor's advisory feed.
  • A documented workaround existed. Disabling SSL-VPN until patched was officially sanctioned by Fortinet, giving organizations without an immediate patch window a real compensating control instead of just an unprotected wait.
  • Say the limit of that out loud. "Shipped a patch the same day" describes availability, not adoption — plenty of appliances kept running vulnerable firmware for years afterward, which is exactly why this flaw kept resurfacing in exploitation reporting into 2025. Naming that gap between patch-released and patch-applied, rather than treating same-day availability as the end of the story, is the senior move.

Senior Security Advice

Keep SELinux in Enforcing Mode on Every Production Host

The Advice

Run every production Linux host with SELinux set to Enforcing, and treat any host where it has been switched to Permissive or Disabled as an open security finding, not a convenience setting.

Why It Matters

Standard Unix file permissions are discretionary: whoever owns a process decides what it can touch, and a compromised process inherits whatever that owner could already do. SELinux adds mandatory access control on top of that — a policy the process owner cannot override — so even a process running as root is confined to the narrow set of files, ports, and actions its security context actually needs. Without it, a single remote code execution bug in a web application has a much shorter path to full host compromise. This is the mechanic behind the web shell attacks that CISA and NSA have repeatedly warned organizations about: an attacker drops a small script through a vulnerable web app, and once that script can execute with the privileges of the web server process, it becomes a foothold for reading other users' files, pivoting to other services, or installing persistence. Mandatory access control doesn't stop the initial bug, but it denies the follow-on filesystem writes and process actions that turn one compromised app into a compromised host. The reason this control keeps slipping is almost always the same: SELinux denials are confusing, deadlines are tight, and setenforce 0 makes the error go away in five seconds — so it gets disabled "temporarily" and never gets turned back on.

How to Implement It

  1. Bake SELINUX=enforcing into the golden image or build pipeline as the default, so new systems never launch in Permissive or Disabled mode in the first place.
  2. Never resolve a denial by disabling SELinux. Pull the AVC denial from the audit log, use audit2allow to draft a narrow custom policy module, test it, and load only that module.
  3. If an app genuinely needs a temporary exception to diagnose a problem, use Permissive mode on that one host for that one investigation — never as a standing production state — then return it to Enforcing.
  4. Treat SELinux state as a monitored configuration item, not a one-time setting: have configuration management (Ansible, Puppet, etc.) check getenforce on a schedule and alert on drift, the same way you'd alert on a disabled firewall.
  5. Verify it's actually working, not just reporting Enforcing: trigger an action the policy should deny — an unauthorized file write or domain transition in a test environment — and confirm it's blocked and logged as an AVC denial. A host that reports "Enforcing" but has never been tested against a real denial is an assumption, not a verified control.

The Pushback You'll Hear

"SELinux broke my app and I don't have time to write a policy, so I just disabled it." The senior response: that trade gives up MAC protection for every process on the host, forever, to avoid writing one scoped policy module for one app. Red Hat's own guidance is direct about this — Permissive mode exists for exactly this kind of debugging, and Disabled mode is "strongly discouraged" because it also stops SELinux from labeling files, which makes turning it back on later even harder. Reading one AVC denial and running audit2allow usually takes less time than the meeting where someone asks why the firewall is also off.

Tech News

If your mail security gateway could already be compromised, Cisco just told you something most vendors never say out loud: don't patch it — rebuild it from scratch. Two stories tonight, and both are about appliances sitting right at your network's edge, both now confirmed under active attack.

Start with Cisco. According to Cisco's own security advisory, reported by BleepingComputer and The Hacker News, the company is warning that CVE-2026-76519, a critical, 9.8-out-of-10 flaw in Secure Email Gateway's Advanced Malware Protection feature, is being actively exploited — Cisco's own security team says it learned of real-world attacks this month. An attacker sends an email with a crafted attachment, and a relative path-traversal bug lets them write arbitrary files to the device and run commands as root. Here's the part that should get your attention: Cisco isn't telling affected customers to just upgrade and move on. Because an upgrade can wipe out the very logs you'd need to prove what happened, Cisco's guidance is to stand up a brand-new instance on a patched release, rebuild the configuration by hand instead of importing the old file, and rotate every credential and cryptographic key the device held. My read: when a vendor tells you not to trust an in-place patch to also serve as your incident response, that's the vendor admitting the compromise may already own the box — and chain-of-custody thinking, not just patch speed, is what separates a senior response from a junior one.

Next up, Palo Alto Networks. According to Palo Alto's own security advisory and reporting from The Hacker News, the company patched CVE-2026-0322, a code-execution flaw in the PAN-OS web management interface that the advisory itself describes as showing "very limited exploitation" against firewalls that exposed that interface to begin with. CISA added it to the Known Exploited Vulnerabilities catalog on October 14th, with a remediation deadline for federal agencies landing today. The fix matters, but so does the exposure it depends on: Cloud NGFW and Prisma Access were never affected, because they don't expose that same management surface the way an on-premises PA-Series box can. My take: this is a reminder that "patch the CVE" and "stop exposing the management interface to begin with" are two different fixes, and only doing the first one leaves you one new bug away from the same conversation.

Same thread both stories tonight: the appliances sitting at your network's edge are also the ones vendors build with the least assumption that an attacker is already watching — which is exactly why, when something goes wrong there, the fix is rarely just "install the update."
