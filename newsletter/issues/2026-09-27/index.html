Current Events

The XZ Utils Backdoor

Here's how close the internet came to one of the widest-reaching backdoors in software history: it was caught not by a security team, but by one engineer noticing an SSH login was four hundred milliseconds slower than it should have been. Two stories from this one: how a patient, years-long con turned a trusted open-source maintainer into an unwitting cover story, and how a single performance complaint unraveled it days before it would have reached almost every major Linux distribution.

XZ Utils is compression software baked into nearly every Linux system on Earth -- it's a dependency of a library called liblzma, which in turn gets linked into OpenSSH, the software that handles secure remote logins on most servers in the world. According to independent research compiled after the fact, starting around 2021, an account using the name "Jia Tan" began contributing to the XZ Utils project, slowly building trust over roughly two years -- fixing real bugs, engaging on the mailing list, and eventually pressuring the sole overworked maintainer into handing over co-maintainer access, reportedly with help from sock-puppet accounts pushing for exactly that outcome.

Here's the mechanism. Jia Tan didn't put the backdoor in plain sight in the source code. It was hidden inside binary test files disguised as corrupted sample data, unpacked and injected during the build process by a modified build script -- specifically a file called build-to-host-dot-m4 -- so a human reviewing the readable source code on GitHub would never see it. The payload patched how liblzma hooked into sshd, giving an attacker holding a specific private key the ability to bypass authentication entirely and run commands on the server. Jia Tan had even disabled a specific fuzzing check in Google's oss-fuzz project months earlier, closing off the one automated tool that might have caught it.

Root cause, in one sentence: a small, volunteer-maintained project that huge parts of the internet quietly depend on had exactly one tired maintainer, and a patient attacker spent two years exploiting that single point of human trust rather than looking for a technical flaw at all.

Here's what actually stopped it. On March 29th, 2024, Andres Freund, a Microsoft engineer, was benchmarking PostgreSQL on Debian's unstable branch and noticed SSH logins taking about five hundred milliseconds instead of the usual hundred. Most people would have shrugged that off. He didn't -- he traced it through a profiler, found the anomaly led into liblzma, and posted his findings to the open-source security mailing list within roughly 48 hours of first noticing the slowdown. Because the backdoor had only reached bleeding-edge, unstable distributions -- Fedora Rawhide, Debian testing, not the stable releases production systems actually run -- the blast radius stayed contained to developers and testers, not the wider internet.

Here's what a senior engineer, or a senior ISSO, would change in how they work because of this. Trusting open source doesn't mean trusting the code alone -- it means asking who maintains a critical dependency, how many people that project actually has, and whether a compromise of one human's judgment could compromise everything downstream. In a RHEL 9 lab, that means running a real dependency audit on one production system: listing what a critical package actually links against, and asking honestly whether you'd notice a five-hundred-millisecond anomaly if it showed up on your watch.

What Held

  • Release engineering practices limited the blast radius. The backdoor had only propagated into bleeding-edge, unstable distribution branches — Fedora Rawhide, Debian testing/unstable, openSUSE Tumbleweed — not the stable, widely-deployed releases most production systems actually run. That gap between "unstable" and "stable" branches is a control, not luck, and naming it as one is the senior read on this incident.
  • One engineer's habit of investigating anomalies instead of dismissing them. A 400-millisecond SSH login delay is the kind of thing most people never notice, let alone chase down to its root cause — that habit, not a security tool, is what caught this.
  • Fast, coordinated disclosure. CVE assignment, a CISA advisory, and distribution-maintainer emergency reverts all happened within roughly 48 hours of the initial report, which is what kept a maximum-severity, pre-widespread-deployment backdoor from ever reaching stable production systems at scale.

Senior Security Advice

Encrypt Data at Rest by Default with Customer-Managed KMS Keys

The Advice

Encrypt every data store by default using customer-managed keys, not the provider's default keys, and make unencrypted storage impossible to create.

Why It Matters

Encryption at rest is the control that determines what a stolen disk, a misconfigured snapshot, or a leaked backup actually costs you. If the data underneath is encrypted with keys you control, a lost or exposed storage volume is close to worthless to an attacker. If it isn't, that same event is a full data breach: customer records, credentials, and internal documents readable by anyone who gets the bytes. This is exactly the failure mode behind the incident class of exposed cloud storage and stolen backup media showing up in breach disclosures year after year - not a sophisticated hack, just data that was never encrypted, or encrypted with a key the organization didn't actually control. NIST SP 800-53's SC-28 control, Protection of Information at Rest, exists specifically because storage devices, databases, and backups routinely end up outside their intended boundary, and cryptographic protection is what keeps that exposure from becoming a compromise.

How to Implement It

  1. Turn on default encryption at the account or organization level for every storage service - object storage, block storage, databases, backups - so a new resource cannot be created unencrypted in the first place.
  2. Use customer-managed keys (for example, AWS KMS customer managed keys) instead of provider-managed defaults for anything sensitive, so you control the key policy, rotation, and who can use the key, not just whether encryption is "on."
  3. Write a key policy that follows least privilege: restrict which IAM principals and services can use or manage each key, and keep humans out of raw key material entirely.
  4. Turn on automatic annual key rotation and enable logging of every key usage event to your central log pipeline.
  5. Verify it's actually working, not just enabled: run an account-wide scan (via your cloud provider's config or posture tool) that flags any storage resource without encryption or using the wrong key, and pull the key usage logs to confirm the expected services - and only the expected services - are actually calling the key.

The Pushback You'll Hear

"Encryption is already on by default, so we're covered." The senior-engineer rebuttal: default encryption using the provider's own managed key protects you from a stolen physical disk, but not from a misconfigured permission that hands your data to the wrong principal, because you don't control that key's policy. Customer-managed keys are what let you decide, in one place, exactly who is allowed to unlock the data - and prove it later with logs.

Senior Talk Tracks

What SREs Mean by Toil

Site Reliability Engineers -- SREs, the people who keep production systems up and running -- use a word you won't hear much outside their world: toil. It's not just a fancy synonym for "hard work." It has a specific, almost clinical definition, and getting that definition right is what separates someone who's read about SRE from someone who's actually lived it.

Here's the plain version. Toil is work that's manual, repetitive, automatable, and produces no lasting value once it's done. Think of restarting the same stuck service by hand every few days, or manually clearing disk space on a server that fills up on a predictable schedule. You did something. Tomorrow, you'll do the exact same thing again. Nothing about the system got better because you did it.

Here's why that matters in production, and the senior take: a junior engineer sees toil as just part of the job -- tickets come in, you handle them, that's operations. A senior engineer treats toil as a number to drive toward zero, because every hour spent on it is an hour not spent on the work that actually prevents the next incident -- better monitoring, automation, fixing the root cause instead of the symptom. Google's own SRE teams famously cap how much of an engineer's time can go to toil, specifically because letting it creep past that line quietly turns an engineering team into a 24-7 manual labor crew.

Think of it like mopping a floor that has a leak in the ceiling directly above it. You can mop that floor every single day forever, and it'll feel like productive work -- the floor gets dry. But until someone fixes the leak, you're not actually solving anything, you're just resetting the same problem on a loop. Toil is mopping. Fixing the leak is engineering.

A natural way to open this at work: "How much of what our on-call rotation handles is genuinely new versus the same three things happening again and again? Because if it's the same three things, that's not an on-call problem, that's an automation backlog."

Key Takeaways

  1. Toil is specifically manual, repetitive, automatable work that produces no lasting improvement — not just "work that feels tedious."
  2. Tracking toil as a percentage of an engineer's time is a deliberate SRE practice, because unmanaged toil quietly crowds out the engineering work that actually prevents future incidents.
  3. The fix for toil is almost never "work harder" — it's automating the repeated task or fixing its root cause so it stops recurring at all.

Reader Question

"If toil is so well understood as a problem, why does it keep accumulating on most teams anyway?"

I'd say it's because toil is individually cheap and automation is individually expensive — fixing one stuck service by hand takes five minutes, while building the automation to prevent it recurring might take a day, so in the moment, the manual fix always looks like the rational choice. My answer would be that a team has to deliberately protect time for automation work against that daily pressure, usually by tracking toil explicitly and treating a rising toil percentage as its own kind of incident worth acting on, not just an annoyance to tolerate.

Tech News

A maximum-severity flaw in an identity gateway used by nearly a thousand banks, telecoms, and government agencies has been under active attack for almost two weeks, and the patch has been sitting there since April. Two stories today: a forged-login bug in WSO2's API platform that CISA wants federal systems fixed today, and a zero-day in the software that runs branch-office networks for enterprises worldwide.

Start with WSO2. CVE-2026-5430 is an authentication bypass in WSO2 API Manager, Control Plane, Traffic Manager, and Universal Gateway, and it scores a perfect 10 out of 10 on severity. Here's the mechanism: when a user logs in, the system checks a signed token — a JWT — to confirm who they are and what they're allowed to do. WSO2's validator was supposed to check that the token was signed with an approved algorithm. It didn't enforce that strictly enough, so an attacker could hand it a token signed with an unsupported algorithm and the system would accept it anyway — no valid credentials required, administrator privileges included. Security firm WatchTowr caught forged tokens hitting a honeypot on September 13th. CISA added it to the Known Exploited Vulnerabilities catalog on September 24th, with a federal deadline of today. Here's the takeaway: this bug was patchable back in April. Five months of exposure on an identity platform, the exact system every other application in the environment trusts to say who's who, is the kind of gap a senior engineer flags loudly in a risk review, not something that waits for a KEV deadline to force the conversation.

Next up, Arista. The company disclosed on September 22nd that attackers are actively exploiting CVE-2026-93952, another perfect-10 flaw, this time in VeloCloud Orchestrator — the management console for Arista's SD-WAN, the software that runs branch-office networking for enterprises. An improper input-validation bug lets a remote attacker reach privileged internal functions on the orchestrator with no credentials and no user interaction at all. CISA gave federal agencies until September 25th to secure their networks. My take: a network orchestrator is a single console with reach into every site it manages — when a flaw like this needs zero authentication, the blast radius isn't one branch office, it's every branch office that console touches, which is exactly why an unauthenticated, zero-interaction bug in central network management earns a same-week patch, not a same-quarter one.

Both stories land on the same principle: the systems that decide who gets trusted — an identity gateway, a network orchestrator — are the highest-value targets in your environment, and that's exactly why their patch cadence can't lag behind everything else's.
