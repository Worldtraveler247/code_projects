Current Events

The CircleCI Session-Token Breach

A stolen browser cookie bypassed two-factor authentication at one of the world's biggest CI/CD platforms -- no password needed, no second factor required, because the attacker already had a logged-in session. Here's how a single infected laptop turned into a breach that touched customer secrets across the industry.

In December 2022, an unauthorized party planted custom malware on the laptop of an engineer at CircleCI, the continuous-integration and continuous-delivery platform thousands of software teams use to build and deploy their code. According to CircleCI's own incident report, that malware did something the company's endpoint security tools weren't watching for: it stole a valid, two-factor-backed single sign-on session cookie. A session cookie is what proves to a system that you're already logged in, so stealing one skips the login screen entirely. The two-factor authentication protecting that account never got a chance to matter, because the attacker wasn't logging in at all -- they were impersonating a session that had already logged in, hours or days earlier.

Here's the chain. That stolen cookie let the attacker act as the engineer, remotely, from wherever they actually were. The engineer happened to hold standing privilege to generate production access tokens, and the attacker rode that same privilege to escalate into a subset of CircleCI's production systems. From there, data belonging to CircleCI's customers -- environment variables, API keys, and tokens those customers had stored in CircleCI to connect to their own GitHub, Bitbucket, and AWS environments -- sat inside the same access the attacker now had. CircleCI says it was alerted to suspicious activity on December 29th, and by January 4th had cut the compromised account off, rotated its own production infrastructure, and gone public with a blunt instruction to every customer: rotate everything.

Root cause, in one sentence: endpoint protection software failed to catch a custom infostealer on a managed laptop, and once that failed, one employee's everyday ability to mint production access tokens became the attacker's ability too.

What actually held: CircleCI didn't try to quietly rotate only the secrets it could prove were touched. It told every single customer to rotate every secret stored on the platform, and it coordinated directly with GitHub and with Atlassian's Bitbucket to revoke and reissue OAuth tokens on the platform side as well. That blanket, fast response is what actually closed the exposure -- not the original authentication, which had already failed days earlier.

So what does this mean for a senior engineer's own environment? A senior engineer treats a stolen session as functionally identical to a stolen password, because from the server's point of view, it is one -- which is why session lifetime and the ability to revoke a session instantly matter just as much as the login check itself. On an AWS or RHEL lab, that means practicing exactly that: setting a short-lived session token, then confirming that a token is actually rejected once it's revoked, not just assuming a strong login means a safe session.

Control Failures

# Failure NIST SP 800-53 Rev 5 Control Family
1 A stolen SSO session cookie was sufficient to impersonate an already-authenticated employee, with no re-verification tied to device or behavior after the original login. IA-5 — Authenticator Management
2 A single engineer held standing privilege to generate production access tokens at any time, with no just-in-time elevation required. AC-6 — Least Privilege
3 The company's endpoint protection (EDR/antivirus) software did not detect a custom infostealer running on a managed laptop. SI-3 — Malicious Code Protection
4 No internal control flagged anomalous session or account behavior during the roughly thirteen-day gap between the December 16 compromise and the December 29 alert. SI-4 — System Monitoring
5 No mechanism existed to instantly invalidate an active session once a device compromise was suspected, beyond revoking it after the fact. AC-12 — Session Termination

What Held

  • Blanket secret rotation closed the exposure, not the original authentication. CircleCI told every customer to rotate every secret rather than narrowly scoping the advisory to confirmed-affected accounts — a wider, blunter response that didn't wait for a complete forensic picture before cutting off the thing attackers actually monetize.
  • Coordinated third-party revocation shortened the downstream window. GitHub and Atlassian's Bitbucket worked directly with CircleCI to revoke and reissue OAuth tokens on their own platforms, closing a path the attacker could otherwise have kept using even after CircleCI secured its own systems.
  • Internal escalation was fast once the signal was real. Cutting the compromised employee's account and rotating production hosts the same day CircleCI understood what it was looking at kept a known-bad session from staying useful any longer than necessary.

Senior Security Advice

Enforce the Two-Person Rule on Every Production and Code Change

The Advice

No single engineer should be able to write a change, approve it, and ship it to production alone — require a second, different person to review and sign off on every production and code change before it goes out.

Why It Matters

Most access controls focus on keeping outsiders out. The two-person rule assumes someone on the inside — a compromised account, a rushed mistake, or a malicious insider — will eventually try to push something harmful straight into production, and it makes sure one set of hands is never enough to do that alone.

Without it, compromise looks like this: an attacker phishes or steals the credentials of a single engineer with merge and deploy access, then commits a backdoored change directly to a pipeline that nobody else reviews. Nothing stops it, because the person who wrote the change is also the person who approved it. This is exactly the pattern behind software supply chain attacks that target build and deployment pipelines — a single trusted identity with unchecked authority to ship code becomes the whole attack surface. A second reviewer, with no stake in rushing the change out, is often the only thing standing between a bad commit and a production incident.

How to Implement It

  1. Turn on required reviews in the code repository so nothing merges to a protected branch without approval from someone other than the author — not a checkbox the author can tick themselves.
  2. Extend the same rule past application code to infrastructure-as-code, pipeline configuration, and production deployment approvals, since attackers go after the pipeline as often as the code.
  3. Close the loophole where "two people" turns out to be one person with two accounts: tie reviewer identity to single sign-on and flag any approval where author and reviewer resolve to the same person.
  4. Verify it, don't just configure it: have someone try to self-approve or push directly to the protected branch and confirm the system blocks it and logs the attempt.
  5. Pull the repository's audit log periodically and look for bypasses — direct pushes, admin overrides, or emergency merges — and require those to be justified and reviewed after the fact.

The Pushback You'll Hear

"This will slow us down — we need to ship fast." The rebuttal: a second review that's wired into the pipeline correctly adds minutes, not days, and most of that friction disappears once reviewers know what they're looking for. The real cost comparison isn't "fast versus slow," it's "minutes of review" versus "the hours or days spent rolling back a change that one compromised or careless account pushed straight to production with nobody else watching."

Tech News

For about eleven hours this week, a tool thousands of developers trust for writing code was quietly handing out a backdoor instead. If you run developer tooling, CI pipelines, or Linux servers, both of tonight's stories are for you. Two stories: a trojanized Claude Code extension that landed on a trusted marketplace, and a Linux kernel flaw serious enough that an AI model built a working exploit for it in under an hour.

Start with the extension. According to Cursor's own disclosure, corroborated by BleepingComputer, Help Net Security, and The Register, a tampered build of the Anthropic Claude Code extension sat live on Cursor's own marketplace for roughly eleven hours on October 29th, reaching as many as five thousand users before Cursor pulled it. The payload tried to drop an attacker's SSH key onto the machine, switch on the local SSH service, and open a reverse tunnel back to the attacker's own server — and even when that failed, it still phoned home with reconnaissance data. Anthropic says it didn't build or publish the tampered copy; Cursor says an attacker used access to its own marketplace to push it, and hasn't yet explained how that access was obtained. Here's my read: uninstalling the extension doesn't remove the backdoor on its own — anyone who ran it needs to check for a planted key and rotate credentials, which is the real lesson developer tooling keeps teaching us. Trust in a package feed is not the same thing as security in a package feed.

Next up, turning to the Linux kernel. According to multiple security researchers covering Anthropic's own disclosure, an unreleased internal Anthropic research model built a working exploit for CVE-2026-98432, a use-after-free bug in the kernel's TCP handling code, carrying a near-maximum severity score. On a server running a Multipath TCP listener, the flaw can hand an unauthenticated remote attacker full root — no password, no login, nothing. As of this report, nobody has confirmed an attack using it in the wild, and patch status still varies distribution by distribution. My take: a senior engineer doesn't wait for exploitation evidence on a bug this severe. A use-after-free with a path to remote root is a patch-today problem, not a patch-when-convenient one.

Tonight's thread: whether it's a marketplace you downloaded from or a kernel you didn't write yourself, the trust you extend to someone else's code is exactly where both of these stories landed.
