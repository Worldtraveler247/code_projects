Current Events

The Knight Capital Trading Glitch

Here's an incident where one missed server erased four hundred forty million dollars in forty-five minutes, and nearly ended one of the largest trading firms on Wall Street. Here's how it actually happened.

On August 1st, 2012, Knight Capital Americas was going live with a new feature for the New York Stock Exchange's Retail Liquidity Program. According to the SEC's own administrative order, a Knight technician manually deployed the new code to the firm's automated order router, called SMARS, across eight production servers. The code went out to seven of them. The eighth server never got the update.

Here's why that mattered. The new code repurposed an old flag inside SMARS -- a flag that used to trigger a function called "Power Peg." Knight had retired Power Peg back in 2003, but the code itself was never deleted. It just sat there, dormant, for nine years. On that one un-updated server, the new flag didn't launch the retail liquidity feature. It woke Power Peg back up.

When the market opened at 9:30 a.m., Power Peg did exactly what it was built to do -- except, per the SEC's findings, the piece of it that was supposed to track how many shares had already filled on a given order had been moved to a different part of the code years earlier and no longer worked. So the system kept firing orders into the market, never recognizing that any of them had been filled, and never stopping on its own. There was no automated circuit breaker. It took Knight's own engineers until 9:58 a.m. -- twenty-eight minutes after the opening bell -- to manually track down the problem and shut the router off. By then, SMARS had sent more than four million orders into a hundred fifty-four stocks, trading over three hundred ninety-seven million shares Knight never meant to buy or sell.

Root cause, in one sentence: a manual deployment left obsolete, undeleted code live on a single production server, and nothing in Knight's process could verify the fleet was consistent before the market opened.

Here's what actually contained this. The New York Stock Exchange broke -- meaning canceled -- trades in six securities where prices had swung by at least thirty percent, limiting the damage in the most extreme cases. And once Knight's capital was nearly wiped out, a group of investors led by Jefferies moved overnight to put in roughly four hundred million dollars, keeping the firm solvent long enough to wind down its position in an orderly way instead of collapsing outright.

Here's what a senior engineer, or a senior ISSO, would change in how they work because of this. A deployment process needs an automated way to confirm every server in a fleet is actually running identical code before anything goes live -- not a technician's checklist under time pressure. In a RHEL 9 lab with Podman, that means pushing a build across a handful of containers standing in for a server fleet, hashing what actually landed on each one, and refusing to call the deployment complete until every hash matches -- so a partial rollout gets caught by a script, the way it never was here.

What Held

  • NYSE's authority to break erroneous trades. Canceling trades in six securities where prices had swung at least 30% limited Knight's locked-in losses in the most extreme cases — a market-structure safeguard, not a Knight control.
  • Emergency private-sector recapitalization. The Jefferies-led consortium's roughly $400 million overnight financing kept Knight solvent and let it unwind its accidental position in an orderly way rather than defaulting outright, limiting broader market contagion.
  • Be honest about the limit of both. Neither control stopped or even slowed the erroneous trading itself — both operated purely after the fact. Detection and containment inside Knight were entirely manual, and took the full 45 minutes the market was open before anyone pulled the plug.

Senior Security Advice

Enforce TLS 1.2+ Everywhere and Retire Legacy SSL/TLS

The Advice

Every service that accepts a network connection must negotiate TLS 1.2 or higher, and SSL 2.0, SSL 3.0, and TLS 1.0/1.1 must be disabled outright, not just deprioritized.

Why It Matters

A login form, an internal API, or an admin panel that still accepts an old encryption protocol is handing an attacker a downgrade path. Those legacy protocols carry known, fixable-only-by-removal weaknesses — predictable initialization vectors, weak padding checks, export-grade ciphers that can be brute-forced — that let an attacker sitting on the network read or tamper with traffic that everyone assumes is private. The incident class this closes is the on-path interception: an attacker on a shared network, a compromised router, or a rogue access point forces or waits for a connection to fall back to an old protocol version, then reads session tokens, passwords, or sensitive data right out of what looked like an encrypted channel. The fix isn't a patch to the old protocol — there isn't one — it's turning the old protocol off.

NIST Special Publication 800-52 Revision 2 sets TLS 1.2 as the floor, requires TLS 1.3 support, and states that TLS 1.1 should not be configured and TLS 1.0, SSL 3.0, and SSL 2.0 shall not be used. CISA's guidance on securing data in transit points the same direction, recommending TLS 1.3 wherever possible and TLS 1.2 or later as the baseline for everything else.

How to Implement It

  1. Inventory every listener that terminates TLS — load balancers, API gateways, internal service mesh endpoints, even old admin interfaces and IoT management ports — because you can't retire a protocol you don't know is running.
  2. Set the minimum negotiable protocol version to TLS 1.2 at every one of those listeners, and enable TLS 1.3 where the platform supports it, instead of leaving the default "any version" setting in place.
  3. Explicitly disable SSL 2.0, SSL 3.0, TLS 1.0, and TLS 1.1 at the server or load-balancer configuration, rather than assuming a weak protocol is unreachable just because nobody uses it on purpose.
  4. Verify the control is actually working, not just configured: run an external TLS scanner (such as testssl.sh or an equivalent handshake test) against each public endpoint and confirm the server actively refuses a TLS 1.0/1.1 handshake instead of silently accepting it.
  5. Re-scan on a recurring schedule, because a new load balancer, a forgotten legacy service, or a default configuration reintroduced during a migration can quietly reopen the old protocol without anyone changing a policy on purpose.

The Pushback You'll Hear

"We have an old client or partner integration that only speaks TLS 1.0." The senior-engineer rebuttal: that client is the risk, not a reason to keep the door open for everyone else. Isolate that one integration behind its own endpoint with a documented exception and an expiration date, instead of lowering the minimum protocol version for every other user and system that connects to you.

Tech News

Fortinet's own email security gateway has a critical flaw under active attack right now, and there's still no patch — only a workaround. That's the gap that keeps a security team up at night. Three stories today: that FortiMail zero-day, fresh detail on what attackers do once they're inside a Citrix appliance, and a quieter flaw in the tool that hands out storage inside a Kubernetes cluster.

Start with FortiMail, Fortinet's email security appliance — the gateway a lot of organizations put in front of the inbox to filter spam and malware before it reaches an employee. According to Fortinet's own advisory, published October first, the flaw — Common Vulnerabilities and Exposures number 2026-104286 — combines a path traversal bug with mishandled null bytes, special characters that trick the system into reading a shorter, different file path than the one actually sent. Severity: nine point eight out of ten. One crafted web request, no login required, and an attacker writes a file anywhere on the underlying system. The Cybersecurity and Infrastructure Security Agency, or CISA, added it to the Known Exploited Vulnerabilities catalog that same day, with a federal deadline of this Sunday, October fourth. Here's my read: when a vendor ships a workaround instead of a fix, that workaround isn't optional reading — disabling identity-based encryption and cutting the management interface off from the internet is the real patch until an actual one exists.

Next up, Citrix. You may recall NetScaler's unauthenticated command-injection hole from late September. According to The Hacker News, researchers this week detailed what attackers do after breaking in: create a hidden superuser account, then drop a web shell disguised as an ordinary style-sheet file so it blends into NetScaler's own interface. My take: patching the vulnerability is step one. If nobody's hunted for new accounts and files that appeared while that door was open, the door's closed, but nobody's checked who already walked through it.

Which brings us to Amazon. AWS disclosed a medium-severity flaw, CVE-2026-103505, in the driver that connects a Kubernetes cluster to its Elastic File System storage. According to AWS's own security bulletin, anyone with permission to request a storage volume could sneak unauthorized mount options past the driver's checks. AWS fixed it in version three-point-five. On its own, that's a narrow bug. My take: the real lesson is that in Kubernetes, the permission to request storage is itself a privileged action — handing it out freely hands out more trust than most teams realize.

Through-line: a missing patch, a planted account, an overly trusted permission — different systems, same gap between what got deployed and what's actually being watched.
