Current Events

The Tesla Kubernetes Dashboard Cryptojacking Incident

In early 2018, a security research firm found one of Tesla's cloud consoles wide open on the internet -- no password, no login screen, nothing -- and inside it, attackers were quietly mining cryptocurrency on Tesla's own dime. Here's how it actually happened.

Tesla, like a lot of companies, ran part of its infrastructure on Kubernetes -- the system that automates deploying and managing containerized applications across a fleet of servers. Kubernetes ships with an optional web-based dashboard for managing a cluster, and according to the security firm RedLock, one of Tesla's Kubernetes dashboards was reachable from the open internet with no authentication required at all.

Here's the chain. Anyone who found that dashboard could see straight into the cluster -- no login, no multi-factor prompt, nothing. Inside one of the exposed pods, RedLock's researchers found access keys for Tesla's Amazon Web Services account, sitting in plain environment variables. Whoever got there first used those keys to reach Tesla's AWS environment and quietly stood up cryptocurrency-mining software across it. And this wasn't a smash-and-grab -- the attackers kept CPU usage low to avoid tripping obvious alarms, ran the mining software on a non-standard port, and hid their mining pool's server behind Cloudflare instead of connecting to a known public pool address that security tools might flag.

Here's the root cause in one sentence: an administrative console that should never have been reachable from the internet was reachable from the internet, and it was sitting one click away from live cloud credentials.

Here's what held. RedLock's cloud security monitoring is what caught this at all -- not Tesla's own internal alerting. And once notified, Tesla fixed it within hours and says the exposure was limited to internally used engineering test cars, with no indication customer vehicle safety, security, or privacy was affected.

Here's what a senior engineer, or a senior ISSO, would change in how they work because of this. An administrative dashboard is not a public-facing product, and it should never be reachable without a network boundary and an authentication layer in front of it -- full stop, no exceptions for internal tooling. And any credential sitting in a pod's environment variables should be treated as one misconfigured ingress rule away from being public, which is exactly why short-lived, tightly scoped credentials and a locked-down Kubernetes dashboard are both non-negotiable in a RHEL, Podman, and AWS environment running any container orchestration at all.

What Held

  • A third-party cloud security monitoring service caught what internal tooling didn't. RedLock's external scanning is the only reason this was found and fixed instead of continuing indefinitely — a strong argument for not relying solely on in-house detection.
  • Tesla's remediation was fast. Once notified, the exposed dashboard was locked down within hours, not days — the kind of response time that limits how long a known gap stays open.
  • Blast radius stayed contained. Tesla's own statement said the impact was limited to internally used engineering test cars, with no indication customer privacy, vehicle safety, or vehicle security was compromised — naming that boundary matters as much as naming the failure.
  • A working bug bounty program turned an external researcher into a partner instead of an adversary. RedLock disclosed responsibly, was credited and compensated through Tesla's program, and the incident became public on Tesla's own remediation timeline rather than through a leak.

Senior Security Advice

Deploy Endpoint Detection and Response on Every Endpoint

The Advice

Put endpoint detection and response (EDR) on every server, workstation, and laptop in the organization, centrally managed, with alerts routed to a human — not just installed and forgotten.

Why It Matters

Traditional antivirus checks a file against a list of known bad signatures and misses anything new. EDR instead watches behavior on the endpoint itself — a process spawning a shell, a script disabling logging, a binary reaching for credentials it has no business touching — and can isolate the machine or kill the process the moment that shows up. Without it, an attacker who lands on one laptop or server gets a quiet window to dump credentials, map the network, and reach for the next machine, with nothing on that endpoint watching the behavior itself. The incident class this stops is exactly the one CISA calls out in its ransomware guidance: an initial foothold that goes undetected long enough for the attacker to escalate and spread before anyone notices. By the time a ransom note appears, EDR was either missing, misconfigured, or its alerts never reached a person who could act.

How to Implement It

  1. Deploy an EDR agent to every server, workstation, and laptop — not just the ones that feel high-risk. CIS Control 10 is explicit that effective malware defense means EDR or anti-malware tooling on all servers, workstations, and laptops, managed centrally, not a patchwork of coverage.
  2. Configure the tool to escalate warnings and indicators to security personnel automatically, rather than leaving alerts to pile up in a console nobody watches.
  3. Enable behavior-based detection, not just signature matching, so the tool catches new or fileless techniques instead of only known malware.
  4. Verify coverage, not just installation: run an automated inventory comparison between your asset list and your EDR console weekly, and treat any endpoint missing the agent as a finding, not a rounding error.
  5. Verify the control actually works: run a benign, pre-approved test detection (most EDR vendors ship one) on a schedule and confirm it generates a real alert that reaches an analyst — an EDR agent that's installed but silently failing to report is functionally the same as no EDR at all.

The Pushback You'll Hear

"We already have antivirus, isn't that enough?" The senior-engineer rebuttal: signature-based antivirus stops known malware; it doesn't watch behavior, and most real intrusions today don't rely on malware a scanner would recognize. CIS Controls treat EDR as the modern baseline specifically because it catches the process-level behavior — credential dumping, lateral movement, disabled logging — that a signature scan walks right past. Antivirus is a floor, not a substitute.

Senior Talk Tracks

What an Admission Controller Buys You

If you've worked with Kubernetes for a while, you've probably heard the term "admission controller" and mentally filed it under "some validation thing." Today I want to give you the senior version of that idea, because it's actually one of the more powerful levers in the whole system.

Plain English first. When you ask Kubernetes to create something -- a pod, a deployment, whatever -- that request doesn't go straight into the cluster. It passes through a checkpoint first. An admission controller is a piece of code that sits at that checkpoint and gets to look at every single object before it's allowed to exist, and either let it through, change it, or reject it outright.

Here's why that matters in production. Say your organization has a rule: no container runs as root. You could try to catch that in code review, or hope your CI pipeline flags it. But someone will always find a path around a rule that only lives in a process. An admission controller enforces it at the one point nothing can bypass -- the literal moment before the object is allowed to exist in the cluster. Write a policy that says "reject any pod requesting to run as root," and it doesn't matter if that pod came from a careful engineer, a rushed hotfix, or a compromised CI pipeline -- it never gets created.

The senior take, the part a junior engineer usually misses: most people think of Kubernetes security as "what can a pod do once it's running" -- network policies, resource limits, that kind of thing. An admission controller moves the question earlier: "should this thing have ever been allowed to exist in the first place." That's a completely different, and much stronger, security posture. You're not cleaning up after a bad deployment, you're refusing to let it happen.

Think of it like airport security instead of a police patrol downtown. A patrol reacts to trouble after someone's already inside the city doing something. Airport security stops the wrong thing from ever getting on the plane in the first place. An admission controller is the checkpoint, not the patrol.

A good way to raise this at work: "before we ship this, do our admission controllers actually block what we think they block, or are we just hoping nobody writes an insecure pod spec?"

Key Takeaways

  1. An admission controller inspects every object before it's allowed to exist in a Kubernetes cluster, not after — it's a gate, not a patrol.
  2. Security rules that only live in documentation or code review get bypassed eventually; rules enforced by an admission controller can't be skipped by a rushed deployment.
  3. Admission control shifts the security question from "what can this pod do once running" to "should this pod have ever been allowed to run at all."

Reader Question

"If an admission controller can reject bad configurations, why do we still need runtime security tools at all?"

Because admission control only sees the object's declared specification at creation time — it can't see what a container actually does once it's running, like an application that behaves fine on paper but gets exploited and starts making unexpected network calls at runtime. I'd treat admission control as closing off an entire category of bad configurations before they exist, and runtime security as the separate layer that watches for the things no static policy could have predicted — together they cover both "was this allowed to start" and "is this behaving the way it should now that it's running."

Tech News

One AWS agent installed on millions of cloud servers had a bug serious enough to hand an attacker your cloud credentials — a 9.9 out of 10 on the severity scale. If you run infrastructure in AWS, or you're studying for a role where you will, today's for you. Two stories: that AWS flaw, and a pair of router bugs that just blew past a federal patch deadline.

Start with AWS. Amazon disclosed CVE-2026-89049 on September 10th — a server-side request forgery flaw in the Systems Manager Agent's port-forwarding feature, the tool a lot of teams use instead of opening SSH to a server directly. Here's the problem: an attacker who only has permission to open a port-forwarding session — not shell access, not Run Command — can abuse that session to reach link-local addresses, including the instance metadata service at 169.254.169.254. Reach that, and you can pull the EC2 instance's own temporary IAM credentials straight out of it. A lot of security teams deliberately hand out port-forwarding access as the "safe," narrow permission and keep shell access locked down separately. This bug erases that boundary. AWS fixed it in Systems Manager Agent version 3.3.4851.0. My read: this is a reminder that a permission's name doesn't tell you its actual reach — "port forwarding" sounds narrow until you test what network it can actually touch.

Next up, routers. CISA added two MikroTik RouterOS flaws to its Known Exploited Vulnerabilities catalog on September 10th, with a mitigation deadline of September 13th — already passed as of this recording. One is a missing-authentication bug in the router's bandwidth-test service that an unauthenticated attacker can use to leak kernel memory or crash the device outright. The other lets an attacker with nothing but an unauthenticated SSH attempt smuggle a crafted username past the login handler and escalate privileges on the box. MikroTik shipped fixes across its RouterOS branches, and the Canadian Centre for Cyber Security and Poland's CERT both issued their own advisories on top of CISA's. Teams that got this right already patch network gear — routers, switches, VPN boxes — on the same clock as servers, instead of treating them as set-and-forget hardware in a closet.

Through-line: whether it's a cloud agent or a router in a rack, this week's lesson is the same — patch management doesn't stop at the server, and a "narrow" permission is only as narrow as someone has actually tested it to be.
