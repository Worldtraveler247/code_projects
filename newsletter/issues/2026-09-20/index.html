Current Events

The Kubernetes API Server Privilege Escalation (CVE-2018-1002105)

In December 2018, the Kubernetes project shipped an emergency patch for a bug that let anyone on the internet, with zero credentials, become a full cluster administrator on almost any Kubernetes cluster running at the time. Here's how it actually happened.

Kubernetes runs a component called the API server, kube-apiserver, that sits in front of everything else in the cluster -- it's the single door every request goes through. Part of its job is proxying certain requests straight through to backend components, like a kubelet running on a worker node, so a user's normal exec or attach or port-forward command can reach that node. According to the Kubernetes project's own security advisory, when one of those proxied "upgrade" requests -- the kind used to open a long-lived streaming connection -- got an error back from the backend, kube-apiserver mishandled that error. Instead of closing the connection and re-checking authorization, it left the TCP connection open and reused it for the next set of requests, at the elevated privilege the API server itself holds internally.

Here's the chain. A user only needed permission to make one proxied request -- something as ordinary as pod exec, attach, or port-forward, which plenty of normal users have -- to open that connection. Once the backend returned an error on the upgrade attempt, the connection didn't close the way it should have. The next requests sent down that same still-open connection got treated as fully authenticated and authorized, at kube-apiserver's own privilege level, completely bypassing whatever narrower permission the user actually had. Researcher Darren Shepherd at Rancher found this in early November 2018 while digging into how Kubernetes handled a related networking setup, not because anyone was actively exploiting it in the wild.

Here's the root cause in one sentence: kube-apiserver treated a connection that had already been opened as still trustworthy after the backend rejected the request riding on it, because nothing re-validated authorization at that point.

I want to flag something honestly here. This wasn't a narrow bug in one feature -- Kubernetes' own advisory says it affected every version of Kubernetes since the project's 1.0 release, across all cloud providers and on-prem installs, and one attack path required no authentication at all. Reporting from Unit 42 and The Register at the time called it the most severe vulnerability found in Kubernetes up to that point, and nothing in the public record suggests anyone found evidence of it being exploited before the patch shipped.

Here's what held. The Kubernetes Product Security Committee ran a coordinated, embargoed disclosure -- fixing the bug quietly upstream first, then shipping patches for four separate release branches within days of Shepherd's report, so operators on older supported versions didn't have to do an emergency major-version upgrade just to get fixed.

Here's what a senior engineer, or a senior ISSO, would change in how they work because of this. Any component that proxies a request to a backend on a user's behalf has to treat that backend's response as the new source of truth for whether the connection stays open -- caching an authorization decision across multiple requests on a long-lived connection is exactly the pattern that broke here. In an RHEL 9 or Podman lab, that means testing your own reverse proxies and sidecars for the same assumption: does a failed backend response actually tear down the connection, or does something quietly let it ride?

What Held

  • A private, coordinated disclosure process caught this before attackers did. Shepherd reported to the Kubernetes Product Security Committee rather than posting publicly, and nothing in the public record indicates exploitation occurred before the patch shipped.
  • Patches landed across four release branches simultaneously, so clusters running any of the actively supported minor versions could patch in place rather than being forced into an emergency major-version upgrade under pressure.
  • The Kubernetes project's own advisory was direct about severity and scope — a 9.8 CVSS score and "affects all versions" — rather than downplaying it, which is what let downstream distributions and cloud providers move fast on their own patch cycles.

Senior Security Advice

Enforce DMARC at p=reject to Stop Email Spoofing

The Advice

Publish SPF and DKIM for every domain that sends mail, then move DMARC to a policy of p=reject so spoofed messages impersonating your domain get dropped before they ever reach an inbox.

Why It Matters

Without DMARC enforcement, anyone can send an email that says it's from your CEO, your IT help desk, or your own domain, and the recipient's mail server has no reliable way to tell the fake from the real thing. SPF and DKIM on their own only help if the receiving side checks them and acts on a failure - a domain that publishes SPF and DKIM but sets DMARC to p=none, or skips DMARC entirely, is still wide open to spoofing because nothing tells receiving mail servers what to do with a message that fails. This is exactly the gap behind business email compromise: an attacker spoofs a trusted internal or vendor address, asks for a wire transfer or a credential, and the message sails through because the domain never told anyone to reject it. It's serious enough that DHS ordered every federal executive branch agency to get there: Binding Operational Directive 18-01 required agencies to publish SPF, sign outbound mail with DKIM, and move DMARC to p=reject within a year, specifically to stop domain spoofing.

How to Implement It

  1. Publish an SPF record listing every server and third-party service authorized to send mail for the domain, including marketing tools and ticketing systems people forget about.
  2. Turn on DKIM signing for all outbound mail streams, not just the primary mail server - each sending service needs its own DKIM key.
  3. Publish a DMARC record starting at p=none with an aggregate-report address, so you can see who's sending mail as your domain before you block anything.
  4. Review the DMARC aggregate reports for a few weeks, fix or add SPF/DKIM entries for any legitimate sender that's failing, then move the policy to p=quarantine and finally p=reject.
  5. Verify the control is actually working: send a test message from an unauthorized source, confirm it's rejected, and keep monitoring DMARC reports monthly for new senders or a drop back to a weaker policy that someone quietly rolled back during an outage.

The Pushback You'll Hear

"We tried DMARC once and it broke a marketing tool's emails, so we backed it off to p=none." The senior-engineer rebuttal: that's what the monitoring phase is for, not a reason to stay unprotected. p=none collects reports without blocking anything - the fix is to find every legitimate sender in those reports, get SPF and DKIM correct for each one, and only then move to p=reject. Staying at p=none indefinitely means you built a smoke detector and never connected it to anything.

Senior Talk Tracks

Egress Cost as an Architecture Force

Let's talk about a cost line that quietly shapes how senior engineers design cloud systems, even though it never shows up in a system diagram: egress cost.

Plain English first. In AWS, and most clouds, moving data INTO a region is free. Moving data OUT to the public internet, or across to a different cloud provider, or sometimes even between regions of the same provider -- that's called egress, and it costs money, billed per gigabyte. It sounds like a small line item. It is not always a small line item.

Here's why that matters in production. A junior engineer designs a system the way a textbook diagram looks: pick the best database for the job, pick the best analytics tool for the job, pick the best CDN for the job, and wire them together, even if that means data has to hop between different providers or regions to get from one to the next. On paper, that's the "best" architecture. In practice, every one of those hops can be an egress charge, and at real production data volumes -- terabytes a day, not gigabytes -- those charges stop being background noise and start being a line item a VP asks about by name.

The senior take, the failure mode a junior usually misses: egress cost isn't just a budget problem, it's an architecture force, the same way gravity is a force on a building. It quietly pulls you toward keeping data and compute in the same place. A senior engineer will sometimes pick a "worse" individual tool -- a database that's slightly less convenient, a provider that's slightly less feature-rich -- specifically because it keeps data from crossing a paid boundary at high volume. That trade-off looks irrational until you've seen a bill.

Think of it like grocery shopping across state lines to save fifty cents on a gallon of milk, but not accounting for the cost of gas to get there. The "best price" on any single item can still be the wrong decision once you count what it costs to move the thing to where you actually need it.

A good way to open this at work: "Before we pick the 'best' service for this piece, have we mapped out what it costs every time data has to cross a network boundary to reach it?"

Key Takeaways

  1. Moving data into a cloud provider is typically free; moving it out, or across providers, is billed per gigabyte as "egress," and at production scale that adds up fast.
  2. Egress cost acts as an invisible architecture force that pulls systems toward keeping data and the compute that touches it in the same place, even when a "better" tool exists elsewhere.
  3. A senior engineer evaluates a new service by its total cost of data movement, not just its feature set — the best tool in isolation can be the wrong choice once egress is priced in.

Reader Question

"If a competing cloud service is genuinely better and cheaper per unit, why would a senior engineer ever choose the AWS-native option instead?"

Because "cheaper per unit" only tells you the price of the tool itself, not the price of getting your data to it and back. If that competing service lives outside AWS and the workload moves a large volume of data every day, the egress cost of shipping that data out — and often back in again — can erase the per-unit savings many times over, and it adds latency and a new failure point besides. I'd want the actual egress math run against our real data volumes before treating "better and cheaper per unit" as the whole answer, because at scale the network boundary itself is often the most expensive part of the decision, not the service.

Tech News

CISA just gave federal agencies two days to patch three Linux kernel bugs that are already being exploited — and if you run RHEL, Ubuntu, or any modern distro in production, this is your weekend homework. Three stories today: that Linux kernel KEV addition, a perfect-ten sandbox escape in a tool a lot of CI pipelines quietly depend on, and a Kubernetes-style control-plane flaw that lets one tenant impersonate a cluster admin.

Start with the kernel. On September 19th, CISA — the Cybersecurity and Infrastructure Security Agency — added three Linux kernel vulnerabilities to its Known Exploited Vulnerabilities catalog, all confirmed under active exploitation. CVE-2025-39682, CVSS nine-point-eight, is a flaw in the TLS receive path that can leak memory or crash the system. CVE-2026-53266, CVSS eight-point-eight, is an out-of-bounds write in the ebtables SNAT — Source Network Address Translation — ARP rewrite path, usable for local privilege escalation. And CVE-2025-39964 is a race condition in the AF_ALG socket interface that can corrupt cryptographic operations. Red Hat updated its advisories on all three at 2 AM UTC that same day to acknowledge exploitation, and federal agencies have until September 21st to patch. My take: three kernel bugs added to the same catalog on the same day means somebody is actively probing production Linux fleets right now — check your kernel version tonight, not Monday.

Next up, a bug in your build pipeline. CVE-2026-93603, a perfect CVSS ten, is a sandbox escape in vm2, a Node.js library a lot of teams use to run untrusted code — think CI runners, code-execution features, AI agent tooling. According to researchers at Endor Labs and VulnCheck, vm2 mishandles a nullish "this" receiver when sandboxed code calls a host function without a receiver — the sandbox ends up holding a live reference to the host's real global object, and from there it's a straight line to running arbitrary shell commands. The fix landed in vm2 3.12.1. My read: a sandbox is only as strong as its escape hatches, and this is the second wave of vm2 sandbox-escape CVEs this year — if your CI or agent tooling still shells out to vm2, that's not a "someday" ticket.

Which brings us to Kubernetes-adjacent infrastructure. CVE-2026-61682, CVSS nine-point-nine, hits kcp — an open-source, Kubernetes-API-style control plane used for multi-tenant workspaces. The front-proxy failed to strip inbound X-Remote-User and X-Remote-Group identity headers before forwarding requests to backend shards, so any authenticated tenant could inject "system:masters" into that header and get treated as a cluster administrator in any workspace on the shard — full read, write, and delete on secrets, RBAC data, and more. It's fixed in 0.31.4 and 0.32.2. My take: this is a textbook lesson in why you never trust a header your own front door didn't set — if you're running multi-tenant control planes, audit every proxy in front of them for exactly this.

All three stories point at the same gap: something inside the system — a kernel path, a sandbox boundary, a proxy header — was trusted to enforce a rule it was never actually enforcing.

Patch the kernel tonight if CISA's clock is running on your fleet, and go check whether anything in your stack still calls vm2 directly.
