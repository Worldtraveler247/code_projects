Current Events

NVIDIA Container Toolkit TOCTOU Escape

Here's an incident where the fix for a critical vulnerability turned out to be incomplete -- and the flaw was found by researchers, not attackers, which is exactly why nobody got hurt the first time around. Here's how it actually happened.

In September 2024, the cloud security firm Wiz Research was looking at NVIDIA's Container Toolkit -- the software that lets a container running on a GPU server actually reach the graphics card underneath it, which is the backbone for pretty much any containerized AI or machine-learning workload. Wiz found that, in its default configuration, the toolkit had a race-condition bug inside the step where it injects NVIDIA's own libraries into a new container -- a flaw known as a time-of-check to time-of-use issue, or TOCTOU.

Here's the mechanic. When the toolkit sets up a container, it checks a file path, and then, a moment later, mounts something at that same path. A malicious container image can exploit the gap between those two steps, using symlinks it controls, to swap what's actually sitting at that path in between the check and the mount. According to Wiz's own technical write-up, that swap tricks the toolkit into mounting the host's entire root filesystem straight into the container. And because Unix sockets stay writable even inside a filesystem that's mounted read-only, an attacker landing there could reach the host's container runtime socket directly and launch a brand-new, fully privileged container -- complete host takeover, rated nine point zero out of ten, critical severity.

Root cause, in one sentence: a default, non-hardened configuration path trusted that a file path checked once would still be the exact same file path by the time it was actually used, and nothing re-validated that assumption at the moment it mattered.

Here's what actually contained this. Wiz reported the flaw to NVIDIA privately on September first, 2024. NVIDIA shipped a patched version, one-sixteen-two, along with its own public security bulletin, just twenty-five days later, on September twenty-sixth. That's coordinated disclosure working exactly as designed -- a real flaw that, by Wiz's own estimate, touched over a third of cloud environments running GPU workloads, and it never got exploited in the wild before a fix existed. There was also an existing safer configuration path, called CDI, the Container Device Interface, that this bug never touched at all -- anyone already running that mode was unaffected by design, not by luck.

But be honest about the limit here too. Trend Micro's researchers found in 2025 that NVIDIA's original patch didn't fully close the hole -- a related code path could still trigger a similar escape. Responsible disclosure bought time to fix it quietly; it didn't guarantee the first fix was actually complete.

Here's what a senior engineer, or a senior ISSO, would change in how they work because of this. Don't trust a default configuration just because it's the default -- confirm which code path you're actually running. In a RHEL 9 lab with Podman, that means checking whether CDI mode is enabled for any GPU-enabled container deployment, and separately, treating any "checked once, used later" pattern in your own scripts -- file paths very much included -- as something to re-validate at the exact moment of use, never something you assume still holds.

What Held

  • Coordinated vulnerability disclosure worked as designed. Wiz reported privately on September 1; NVIDIA shipped a patch and a public bulletin twenty-five days later, on September 26 — fast enough that no confirmed in-the-wild exploitation occurred in that window.
  • An existing safer configuration path contained the blast radius for some users by design. CDI (Container Device Interface) mode never touched the vulnerable code path at all, so any environment already running it was unaffected without taking new action.
  • Be honest about the limit of both. Disclosure speed and an alternate safe path only helped organizations that patched promptly or had already adopted CDI — and Trend Micro's 2025 finding shows even "patched" was not fully true for everyone else. Naming both the win and its boundary is the senior move, not just citing the clean headline.

Senior Security Advice

Replace Flat VPN Access with Zero Trust Network Access

The Advice

Stop handing remote users a VPN tunnel into the whole corporate network — replace it with Zero Trust Network Access that grants identity- and device-verified access to one application at a time.

Why It Matters

A traditional VPN is an all-or-nothing door: once a user authenticates, they land inside the corporate network itself, with broad reachability to whatever that network segment can see. That design assumes anything inside the tunnel is trustworthy, which is exactly the assumption attackers exploit. A phished credential, a stolen laptop, or a compromised VPN appliance doesn't just expose one application — it hands the attacker a foothold on the internal network, free to scan for the next target. That's the incident class that keeps repeating: an attacker compromises one set of VPN credentials or one unpatched VPN gateway and uses that single entry point to move across systems the remote user never even needed to reach.

NIST Special Publication 800-207, the government's reference architecture for Zero Trust, lays out the fix directly: move away from static, network-based perimeters and evaluate every access request based on identity, device state, and context, rather than trusting a connection just because it's inside the network boundary. CISA's Zero Trust Maturity Model builds on that same foundation, organizing the shift around five pillars — identity, devices, networks, applications, and data — so access is brokered per resource instead of granted to an entire network segment.

How to Implement It

  1. Inventory which applications remote users actually need, and stand up an identity-aware proxy or ZTNA broker (examples include Cloudflare Access, Zscaler Private Access, or a cloud provider's equivalent) in front of each one instead of a network-wide VPN concentrator.
  2. Tie every access decision to identity and device posture together — a valid login from a non-compliant or unmanaged device should still be denied, not waved through because the password and MFA were correct.
  3. Grant access per application, not per network: a remote engineer who needs the deployment dashboard should never land on a network segment where the finance server is also reachable.
  4. Run the ZTNA broker alongside the legacy VPN during migration, moving one application group at a time, so you can compare access logs and catch anything that silently breaks before you decommission the old path.
  5. Verify the control is actually working, not just deployed: attempt access from a device you've deliberately made non-compliant or from an account scoped to a different application, and confirm the broker denies it and logs the denial — don't take "it's configured" as proof it enforces anything.

The Pushback You'll Hear

"Our VPN already requires MFA, so we're covered." The senior-engineer rebuttal: MFA proves who logged in, not what they can reach once they're in. A VPN with MFA is still a flat network behind the login screen — compromise that one authenticated session and you inherit everything the VPN exposes. ZTNA doesn't replace MFA, it removes the blast radius MFA alone can't touch, by never placing the user on the network in the first place.

Tech News

A cybersecurity nonprofit whose entire job is finding vulnerabilities just got breached — by what behaved less like a person at a keyboard and more like an autonomous AI agent making its own calls once it got inside. Here's why that matters: three big security stories this week share one root cause — AI agents are getting bolted onto production systems faster than teams are re-checking the authentication and sandboxing underneath them. Three stories: that AI-driven helpdesk breach, a perfect-ten flaw in Amazon's agent platform, and a sandbox escape in GitLab's AI Gateway.

Start with Zammad, open-source helpdesk software plenty of IT teams run. According to the Dutch Institute for Vulnerability Disclosure, or DIVD, an attacker breached its own Zammad system on September twenty-first by chaining two zero-days: a session-fixation bug that hijacked a live login to run code as Zammad's service account, then a second flaw that escalated straight to root. DIVD says the intrusion's speed looked autonomous, not human. CISA, the Cybersecurity and Infrastructure Security Agency, added both to its Known Exploited Vulnerabilities catalog on October second, fix-by date this Monday. Zammad patched in version seven-point-two. My read: AI attacker or not, the bug is old and boring — broken session handling. If something exploits that in seconds, your detection window just shrank.

Next up, Amazon. According to AWS's own security bulletins, published October second, the company fixed four flaws across Loom, its AI-agent orchestration platform, and SageMaker, its machine-learning workspace. The worst, CVE-2026-103956, scores a perfect ten: with no identity provider configured, any client on the network gets full administrator control of the agent control plane, no credentials required. My take: identity and access management can't be a setting you remember later. A platform secure only if every customer configures it right isn't security — it's hope.

Turning to GitLab. The company patched CVE-2026-90970, rated nine point nine out of ten, in the AI Gateway behind its Duo coding assistant. An authenticated user could craft a malicious configuration, escape the sandbox meant to contain AI prompt templates, and run commands on a system holding signing keys and AI-provider credentials. CISA reports no confirmed exploitation yet, so this one's prevention, not cleanup. My take: a sandbox only works if nothing inside can reach outside it, and a credential-holding gateway is exactly the blast radius that turns one account into a company-wide compromise.

Three vendors, one pattern: shipping AI agents faster than re-verifying the authentication and isolation basics underneath them.
