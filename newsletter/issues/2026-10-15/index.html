Current Events

Leaky Vessels (runc/BuildKit Container Escapes)

Picture a container -- the thing that's supposed to be a sealed box, isolated from the host machine it's running on -- and now picture that box having a tiny crack in its wall that nobody noticed, because the crack wasn't in the box itself. It was in the tool that builds and runs the box in the first place. That's Leaky Vessels, a set of container escape flaws disclosed in early 2024, and the most serious one sits in a piece of software almost every container on Earth depends on without most engineers ever knowing its name: runc. Here's how it actually worked.

runc is the low-level tool that actually creates and starts containers underneath Docker, Kubernetes, and basically every major container platform -- when you run a container, something eventually calls runc to do the real work of setting it up. Security researchers found that runc had an internal file-descriptor leak: a reference to a file or directory on the HOST system -- not inside the container -- that accidentally stayed open and reachable from inside the new container process. Normally a container can only see its own sealed-off filesystem. But if an attacker controlled the container image, or could run a command inside an existing container, they could reach through that leaked file descriptor and touch the host's actual filesystem -- in the worst case, overwriting a binary on the host itself. That's tracked as CVE-2024-21626, and three related flaws in BuildKit, the tool that builds container images, got their own CVE numbers for similar build-time breakout and file-deletion bugs.

Root cause, in one sentence: a container's entire security model depends on genuinely sealing it off from the host, and a small, internal plumbing mistake in the open-source tool doing that sealing was enough to put a crack in boxes most people assumed were solid everywhere at once.

Here's what held, and it's the reason this is remembered as a close call rather than a breach. The people who found it -- security researchers who privately reported it -- didn't post it to social media first. They coordinated with the runc maintainers and major cloud providers under embargo, so patches and updated managed-container services were largely ready before the technical details went public on January 31st, 2024. No major cloud provider or distribution reported in-the-wild exploitation before that disclosure. The fix shipped in runc 1.1.12.

So what does that mean for you? A senior engineer treats the container RUNTIME itself -- not just the application running inside the container -- as something with its own patch cycle and its own CVE history, because this incident proves that the sealed box you're trusting for isolation is only as sealed as the specific version of the tool that built it.

What Held

  • Coordinated, embargoed disclosure. The researchers who found Leaky Vessels reported it privately to runc and BuildKit maintainers and major cloud providers first, rather than publishing immediately. That gave vendors time to ship runc 1.1.12, BuildKit 0.12.5, and updated managed-container services largely in step with the public CVE disclosure on January 31, 2024.
  • No confirmed in-the-wild exploitation before the fix. Across the public reporting, no cloud provider or major distribution disclosed evidence of these specific flaws being exploited against real customers before patches were available — the kind of outcome embargoed disclosure is specifically meant to produce.
  • Say the limit of that out loud. "No confirmed exploitation reported" describes what vendors have publicly disclosed, not a guarantee that no one, anywhere, ever tried — naming that distinction, rather than calling the response a clean win, is the senior move.

Senior Security Advice

Eliminate Default Credentials Before Production

The Advice

Change or remove every default, vendor-supplied credential — on routers, IoT devices, databases, admin consoles, and cloud images — before that device or account ever touches a production network.

Why It Matters

Default credentials are not a secret. Vendor manuals, support forums, and public credential lists all document the factory admin password for a given router, camera, or appliance model. An attacker does not need to guess or crack anything; they just try the documented default against every device they can reach. That is the exact mechanism behind the large IoT botnets that have conscripted hundreds of thousands of internet-connected devices simply by scanning for ones still running their factory password. It is also the pattern CISA called out when it warned that threat actors, including nation-state-linked groups, had compromised operational technology at U.S. critical infrastructure sites by targeting devices left on default credentials. Without this control, a single unboxed device or a quietly reset admin account becomes a standing, fully "authorized" door into the network — no exploit required.

How to Implement It

  1. Make "no default credentials" a blocking gate in device and account provisioning: nothing joins the network, or goes into the asset inventory as production-ready, until its default authenticator has been replaced.
  2. Generate a unique credential or certificate-based identity per device or account at setup time. Never let one shared factory password cover an entire fleet of the same model.
  3. For appliances and IoT gear that ship with a default login, force a mandatory change-on-first-use flow and keep the device off the network until that change is confirmed.
  4. Run recurring scans of your own asset inventory using published vendor default-credential lists, and treat any successful login with a default as a security incident, not a configuration finding to file away.
  5. Verify the control is actually working: pull a sample of production devices and accounts and attempt to log in with the vendor's documented defaults yourself. Every attempt should fail. A clean scan report with no spot-check behind it only tells you the scanner looked — not that the credential is really gone.

The Pushback You'll Hear

"This device sits on our internal network, not the internet, so the default password isn't a real risk." A senior engineer's answer: most intrusions don't start at the internet edge — they start with one compromised laptop, one phished user, or one exposed internal service, and from there the attacker moves laterally looking for exactly this kind of easy win. A default credential on an internal device is the resource that turns a small foothold into full control of that system. Network segmentation is a separate, complementary control; it's not a substitute for removing the credential itself.

Tech News

If you've got Windows anywhere in your environment, or an Ivanti Connect Secure box handling remote access, the US government just told you — officially — that attackers are already walking through doors just like yours. Two stories tonight, and they landed in the same federal alert on the same day: a Windows flaw and an Ivanti VPN flaw, both now confirmed under active attack.

Start with Windows. According to CISA's own alert, published October 13th, the agency added CVE-2026-96951 — a command injection vulnerability in Microsoft Windows — to its Known Exploited Vulnerabilities catalog. That catalog isn't a guess list. CISA only adds a CVE to it when the agency has direct evidence that attackers are exploiting it right now, not just that it's theoretically dangerous. Command injection means an attacker smuggles their own operating-system commands into a process that was only ever supposed to accept narrow, specific input, and the system runs them as if it had typed them itself. Federal civilian agencies now have a hard patch deadline on the books. My read: once something clears the bar for that catalog, it stops being a "get to it this sprint" item. It's a "this is being used against real networks today" item, and your own patch cadence should move at the same speed CISA's deadline does, clearance or no clearance.

Next up, Ivanti. According to that same CISA alert, the agency also added CVE-2026-104935 — an authentication bypass in Ivanti Connect Secure — on the same day. Ivanti Connect Secure is remote-access VPN infrastructure, the kind of appliance that lets employees log into their desktops from outside the building, and it's used widely across government and defense-adjacent networks specifically because of that job. An authentication bypass means an attacker reaches whatever sits behind that login screen without ever producing valid credentials — no password guess, no stolen token, just a flaw that skips the check entirely. Ivanti's product line has a well-documented history of being targeted precisely because it's remote-access infrastructure: compromise the VPN appliance, and you're not attacking one account, you're attacking the front door everyone uses. My take: any authentication bypass in your remote-access layer jumps to the front of the patch queue, full stop — the blast radius isn't one user's credentials, it's everyone who authenticates through that box.

Same thread both stories tonight: CISA doesn't add a CVE to that catalog on a hunch. Confirmed active exploitation is the bar, and once a flaw clears it, the clock you're racing against isn't your own change-management calendar anymore — it's the attacker's.
