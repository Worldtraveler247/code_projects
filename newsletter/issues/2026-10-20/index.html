Current Events

The AWS US-EAST-1 DynamoDB DNS Outage

In October 2025, a single incorrect DNS record -- for one regional endpoint of one AWS database service -- took down a meaningful share of the internet for most of a day. No attacker, no outage at a data center, just automation racing against itself. Here's how it actually happened.

Amazon DynamoDB is a managed database service, and in AWS's largest region, US-EAST-1, its regional endpoint depends on an internal system that automatically creates and updates the DNS records clients use to find it. According to AWS's own published summary of the event, that automation has multiple redundant DNS Enactors working in parallel for reliability. On October 19th, a race condition between two of those Enactors caused one of them to apply a stale, outdated plan while a newer one was being deployed -- and a separate automated cleanup process then deleted the IP addresses the stale plan depended on, leaving the regional endpoint's own DNS record empty.

Here's the mechanism that turned one bad DNS record into a cascading outage. With an empty DNS record, DynamoDB API calls in US-EAST-1 started failing around 11:48 PM Pacific time. Because so many other AWS services internally depend on DynamoDB, and because EC2's own instance-launch subsystem depends on DynamoDB too, the failure didn't stay contained. Once the DNS record was manually repaired, EC2's instance-launch pipeline came back under a flood of retrying requests that had been queuing the whole time, and separately, AWS's own Network Load Balancers began failing health checks and dropping connections for several more hours, because their health-checking system had also been affected.

Root cause, in one sentence: a redundancy mechanism built to prevent a single point of failure -- multiple DNS Enactors running in parallel -- instead created a race condition between its own redundant parts, and nothing caught the resulting empty DNS record before it went live.

What contained it, and this is the senior detail worth naming: the DNS fix itself was fast, repaired within roughly three hours of the first alarms. What took the other twelve-plus hours wasn't the original bug -- it was the secondary congestion from every dependent system retrying at once the moment service came back. AWS has since said it's adding safeguards against this exact DNS race condition and against retry storms overwhelming recovery.

So what does that mean for you? A senior engineer treats a system's own internal automation -- the stuff meant to make things more reliable -- as something that needs its own tested failure mode, not a black box assumed safe because it's redundant. And a senior engineer builds retry logic with exponential backoff and jitter by default, because this incident is a textbook case of a recovering system getting re-broken by its own dependents all retrying at the exact same instant -- something worth actually reproducing on a small scale in a Podman lab, not just reading about.

What Held

  • The core DNS fix was fast. Once identified, AWS engineers repaired the empty DNS record in roughly three hours — the original fault itself wasn't a prolonged mystery.
  • AWS published a detailed public accounting. AWS's own post-event summary gives a specific, named root cause (the DNS Enactor race condition) rather than a vague description, which is exactly the kind of primary-source detail that lets outside engineers actually learn from the event instead of only hearing that it happened.
  • Say the limit of that out loud. A fast root-cause fix did not mean a fast full recovery — the retry-storm secondary effects ran for roughly twelve more hours after the DNS record itself was already correct. Naming that gap, rather than treating "root cause fixed" as "incident over," is the senior move.

Senior Security Advice

Require IMDSv2 on Every EC2 Instance

The Advice

Require IMDSv2 (Instance Metadata Service Version 2) on every EC2 instance, so a single server-side request forgery bug in your application can't be used to steal your cloud credentials.

Why It Matters

Every EC2 instance with an IAM role can ask a special internal address, 169.254.169.254, for temporary AWS credentials. Under the original metadata service, IMDSv1, that's a plain GET request: no token, no proof the caller is trusted. If your application has a server-side request forgery flaw — a bug that lets an attacker trick your server into making a web request on their behalf — they can point that request at the metadata address and walk out with your instance's live IAM credentials. From there they can read your databases, pull data from your storage buckets, or spin up resources under your account, all using an identity your own infrastructure handed them. This is the exact technique behind one of the best-known cloud breaches on record: an attacker exploited a server-side request forgery flaw in a public-facing application to reach the EC2 metadata service, pulled the IAM role's temporary credentials, and used them to exfiltrate a large volume of customer data from cloud storage. IMDSv2 closes that path by requiring a session token, fetched with a PUT request first, before any metadata can be read — and most simple server-side request forgery bugs can only force a GET, so they hit a locked door instead of an open one.

How to Implement It

  1. Inventory current exposure: query every instance's MetadataOptions.HttpTokens setting, or use the AWS Config managed rule ec2-imdsv2-check, to find instances still allowing IMDSv1.
  2. Before flipping the switch, check the MetadataNoToken CloudWatch metric per instance for a few weeks to confirm nothing is still calling the metadata service without a token — that catches legacy agents or old SDK versions before they break.
  3. Enforce it with aws ec2 modify-instance-metadata-options --http-tokens required --http-endpoint enabled on existing instances, and set the account-level default with modify-instance-metadata-defaults so every new instance and launch template inherits "required" automatically.
  4. For containerized workloads proxying metadata calls through an extra hop (ECS or EKS on EC2), raise HttpPutResponseHopLimit just enough to cover that hop — don't leave it wide open.
  5. Verify the control is working, not just configured: confirm MetadataNoToken stays at zero after enforcement, and check that your CIS AWS Foundations Benchmark results in Security Hub show the IMDSv2 control passing across every account, not just the one you tested.

The Pushback You'll Hear

"This will break old scripts and agents that still use IMDSv1." The senior-engineer rebuttal: that's exactly what the MetadataNoToken metric is for — find those callers before you enforce anything, not after. Every current version of the AWS SDK and CLI already defaults to IMDSv2 on its own, so in practice the list of real holdouts is usually short: a handful of old agents or custom scripts worth fixing anyway. A short, targeted migration window costs you a few tickets. A server-side request forgery bug against an instance still running IMDSv1 costs you your IAM role's credentials and everything they can touch.

Tech News

A single crafted email attachment can now hand an attacker root access on a Cisco security appliance — no login, no credentials, nothing. That's tonight's lead. Two stories: a mail gateway flaw with no workaround at all, and a kernel bug that lets one cloud customer peek into another customer's memory.

Start with Cisco. According to Cisco's own security advisory, confirmed by SecurityWeek and TechNadu, an unauthenticated attacker can send a single email with a crafted attachment through Cisco Secure Email Gateway and get arbitrary file writes and root-level command execution on the appliance itself. It's tracked as CVE-2026-76519, rated 9.8 out of 10, and Cisco's own PSIRT team confirmed active exploitation this month. CISA added it to the Known Exploited Vulnerabilities catalog on October 14th with a federal patch deadline of October 17th. Here's the detail that should worry you most: Cisco says there is no workaround. Disabling the feature doesn't help — you have to actually upgrade to a fixed build. My read: an email gateway's entire job is opening other people's attachments, so when the attachment-scanning engine itself becomes the way in, that's the one layer in your defense-in-depth stack that was never supposed to fail — which makes this a same-week, not same-quarter, patch.

Turning to a different kind of boundary failure. According to The Hacker News, researchers disclosed a Linux kernel flaw — being called PwnEscape — in the kernel's networking code that lets a process inside a guest virtual machine read memory belonging to the host underneath it. A researcher demonstrated the leak against Vercel's live cloud sandboxes, and Vercel confirmed it. Because the bug sits in shared kernel networking code and not in one provider's own setup, it's plausible other cloud and container platforms built on the same kernel code path carry the same exposure. My take: the entire promise of multi-tenant cloud computing is that the kernel boundary between your workload and your neighbor's actually holds — a bug that lets a guest read host memory is a direct hit on that promise, not a side issue.

Same thread both stories: defense-in-depth isn't a checklist you complete once — it's only as strong as the one layer everyone quietly assumed was a floor, not a wall.
