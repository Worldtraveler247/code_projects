Current Events

The containerd-shim Abstract Socket Escape

A socket that was never supposed to be reachable from inside a container turned out to be reachable from inside a container -- and on the other end of it was root access to the entire host. Here's how one abstract detail in Linux networking nearly undid container isolation for half the industry's container runtime.

In 2020, researcher Jeff Dileo at NCC Group was auditing containerd, the container runtime that sits underneath Docker, Kubernetes, and a long list of cloud platforms. He found that containerd's shim process -- the small helper that actually supervises each running container -- exposes a control API over a Unix domain socket. Nothing unusual there. The problem was which kind of Unix socket. containerd-shim used what's called an abstract socket, a Linux feature where the socket lives in a network namespace's own private naming table instead of on the filesystem. Abstract sockets don't check filesystem permissions at all. They're visible to any process sharing that same network namespace.

Here's the chain. Containers normally get their own private network namespace, so they can't see the host's abstract sockets, and this whole class of exposure never comes up. But a container started with host networking turned on -- in Docker that's the dash-dash-net-equals- host flag, in Kubernetes it's hostNetwork colon true -- shares the host's actual network namespace instead of getting its own. Any process inside that container can now see every abstract socket the host can see, including containerd-shim's control socket. The shim's only real check was whether the connecting process reported itself as UID zero. A process running as root inside that host-networked container passes that check instantly, and from there it can command the shim directly -- reaching code execution as root on the host itself, fully outside the container.

Root cause, in one sentence: a privileged control API was bound to a socket type whose exposure is governed by network-namespace sharing, not by any permission model that accounted for containers deliberately opting into that sharing.

What actually held: exploitation required two specific choices stacked together -- host networking turned on, and the container running as root -- so any container left on its own default, isolated network namespace, or running as a non-root user, was never reachable in the first place. containerd fixed it properly in versions 1.3.9 and 1.4.3 by changing how the shim's socket is exposed.

So what does this mean for a senior engineer's own environment? A senior engineer treats host networking as a flag that needs a specific, written justification every time it appears, not a convenience toggle -- and audits for containers running as root with that flag set together, because that exact combination is what turned an obscure socket detail into a full host compromise. On a Podman or Kubernetes lab, that means actually checking, not assuming, which workloads use host networking and whether any of them also run as root.

What Held

  • The exposure required two specific choices stacked together. Exploitation only worked for containers that both used host networking and ran as root — any container left on its own isolated network namespace, or running as a non-root user, never had a path to the shim's socket at all. That's least privilege and least functionality doing real work even before the patch existed.
  • containerd's own disclosure process worked as designed. NCC Group reported the flaw through the project's official security channel, and containerd shipped fixed releases (1.3.9, 1.4.3) rather than a silent or delayed patch.
  • Downstream distributions propagated the fix quickly. Arch Linux and other distributions logged their own advisories within days of the upstream fix, shortening the exposure window for anyone tracking patches.

Senior Security Advice

Enable S3 Block Public Access at the Account Level

The Advice

Turn on Amazon S3 Block Public Access at the AWS account level for every account you own, not just on individual buckets.

Why It Matters

An S3 bucket can be made public through a bucket policy, an object ACL, or an access point, and any one of those paths is enough to expose everything inside it to the open internet. Buckets get misconfigured constantly: someone widens a policy to unblock a legitimate integration, a template copied from an old project carries a public ACL forward, or a developer flips a setting to "just get it working" during a deploy and never flips it back. The incident class this produces is one of the most common sources of cloud data breaches over the last decade — researchers and attackers alike scan the internet for open buckets, and when they find one, whatever is inside, customer records, credentials, source code, backups, becomes available to anyone with the URL, with no login required. A bucket-by-bucket fix only protects the buckets someone remembered to fix. The account-level setting removes the exposure path entirely, for every current and future bucket, in one place.

How to Implement It

  1. Enable all four Block Public Access settings (block public ACLs, ignore public ACLs, block public bucket policies, restrict public buckets) at the account level in every AWS account, including new accounts created by automation, so the default state is "no bucket in this account can be made public."
  2. For AWS Organizations, apply an SCP or a centrally managed Block Public Access configuration across all member accounts, since CIS AWS Foundations Benchmark guidance treats this as an account-wide control, not a per-bucket opt-in.
  3. Where a specific bucket genuinely needs public content, such as static website assets, carve out that one bucket deliberately rather than leaving the account-wide setting off for everyone.
  4. Verify it's actually enforced, not just configured: run aws s3control get-public-access-block against the account, and separately check AWS Security Hub for the relevant S3 control (S3.1 / S3.8 in current benchmark mappings) to confirm it reports PASSED rather than relying on the console toggle alone.
  5. Test the control, don't just read it: attempt to apply a public bucket policy to a test bucket in that account and confirm S3 rejects it, which proves the setting is actively blocking changes, not just present in a configuration file.

The Pushback You'll Hear

"We have a bucket that needs to be public, so we can't turn this on for the whole account." The senior-engineer rebuttal: the account-level setting and bucket-level settings work together, not against each other. AWS's own documentation is explicit that the account-level control is the recommended baseline specifically because a bucket policy can be edited to turn off a bucket's own public-access settings, while the account-level setting still blocks that bucket from going public even if someone does. Leave the account-wide protection on and grant the narrow, intentional exception only on the one bucket that needs it.

Tech News

One compression library sits quietly inside Node.js, .NET, Python, and PowerShell — and this week it forced emergency patches across all four at once, even though none of those platforms share a codebase. If your stack touches any of those runtimes, tonight's lead story is for you. Two stories: a single open-source library forcing emergency patches across completely unrelated platforms, and a checkout page that quietly skimmed shopper card data for three days because nobody was watching a script nobody remembered installing.

Start with the library. According to Node.js's own security disclosure, corroborated by Help Net Security, SecurityWeek, and BleepingComputer, researchers publicly disclosed on October 21st a critical out-of-bounds write flaw in the decoder for Brotli, Google's widely used data-compression format. The bug, tracked as CVE-2026-111497, carries a near-maximum severity score, and it isn't contained to one ecosystem — Brotli's reference code gets copied, or "vendored," directly into Node.js, into Microsoft's .NET and PowerShell, and into multiple Python packages, so the same flaw showed up in products that otherwise have nothing to do with each other. Microsoft shipped an out-of-cycle emergency patch for .NET days after disclosure, according to BleepingComputer. Proof-of-concept exploits are already public on GitHub, and researchers have demonstrated working code execution against official Node.js container images — though as of now, no vendor has confirmed active exploitation in the wild. My read: when a vulnerability lives in a vendored dependency, patching your own application isn't enough — you have to know everywhere that copied code actually ended up, which is exactly what a software bill of materials is supposed to answer and exactly what most teams don't actually have.

Next up, turning to e-commerce. According to the security research firm Sansec, corroborated by BleepingComputer, attackers linked to a Magecart card-skimming group compromised Convertr, an analytics script used across dozens of fashion retailers' checkout pages in Brazil. Sansec says the script ran on an outdated, unpatched build of the open-source tool Plausible, and the skimmer quietly adjusted itself within two days to match Convertr's exact checkout fields. Shoppers who paid by card from October 24th until Convertr removed the malicious code on the morning of the 27th may have had their card data copied. My take: this is the same lesson as tonight's first story wearing a different costume — a third-party script you didn't write, sitting on infrastructure you don't directly watch, still runs with full access to your customers' data the moment it loads.

Tonight's thread: whether it's a compression library or an analytics script, the code you didn't write is still code you're responsible for.
