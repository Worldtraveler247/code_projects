Current Events

Salesloft Drift OAuth Token Breach

Here's how a single stolen login at a marketing-tech vendor turned into a data breach at more than seven hundred companies — without the attackers ever touching those companies' own networks. This is the Salesloft Drift OAuth token breach, and it's one of the cleanest lessons in why trusting a vendor's access token is the same as trusting the vendor's entire security program.

Salesloft makes a sales-engagement tool called Drift, and Drift connects to customers' Salesforce instances through OAuth — a standard way for one application to access another on a user's behalf, without ever handling that user's password directly. Sometime between roughly March and June of 2025 — reporting differs on the exact entry point here — attackers compromised Salesloft's GitHub account. From there, they pivoted into Salesloft's AWS environment, where Drift's integration credentials lived. By early-to-mid August, a group tracked as UNC6395 had stolen OAuth and refresh tokens tied to the Drift-to-Salesforce integration — and, Google later disclosed, tokens tied to a separate Drift email integration too.

Here's the part that makes this a blast-radius story, not just a vendor-breach story: those tokens worked directly against customer Salesforce instances. No phishing email to the customer. No password to crack. The attacker simply replayed a stolen, valid token, and Salesforce let them in, because from Salesforce's point of view that token was Drift, and Drift was authorized. Between roughly August 8th and 18th, the group queried and exfiltrated data — cases, accounts, users, support tickets — across more than seven hundred downstream organizations, among them Cloudflare, Palo Alto Networks, and Zscaler.

Salesloft disclosed the issue on August 20th and revoked every active Drift token; Google's Threat Intelligence Group published the technical write-up on August 26th; and by August 28th, Google had found its own Workspace accounts touched through the email-integration tokens, and told everyone to treat all Drift-connected tokens as burned. The FBI and the Internet Crime Complaint Center followed with a joint advisory on September 12th.

The root cause: long-lived, broadly scoped OAuth tokens that nobody was watching for anomalous use. A single vendor compromise became a multi-tenant breach because the trust those tokens carried was standing and unmonitored.

What actually contained this was fast, public token revocation — inside about two days of detection — and Google's decision to publish the technical detail openly, which let hundreds of downstream victims self-audit instead of waiting to be told. Several victims, including Cloudflare and Palo Alto Networks, published their own transparent postmortems. That's the senior move here: naming the controls that worked is just as valuable in an interview as naming what failed.

For a senior Linux sysadmin or ISSO, the lesson a junior engineer misses is this: a vendor integration token is not a lower-risk credential just because a human never typed it. It needs the same lifecycle discipline as any other credential — short lifetimes, scoped permissions, monitoring for anomalous use. A senior engineer takes that lesson into the lab, not just the interview: standing up a test identity provider and checking the default access-token lifetime before trusting any integration in production — the same action in today's lab verification below.

Control Failures

Failure NIST SP 800-53 Rev 5 Control Family
Long-lived, broadly scoped OAuth tokens with no expiration/rotation enforcement IA-5 (Authenticator Management)
No anomaly detection on token usage patterns across customer tenants AU-6 (Audit Record Review, Analysis, and Reporting)
Vendor's source-code repository (GitHub) compromised, opening a path to production credentials AC-6 (Least Privilege) / SC-7 (Boundary Protection)
Standing trust granted to a third-party integration without continuous verification SA-9 (External System Services)
No scoping to limit a single integration's reach across unrelated customer data fields AC-6 (Least Privilege)

What Held

Fast, coordinated token revocation across Salesloft and Salesforce within roughly two days of detection cut off the active campaign before further expansion. Google's decision to publish full technical detail — rather than a vague advisory — let over 700 downstream organizations self-audit their own logs immediately instead of waiting for individual notification. Victim organizations including Cloudflare and Palo Alto Networks ran their own transparent postmortems and rotated every credential that had touched the Drift integration, treating the compromise as total rather than partial. Naming these controls — rapid revocation, public disclosure, "assume full compromise" rotation — as what worked signals defense-in-depth thinking in an interview, not just headline recall.

Senior Security Advice

Scan Container Images for Vulnerabilities Before They Reach Production

The Advice

Scan every container image for known vulnerabilities at build time, in the registry, and again before deployment, and block the pipeline when a scan finds a critical flaw.

Why It Matters

A container image is a frozen snapshot of an operating system, a runtime, and every library the application depends on. If any layer ships with a known vulnerability, that flaw rides into production inside every container built from it, often without anyone looking at the base layer again. Images get pulled from public registries and rebuilt from cached layers for months, so a vulnerability patched upstream a year ago can still be running today simply because nobody rescanned it. This is the well-documented incident class behind container compromises: attackers do not need a zero-day when a public base image carries an old, unpatched library with a public exploit already written for it. Scanning catches that before the image ever runs, when fixing it means rebuilding, not responding to an incident.

How to Implement It

  1. Add a container-aware scanner (Trivy, Grype, Snyk Container, or Docker Scout) to the CI pipeline so every image is checked for known CVEs the moment it is built.
  2. Set a policy gate, not just a report: fail the build on critical and high-severity findings, so a vulnerable image cannot be pushed to the registry.
  3. Scan the registry itself on a recurring schedule, since a new CVE can be disclosed against a library already sitting in a stored image.
  4. Pin and minimize base images (distroless or slim variants) so there is less surface to scan and less to patch.
  5. Verify the control works: build a test image with a library known to carry a published CVE and confirm the pipeline blocks it, with both the alert and the block visible in the pipeline logs.

The Pushback You'll Hear

"Scanning slows down every build over vulnerabilities nobody will exploit." The senior response: a scan in CI adds seconds to a build that was running anyway, and a blocked build is a five-minute rebuild with a patched base image, not a multi-day incident response. NIST's own container security guidance says image vulnerabilities should be caught by purpose-built scanning tools wired into the pipeline, because catching them before deployment is far cheaper than after. Skipping this doesn't avoid the slowdown, it just moves it to whenever that old CVE gets used against you.

Senior Talk Tracks

ConfigMaps vs Secrets

If you've ever stored a database password in a Kubernetes Secret and felt safe because it wasn't a ConfigMap, I need to walk you back from that. Here's what you need to know: a Kubernetes Secret is not encrypted by default. It's base64-encoded — that's just a text format, not encryption — and anyone can reverse it in about two seconds.

So what's actually going on? Kubernetes gives you two similar-looking objects: a ConfigMap, for non-sensitive configuration, and a Secret, for sensitive values like passwords and API keys. They look almost identical in how you create and mount them. But under the hood, by default, both are stored the same way inside etcd — the cluster's backing database — in effectively plain text, unless you've explicitly turned on encryption at rest. And if anyone on your team has permission to run "get" or "list" on secrets in that namespace, they can read every one of them, no extra barrier required.

Here's the senior take: the failure mode isn't a hacker breaking in through some exotic exploit. It's an engineer who assumes the object type alone is the security control. Secrets leak constructively all the time — through a pod's environment variables showing up in a crash dump, through "kubectl describe," through a process-inspection tool. A senior engineer's response is to turn on etcd encryption at rest, scope role-based access control tightly so only the pods and people that truly need a secret can read it, mount secrets as files instead of environment variables wherever possible, and often skip the built-in Secret object entirely in favor of an external secrets manager that Kubernetes just references.

Think of it like a locked drawer with a label that says "valuables" sitting in an unlocked office. The label tells you what's supposed to be protected — it doesn't actually protect it. The lock is a separate thing you have to add.

Here's a line you could open with at work: "Hey, are we actually encrypting secrets at rest in that cluster, or just trusting the object name?"

Key Takeaways

  1. A Kubernetes Secret is base64-encoded, not encrypted — encoding and encryption are not the same thing.
  2. Without etcd encryption at rest explicitly enabled, Secrets sit in the cluster database in effectively plain text.
  3. Mounting secrets as files instead of environment variables, and scoping RBAC tightly, does more for real security than the object type ever will.
