Current Events

The Shai-Hulud npm Supply Chain Worm

Here's an incident that shows what happens when stealing one password doesn't just compromise one account -- it reprograms a worm to go steal more. Here's how it actually happened.

In mid-September 2025, researchers discovered malicious code hidden inside tinycolor, a popular JavaScript color-manipulation package downloaded millions of times a month through npm, the world's largest JavaScript package registry. According to GitHub's own account and the GitLab Advisory Database, that package was altered on September fourteenth by someone who had gained control of a legitimate maintainer's publishing access. Within days, researchers were calling the payload "Shai-Hulud" -- a self-replicating worm, named after the giant sandworm in the novel Dune.

Here's the mechanic. Every time a developer or a build server ran "npm install" on an infected package, npm automatically executed a hidden postinstall script bundled inside it -- no approval step, no sandbox, just code running with whatever privileges that install already had. That script quietly ran a repackaged copy of TruffleHog, a legitimate open-source secret scanner, to hunt the local filesystem and environment variables for npm publishing tokens, GitHub personal access tokens, and cloud API keys for Amazon Web Services, Google Cloud, and Microsoft Azure. Whatever it found was uploaded, using the victim's own stolen GitHub token, to a new public repository the malware itself created and named, fittingly, "Shai-Hulud." Then, if it had found a valid npm publish token, the worm used it immediately to push trojanized versions of every other package that same maintainer could publish -- turning one compromised developer into the next infection point, automatically, with no attacker even watching.

Root cause, in one sentence: npm's install process runs arbitrary maintainer-supplied code with full local privileges by default, so one stolen publishing credential wasn't just a leaked password -- it was a working key to re-arm the worm against the next maintainer's packages.

Here's what actually contained this. GitHub has stated it removed more than five hundred compromised packages from the registry and blocked re-uploads matching known indicators of compromise within roughly a day of being notified. Independent researchers, including Semgrep and the maintainers of the GitLab Advisory Database, published technical indicators just as fast, letting defenders elsewhere block the worm before it reached them. On September twenty-third, the Cybersecurity and Infrastructure Security Agency issued its own alert, turning "maybe rotate your tokens" into a direct instruction to rotate every developer credential immediately.

Be honest about the limit here. None of that un-exfiltrated the secrets already stolen before detection, and the actual structural fix -- GitHub requiring two-factor authentication for local publishing and moving toward short-lived, identity-based trusted publishing instead of long-lived tokens -- did not ship until mid-December, three months later.

Here's what a senior engineer would change in how they work because of this. Never let a package install run unreviewed code against a real credential store by default. In a RHEL 9 or Podman lab, that means running npm install with the ignore-scripts flag as the default posture for any build or CI environment, and separately testing that a postinstall script still executes, and can still read environment secrets, the moment that flag is left off.

What Held

  • GitHub's rapid takedown. GitHub states it removed more than 500 compromised packages and blocked re-uploads matching known indicators of compromise within roughly a day of being notified on September 14.
  • Fast, public, independent disclosure. Semgrep and the GitLab Advisory Database published technical indicators of compromise within a day of the first malicious publish, letting defenders elsewhere block the worm before their own environments were hit.
  • A same-week federal alert. CISA's September 23 alert turned an ecosystem-specific advisory into a direct, government-level instruction to rotate every developer credential immediately — not just for npm users, but for anyone touching the same token types.
  • Be honest about the limit of all three. None of this un-exfiltrated secrets already stolen before detection on September 14-15, and the structural fix that removes the enabling condition — mandatory 2FA for local publishing and a move away from long-lived tokens — did not ship until December 15, three months after the worm was first found. Containment and root-cause remediation happened on very different timelines, and naming that gap is the senior move.

Senior Security Advice

Run Periodic Access Reviews and Disable Dormant Accounts

The Advice

Review every user's access on a fixed schedule and disable any account that has gone quiet, so privilege that no one still needs cannot sit there waiting to be abused.

Why It Matters

Access rarely gets removed on its own. People change teams, finish projects, take leave, or leave the company, and the permissions they picked up along the way keep working long after the reason for them is gone. That buildup is called access creep, and it does two kinds of damage: it hands an attacker who compromises any one of those accounts a bigger blast radius than the person's current job would ever justify, and it leaves dormant, forgotten accounts sitting around as an easy, low-noise target, since nobody notices if a login that hasn't been used in months suddenly gets used again. Insider-threat and breach investigations repeatedly turn up the same root cause: a former employee's account, or a side permission nobody remembered granting, that was never switched off.

How to Implement It

  1. Build a current account inventory first, covering every system, not just the identity provider - CIS Controls v8 Safeguard 5.1 treats this inventory as the prerequisite for everything else on this list.
  2. Set an organization-defined review cadence in writing (quarterly is a common baseline) and run it against that inventory, checking each account's access against what its owner's current role actually requires - this is the review NIST SP 800-53's AC-2 account-management control calls for.
  3. Automatically flag and disable dormant accounts - CIS Safeguard 5.3 sets 45 days of inactivity as its baseline threshold, and most identity platforms can enforce that on a timer without a human chasing it down.
  4. Route every finding through a named approver per account, not a blanket "looks fine" sign-off, and track each one to a closed ticket: access removed, or access justified and documented.
  5. Verify the control is actually working: pull a last-activity report at the end of each cycle and confirm the dormant-account count went to near zero, then spot-check a handful of "reviewed and kept" accounts to confirm the stated justification still matches what the account can actually touch.

The Pushback You'll Hear

"We just did a review last quarter, this is redundant." The senior-engineer rebuttal: access creep starts again the moment the review ends, because role changes and offboarding keep happening in between cycles. The review isn't a one-time cleanup, it's a recurring control precisely because the thing it's checking for never stops accumulating.

Tech News

A Danish technical university just told as many as 200,000 current and former students and staff that attackers got into the very system built to manage who's allowed to log in — and they didn't need a zero-day to do it, just a working set of stolen credentials. If identity and access management is anywhere near your job description, that sentence alone should bother you. Two stories today: that university's identity-system breach, and Google's October Android security bulletin, which landed with a flaw that needs zero clicks to work.

Let's start in Denmark. According to the Technical University of Denmark's own breach notification, attackers used compromised login credentials to get into DTUBasen — the identity and access management system, or IAM system, that holds records on the university's current and former users. DTU says the database covers close to 40,000 active accounts and roughly 160,000 former ones, and the university still can't say exactly what was downloaded. Sitting inside it: Danish CPR numbers — the civil registration number every resident carries for life — full names, home addresses, and for a lot of people, next-of-kin details too. DTU has reported the incident to Denmark's data protection authority and is notifying affected people directly. My read: an identity and access management system isn't just another app on the network — it's the directory every other system trusts to say who's real. When that one system gets walked into with stolen-but-valid credentials, you're not looking at one breach, you're looking at every downstream system that trusted its word. Segmenting admin access to the IAM layer itself, and alerting on any login pattern that system has never seen before, belongs higher on the priority list than almost anything else you manage.

Next up, Google. The October Android security bulletin, published October 5th, patches a couple dozen vulnerabilities, and the headline one is critical: a flaw in the System component that lets an attacker escalate straight to full local privileges, with no extra starting access and zero user interaction required. My take: "zero user interaction" is the detail that should change your priority order. A well-trained user who never clicks a bad link doesn't help you here — the only real control is getting the patch pushed before anyone pairs this with a way to reach the device remotely. If you manage a mobile fleet for a client or an agency, patch compliance on this one belongs at the top of next week's dashboard, not buried in a monthly summary.

Different systems, same lesson: a login or a device being "legitimate" always needs a second check behind it, because both of today's stories show what happens the moment that second check is missing or too slow.
