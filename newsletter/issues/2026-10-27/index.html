Current Events

The Rogers Communications Nationwide Outage

One mistake, inside one routine network change, took down phone and internet service for roughly half of Canada's population for most of a day - cutting off access to 911 in parts of the country. No attacker. No malware. Just a configuration change that went wrong, and a network that had no way to stop it from spreading. Here's how it actually happened.

Rogers Communications is one of Canada's largest telecom providers. According to the executive summary of the independent review the CRTC, Canada's telecom regulator, commissioned from Xona Partners, the outage on July 8th, 2022, traces back to a configuration change inside Rogers' own IP core network. Staff removed an access control list filter from the distribution routers as part of a planned network update.

Here's the chain, step by step. The moment that filter came out, it let a flood of internal routing data pour into Rogers' core routers - exactly the kind of traffic that filter had been quietly blocking. The review found the core routers were never configured with overload protection mechanisms that could have absorbed or throttled that flood. Without that safeguard, the core routers crashed within minutes of the filter's removal. And once the core crashed, there was nothing left underneath the rest of the network holding it up - voice, data, and even Rogers' own internal diagnostic access went down with it.

Root cause, in one sentence: a single change-management step removed a safeguard that the network's core hardware had no independent backup for, and nothing in the change process caught that gap before it shipped.

What actually dragged this out, and this is the detail worth sitting with: Rogers' own staff couldn't reach the system's error logs for roughly fourteen hours after the crash, because the very network they needed to use to diagnose the problem was the network that had just gone down. Multiple other configuration changes were already in flight that same day, which further confused the diagnosis. The review found Rogers had since implemented the recommended fixes and judged the remediation satisfactory - but that's two years of safeguards built after the fact, not before it.

So what does that mean for the kind of system a senior engineer is responsible for? A senior engineer never treats a change window as a formality - every change to a core routing or access-control component gets a peer review and a rollback plan before it runs, and critical infrastructure gets independent, out-of-band access for diagnostics, so losing the primary network doesn't also cost you the ability to see what broke it. On an AWS or Kubernetes lab, that means practicing exactly that discipline: never applying a security-group or network- policy change to a shared environment without a documented peer review and a tested rollback step ready before you run it.

What Held

  • The regulator's oversight function worked as designed. The CRTC ordered a detailed explanation and commissioned an independent technical review rather than accepting Rogers' own account at face value — exactly the external verification function a regulator exists to provide, even though it took two years to reach the public in redacted form.
  • Remediation, once forced, was judged adequate. The CRTC's 2024 summary states Rogers implemented the review's recommended changes and found the steps taken to address the root cause satisfactory — a real, verified fix, even though it arrived only after a regulator required it.
  • Say the limit out loud. Nothing about this incident "held" during the outage itself — there was no internal safeguard, no segmentation, and no backup diagnostic path that limited the blast radius in the moment. Naming that plainly, rather than searching for a silver lining that wasn't there, is itself the senior-level move: some incidents teach you what containment looks like, and this one teaches you what its total absence looks like.

Senior Security Advice

Default-Deny Network Policies for Every Kubernetes Namespace

The Advice

Put a default-deny NetworkPolicy in every Kubernetes namespace, for both ingress and egress, then explicitly allow only the pod-to-pod traffic each workload actually needs.

Why It Matters

Kubernetes ships flat. Out of the box, every pod in a cluster can reach every other pod, in any namespace, with nothing in the network stopping it. NSA and CISA's joint Kubernetes Hardening Guidance calls this out directly: no network policies apply to pods or namespaces by default, so traffic stays unrestricted until an administrator changes that. That flat network turns one compromised container into a free pass to everything else running in the cluster. The incident class this stops is a familiar one: a single vulnerable workload — a web app with a code execution bug, a misconfigured sidecar, a poisoned dependency — gets popped, and because nothing on the network ever says no, the attacker pivots straight from that one pod to the database, the internal API, or the cluster's own control plane. The CIS Kubernetes Benchmark treats this as a baseline control, not an advanced one: it checks that every namespace has network policies defined, because a namespace with none leaves every pod in it open in both directions.

How to Implement It

  1. Map real traffic first. Before writing a single policy, inventory which services actually call which other services in each namespace — jumping straight to deny-all without this step breaks production the moment you flip it on.
  2. Confirm the cluster's CNI plugin (Calico, Cilium, or similar) actually enforces NetworkPolicy objects. A non-enforcing CNI makes every policy you write a no-op that only looks like protection.
  3. Apply a default-deny-all policy, ingress and egress, to every namespace as the baseline, then layer narrow allow rules on top for legitimate traffic. Remember that denying egress also blocks DNS lookups, so a specific allow rule for DNS on port 53 has to go in alongside the rest.
  4. Bake the baseline into namespace creation through GitOps or Helm/Kustomize templates, so no new namespace ever launches without it already in place.
  5. Verify it is actually enforced, not just applied: spin up a test pod in the namespace and try to reach a pod it should not be able to reach — confirm the connection hangs or is refused — and audit the whole cluster against the CIS benchmark control that checks for network policies in every namespace.

The Pushback You'll Hear

"We don't know every dependency well enough to deny-all without breaking something." The senior-engineer rebuttal: that uncertainty is the argument for mapping traffic and rolling out namespace by namespace, starting with anything internet-facing, not a reason to leave the whole cluster flat indefinitely. Incomplete visibility gets fixed by doing the mapping work, not by skipping the control until you magically have perfect knowledge of every call path.

Tech News

Session tokens, not passwords, are now the weak point in Microsoft 365 — and a campaign that's been running quietly since July just hit 79 organizations. If your team relies on multi-factor authentication to call the security problem solved, tonight's story is for you. Two stories: a session-hijacking campaign that proves MFA alone isn't the finish line, and an update on the PHP flaw I told you about last week.

Start with the Microsoft 365 campaign. According to security firm Huntress, attackers ran an adversary-in-the-middle operation — essentially a fake Microsoft sign-in page sitting invisibly between the victim and the real one — from mid-July through late September. Victims typed their real password and approved a real MFA prompt, and the attacker simply copied the session token that got issued afterward. Huntress calls the technique "token spraying," because once attackers have a working token, they replay it at scale across many organizations, the same logic as password spraying but one step past MFA. Across the campaign, Huntress counted 497 successful sign-ins out of more than 200,000 attempts, compromising 97 accounts at 79 organizations. In at least 19 of those organizations, the attackers moved fast to keep their access — removing the victim's existing MFA method and registering a new one within three hours, then quietly setting up inbox rules to hide or delete any mail about payroll, direct deposits, or bonuses. My read: this is why a senior engineer treats a session token with the same seriousness as a password. MFA protects the login moment. It does nothing to protect the token that login moment hands out, and that token is what the attacker actually wanted.

Now, a quick update on PHP2Shell, the pair of critical PHP flaws I covered last week. Here's what's changed: multiple security firms, including the vulnerability's own responders, have now confirmed CVE-2026-109618 and CVE-2026-109619 are under active exploitation in the wild, not just early probing. PHP shipped fixes in versions 8.5.12, 8.4.27, 8.3.36, and 8.2.35. My take: the gap between "patch available" and "patch applied" is exactly where this one is being hit right now — if your org runs PHP with mod_php on Apache, this is the week to verify, not assume.

Tonight's thread: a password check at the front door doesn't protect what happens after someone's already inside the building.
