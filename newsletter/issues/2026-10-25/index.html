Current Events

XZ Utils Backdoor

A contributor spent more than two years quietly earning trust on an open-source project nobody outside a small community had ever heard of — and then used that trust to plant a backdoor capable of giving an attacker remote root access to a huge share of the internet's Linux servers. It was caught by sheer accident, days before it would have shipped everywhere. Here's how it actually happened.

XZ Utils is a compression library — the kind of low-level utility baked into nearly every Linux distribution, used constantly and noticed by almost nobody. According to the public account assembled from the project's own commit history and corroborated by Red Hat's own security advisory, a contributor using the name "Jia Tan" had been submitting legitimate code to the project since 2021, gradually taking on more maintainer responsibility as the original maintainer's own bandwidth became a recurring complaint on the project's mailing list. That's the setup: patient, multi-year social engineering of an open-source maintainer pipeline, not a technical exploit.

Here's the chain, step by step. In February 2024, this now-trusted maintainer account introduced malicious code across two releases, version 5.6.0 and 5.6.1. The payload didn't live in the public GitHub source code itself — it was hidden inside the release tarballs, the packaged archives that Linux distributions actually download and build from, specifically disguised inside test files used to validate the build. When a system built XZ Utils from one of those tarballs under the right conditions, the hidden code intercepted and modified SSH authentication — opening a path for a specific attacker, holding a specific private key, to gain unauthenticated remote access. On March 29, 2024, a Microsoft engineer named Andres Freund noticed something almost absurdly mundane: SSH logins on a development machine he managed were taking slightly longer than normal, and burning more CPU than they should. He investigated that one small performance anomaly, traced it back to XZ Utils, and disclosed it the same day.

Root cause, in one sentence: a years-long, patient social-engineering campaign earned trusted-maintainer status on a critical dependency, and that trust was the actual vulnerability — the malicious code itself was almost incidental once that trust existed.

What actually limited the damage, and this is the senior-level detail worth naming: this backdoor was caught before it ever reached a stable, widely-deployed Linux release. It existed only in bleeding-edge, pre-release distributions — Fedora Rawhide, Debian unstable and testing, Kali's rolling release, openSUSE Tumbleweed — the versions power users and developers run specifically to catch problems before they reach production. Red Hat's own advisory confirmed no shipped version of Red Hat Enterprise Linux was ever affected. The backdoor was weeks, maybe one release cycle, from reaching stable distributions that run in production environments everywhere, and it was one engineer's attention to a 100-millisecond delay that closed that window in time.

So what does that mean for the kind of system a senior engineer is responsible for? A senior engineer treats "who maintains this dependency, and how did they earn that position" as a real question, not an unanswerable one — because XZ Utils proves that trust in open source is a security boundary like any other, and it can be patiently built up specifically to be abused. On a RHEL and AWS lab, that means practicing exactly what caught this in the real world: establishing a performance baseline for routine operations like SSH authentication, so that a small, unexplained anomaly actually stands out instead of disappearing into normal variance nobody's watching closely enough to notice.

Control Failures

# Failure NIST SP 800-53 Rev 5 Control Family
1 A single contributor account was allowed to accumulate maintainer-level trust and release authority over an extended period with no apparent secondary review of that account's own trajectory or behavior. AC-6 — Least Privilege
2 The malicious payload was hidden inside release tarball test artifacts rather than the public, reviewable source repository, meaning normal code review of the visible source never saw it. SI-10 — Information Input Validation
3 No configuration management process flagged or questioned why build/release artifacts (the tarballs) differed meaningfully in content from the public version-controlled source. CM-3 — Configuration Change Control
4 Downstream Linux distributions had no systematic process to independently verify that a dependency's released build artifact matched its publicly reviewable source. CM-7 — Least Functionality
5 Detection depended entirely on one engineer's personal, informal observation of a performance anomaly — no automated monitoring or audit baseline caught the backdoor. AU-6 — Audit Record Review, Analysis, and Reporting

What Held

  • Rolling-release distributions acting as an unintentional tripwire. Because the backdoor first reached only bleeding-edge, pre-stable distributions — the versions used by developers and power users specifically because they tolerate instability in exchange for catching problems early — it was exposed to exactly the kind of technically sophisticated, performance-sensitive users most likely to notice something subtly wrong before the code ever reached a stable release.
  • Fast, transparent, coordinated vendor response. Within hours of Freund's disclosure, Red Hat, Debian, and other distributions independently confirmed scope, issued urgent guidance, and reverted affected packages — a senior engineer credits that coordinated response as a real mitigating factor distinct from praising the fact that the backdoor existed at all.
  • One engineer's baseline awareness of "normal." Andres Freund only caught this because he had a working sense of how long SSH logins on his own systems ordinarily took. That's the senior-level point worth naming out loud: the control that actually worked wasn't a tool, it was one person's calibrated expectation of normal system behavior.

Senior Security Advice

Disable Direct Root Login Over SSH

The Advice

Turn off direct root login over SSH on every server, and require every administrator to authenticate with their own named account before elevating privilege.

Why It Matters

Root is the one account guaranteed to exist with full superuser rights on almost every Linux and Unix host, which makes it the single most valuable target for anyone scanning the internet for exposed SSH. When PermitRootLogin is left at its default or explicitly set to "yes," a stolen password, a weak passphrase, or a successful brute-force attempt against that one account hands an attacker complete control with no extra steps. Worse, every session shows up in the logs as "root" — there is no way to tell which human, or which compromised credential, was actually behind the keyboard. That is the pattern behind a huge share of internet-facing server compromises: automated bots continuously sweep for port 22, spray common credentials at the root account specifically, and the first server that answers "yes" to root login is the one that gets fully owned, not partially owned. DISA's own hardening requirement for this control exists precisely because shared root access destroys non-repudiation: without it, an incident responder cannot reconstruct who did what during a breach.

How to Implement It

  1. Before touching anything, confirm every administrator already has a personal account with SSH key-based access and sudo or RBAC rights configured and tested — this step prevents a lockout.
  2. Set PermitRootLogin no in /etc/ssh/sshd_config. On RHEL 9 specifically, check /etc/ssh/sshd_config.d/ first, since a drop-in file there can silently override the main config and undo the change.
  3. Push the setting through the base image or configuration management tool (Ansible, Puppet, cloud-init) rather than editing boxes by hand, so the control survives the next rebuild instead of drifting.
  4. Restart sshd, then verify from a second, already-open session: run ssh root@host from another machine and confirm it is rejected before closing the session you used to make the change.
  5. Confirm the control is actually enforced, not just configured, by running sshd -T | grep -i permitrootlogin and by scanning the host with an OpenSCAP profile against the applicable STIG or CIS benchmark — the finding should come back closed.

The Pushback You'll Hear

"It's a small environment, I'm the only admin, this is overkill." The senior-engineer rebuttal: the size of the team has nothing to do with the size of the blast radius. Direct root login means anyone who ever obtains that one password or key — through phishing, a leaked backup, or a brute-force hit — gets instant, untraceable superuser access. Logging in as yourself and elevating with sudo costs one extra command and buys a named audit trail, which is exactly what you need the day something does go wrong.

Tech News

A vulnerability that's been quietly backdooring Nextcloud servers since mid-September just landed on the US government's official list of flaws that are actively being exploited right now. If your organization runs self-hosted collaboration tools, this is the one to know tonight. Two stories: a document-collaboration flaw that just graduated to a federal action item, and a fresh, still-unpatched crack in the language a huge share of the internet runs on.

Start with Collabora and Nextcloud. According to Collabora's own advisory and the CVE record, tracked as CVE-2026-110447, an unauthenticated command-injection flaw in the built-in CODE Server component — the piece that lets Nextcloud users edit documents collaboratively — carries a near-maximum severity score. BleepingComputer and multiple outlets confirmed attackers have been exploiting it in the wild since mid-September, dropping PHP web shells onto compromised servers weeks before the public advisory caught up. Here's what's new as of this week: CISA added this exact flaw to its Known Exploited Vulnerabilities catalog on October 23rd — a federal confirmation, based on real-world attack evidence, that this isn't a theoretical risk anymore. The fix has existed since mid-September, but only the self-hosted, built-in version of the CODE server is affected; standalone Collabora deployments and Nextcloud's all-in-one package were never exposed. My read: the gap here isn't the patch — it's the month-plus window between "attackers are already using this" and "the government formally says so." If you're waiting for a KEV listing to tell you something's urgent, you're always going to be behind the attackers who found it first.

Next up, an update on a story I covered two nights ago. I told you about PHP2Shell, the pair of critical remote-code-execution flaws PHP patched across its supported versions. Here's what's changed: PHP's own security team has now disclosed a third, related flaw in the same memory-handling code — and this one doesn't have a patch yet. According to PHP's own advisory, the issue involves internal request data that can be accessed after its backing memory has already been freed, and the only mitigations available right now reduce exposure without closing the hole completely. My take: when a vendor finds a second and third issue in the same subsystem within weeks of the first, that's not three unrelated bugs — that's a sign the underlying code pattern itself needs a harder look, not just another patch.
