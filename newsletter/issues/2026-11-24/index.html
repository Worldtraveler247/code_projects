Senior Security Advice

Deploy Protective DNS to Block Malicious Domains Before They Load

The Advice

Route every endpoint, server, and guest network through a protective DNS service that blocks known-malicious domains before any connection is made.

Why It Matters

Almost every stage of an attack depends on a DNS lookup first: a phishing link has to resolve before the fake login page loads, and malware has to resolve a command-and-control domain before it can phone home or receive instructions. A protective DNS service sits in front of that lookup and checks it against threat intelligence before answering, so a device trying to reach a known-bad domain gets blocked or redirected instead of connected. Without that layer, the first real defense is often the endpoint itself, after the connection has already succeeded. NSA and CISA's joint guidance on this control states plainly that protective DNS can greatly reduce the effectiveness of ransomware, phishing, botnet, and malware campaigns, because so many of those campaigns depend on DNS resolution working normally. Ransomware in particular needs to reach staging and command-and-control infrastructure to retrieve keys and instructions; cutting off that resolution stalls the attack before it reaches the point of data loss.

How to Implement It

  1. Deploy a protective DNS service with current threat-intelligence feeds and point every corporate endpoint, server, and guest network's DNS resolution to it — nothing should be allowed to fall back to an unfiltered public resolver.
  2. Block outbound DNS on port 53, and DNS-over-HTTPS or DNS-over-TLS to resolvers other than the approved one, at the egress firewall so devices can't bypass the protective resolver by setting their own DNS.
  3. Turn on query and block logging and feed it into the SIEM, so a hit against a malicious domain becomes an alert a team actually sees, not a silent drop.
  4. Verify the control is actually working, not just configured: resolve a vendor-supplied test malicious-category domain from inside the network and confirm it gets blocked, and pull resolver logs to confirm traffic from every subnet is actually transiting the protective resolver rather than slipping around it.
  5. Review blocklists and allowlist exceptions on a schedule, so newly reported malicious domains get added quickly and legitimate business domains don't get caught as false positives.

The Pushback You'll Hear

"Attackers can route around DNS filtering with IP literals or their own encrypted resolver, so what's the point?" The senior rebuttal: no single control is complete, and that's exactly why step two exists — blocking rogue DNS-over-HTTPS and DNS-over-TLS at the egress firewall closes the obvious bypass. Protective DNS isn't meant to replace endpoint detection or egress filtering; it's a cheap, high-coverage layer that stops a large share of commodity phishing and malware traffic using a lookup that was going to happen anyway, freeing the more expensive controls to catch what gets through.

Why Ansible Handlers Don't Run When You Think They Do

Here's a gotcha that trips up almost everyone the first time they write an Ansible playbook: you notify a handler to restart a service, the playbook finishes, and the service never actually restarted when you expected it to. Today I want to explain why that happens, because it's one of the fastest ways to lose trust in your own automation.

A handler in Ansible is just a special kind of task that only runs when another task tells it to, using something called "notify." The classic example is a task that changes a config file and then notifies a handler to restart the service that reads that file. Here's the part that catches people off guard: a notified handler does not run the instant it's triggered. It runs once, at the very end of the play, after every other task in that play has finished — and only if that task actually reported a change.

Why does this matter operationally? Picture a playbook with ten tasks. Task three updates a config file and notifies "restart nginx." Tasks four through ten keep running. If task seven fails and the play stops, that handler never fires at all, even though the config already changed on disk. Now you've got a config file and a running service that are out of sync, and nothing in the output screamed "warning" at you — it just quietly didn't get to the end.

Here's the senior take. A junior engineer assumes handlers behave like a function call: notify it, it runs immediately. A senior engineer treats handler timing as a sequencing hazard worth designing around — either by forcing an early flush with "meta: flush_handlers" when a restart truly can't wait, or by not depending on handler timing for anything order-sensitive in the first place.

Think of it like leaving a note on a coworker's desk instead of walking over to tell them directly. The note gets read, but only at the end of their day, and only if they actually come back to their desk. If they leave early, that note sits there untouched — same as a handler that never gets its chance to run because the play stopped first.

So next time you're reviewing a playbook with a teammate, a good line to open with is: "Where in this play do we actually need that restart to happen immediately, versus where can it wait until the end?"

Key Takeaways

  1. A notified Ansible handler doesn't run immediately — it runs once, at the end of the play, and only if the task that notified it reported a change.
  2. If a play fails or stops before reaching the end, any handlers that were notified earlier never run, which can leave config files and running services out of sync.
  3. "meta: flush_handlers" forces queued handlers to run early, which is the right tool when a restart genuinely can't wait until the end of the play.

Reader Question

Q: "If a handler only runs at the end of the play, how do you make sure a service actually restarts before the next task that depends on it runs?"

Tech News

If any website or app in your world runs on PHP, here's the story to know about today: researchers found a way to get a server to run attacker-controlled code through the ordinary business of storing a web session, and PHP's own maintainers disagree with the researcher over how easy it actually is to pull off. Two stories today: that session-handling flaw sitting inside PHP's emergency November release, and a browser bug with a federal patch deadline that lands today.

Let's start with PHP. On November 19th, the PHP project shipped security releases across versions 8.2, 8.3, 8.4, 8.5, and the upcoming 8.6, fixing seventeen separate advisories, seven of them rated critical. The one to know by name is nicknamed phpAfterShell, tracked as CVE-2026-126714, scoring 9.2 out of 10 on the newer Common Vulnerability Scoring System, version 4.0. According to the security firm Depthfirst, which found and reported it, the bug is a time-of-check-to-time-of-use flaw — TOCTOU for short — sitting in PHP's default file-based session handler. In plain terms, there's a gap between the moment PHP checks a session file and the moment it actually uses it, and that gap is wide enough for an attacker to slip in and get code to run. Here's where it gets interesting: PHP's own advisory says exploiting the worst of these issues needs a non-default configuration. Depthfirst's CEO disputes that, saying the exploits work against PHP running with its default settings. Here's my read: when the people who found a bug and the people who patched it disagree about how exposed you actually are, the responsible move is to patch on the emergency's timeline anyway, not wait for that argument to get settled.

Turning to something that touches nearly every workstation in a federal network. According to the Cybersecurity and Infrastructure Security Agency, or CISA, a use-after-free flaw in Chrome's XML handling component — tracked as CVE-2026-125350 — was already being actively exploited when Google patched it on November 9th in Chrome version 157.0.8103.50. CISA added it to its Known Exploited Vulnerabilities catalog on November 10th and set today, November 24th, as the deadline for federal civilian agencies to have it patched. That's the eighth Chrome zero-day Google has had to fix this year alone. My take: a browser isn't a side application anymore — it's the interface every employee uses for email, internal tools, and cloud consoles, which makes a Chrome zero-day a workstation-fleet problem, not a one-app problem, and exactly why a federal deadline attaches to something as ordinary-sounding as a browser update.

So here's the through-line: one story is about patching ahead of an unresolved dispute instead of waiting for it to settle, the other is about a deadline landing today on a piece of software everyone assumes updates itself.
