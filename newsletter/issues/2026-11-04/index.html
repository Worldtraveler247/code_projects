Current Events

Microsoft Power Apps Portals Data Exposure

Thirty-eight million records -- names, Social Security numbers, COVID test results -- sat open to anyone on the internet for weeks, and nobody had to hack anything to get at them. The setting that exposed them was just... the default. Here's how a feature meant to make building apps easier turned into one of the biggest accidental data exposures of the decade.

Microsoft's Power Apps is a low-code tool that lets organizations build quick web portals -- things like a COVID testing sign-up page, or a job-application form. According to the security research firm UpGuard, an analyst found in May of 2021 that many of these portals were pulling data through a feature called an OData feed, and that feed's access setting defaulted to open to anyone who could guess or find the right web address -- no login required.

Here's the chain. A developer builds a portal, turns on a list to display records, and never touches the permissions, because the default already looks like it's working -- the list displays data, the app works, the ticket closes. What they didn't realize is that the same data was also reachable directly through the OData feed's raw address, completely bypassing whatever login screen sat in front of the portal itself. UpGuard notified Microsoft in June; by the time access was cut off in July, the exposure had touched at least forty- seven organizations, including airlines, a trucking company, and several US state governments, with some of the exposed data including Social Security numbers.

Root cause, in one sentence: the tool's default configuration treated "convenient for the developer" and "private by default" as the same thing, when they were never the same thing at all.

What actually held: nothing stopped the records from being public in the first place -- that's the honest version of this story. What limited the damage afterward was that a legitimate security research firm found it first, through ordinary internet scanning, and reported it responsibly instead of selling it or dumping it. Microsoft's fix wasn't a patch -- it was flipping the default itself, so new portals start locked down instead of starting open.

So what does this mean for how a senior engineer treats a vendor's own defaults? A senior engineer never reads a default setting as a security decision someone already made on their behalf -- not on a RHEL box, not on an AWS account, not on any low-code platform. The standing question becomes: not "does this work the way it shipped," but "has someone actually verified what this default exposes, and proven it's closed." On a RHEL or Podman lab, that means treating every new service's default access the same way -- confirmed closed, never assumed closed.

Control Failures

# Failure NIST SP 800-53 Rev 5 Control Family
1 The platform's default configuration for OData feed access was public rather than restricted, requiring an explicit opt-in to lock it down. CM-6 — Configuration Settings
2 No access control enforced authentication or authorization before serving records through the OData feed, even where the portal's own login screen implied one existed. AC-3 — Access Enforcement
3 Organizations had no process to verify that a deployed portal's actual data-access surface matched what they believed they had configured. CA-7 — Continuous Monitoring
4 The exposure was found by an external research firm's internet scan rather than by the affected organizations' own vulnerability management process. RA-5 — Vulnerability Monitoring and Scanning
5 Sensitive data categories, including Social Security numbers, were stored and served through a general-purpose, low-code data feature without additional handling controls. SC-28 — Protection of Information at Rest

What Held

  • Responsible discovery and disclosure. UpGuard found the exposure through routine research, not by targeting a specific victim, and followed a standard notify-then-publish disclosure timeline rather than exploiting or selling the access.
  • A fast cutoff once notified. Public access was closed within roughly two weeks of Microsoft being notified, limiting how long the window stayed open after the right people knew.
  • A systemic fix, not just individual cleanup. Microsoft's response changed the platform's own default behavior going forward, which protects every portal built afterward, not just the ones already found and fixed.

Senior Security Advice

Replace Long-Lived CI/CD Credentials with Short-Lived OIDC Federation

The Advice

Stop storing cloud access keys as secrets in your CI/CD pipeline — federate the pipeline's identity through OpenID Connect so it receives short-lived, narrowly scoped credentials instead of a static key.

Why It Matters

A cloud access key dropped into a CI/CD secrets store (GitHub Actions secrets, a Jenkins credentials store, a GitLab CI variable) is a long-lived, static credential. It works from anywhere, with no built-in expiration, until someone remembers to rotate it. If that key leaks — through a misconfigured build log, a malicious pull request that triggers an unreviewed workflow, or a compromised third-party action — the attacker doesn't just get into one build, they get standing access to whatever that key can touch in your cloud account.

CISA and the NSA's joint guidance on defending CI/CD environments names insecure secrets management and insufficient pipeline access controls as core threats, and recommends minimizing long-term credentials and applying least privilege to CI/CD access. The incident class this prevents is the one where attackers pivot through a build pipeline's cloud credentials to reach production infrastructure — the pattern behind the software supply-chain compromises this guidance exists to stop.

How to Implement It

  1. Register the CI/CD provider (GitHub Actions, GitLab, etc.) as an OpenID Connect identity provider in IAM.
  2. Create a narrowly scoped IAM role whose trust policy checks the sub claim — restricting it to one repository, branch, or environment — rather than trusting the provider broadly.
  3. Update the pipeline to exchange its OIDC token for temporary credentials at runtime (for example, aws-actions/configure-aws-credentials with role-to-assume), then delete the stored long-lived access key secret entirely.
  4. Scope that role's permissions to exactly what the one job needs — push to one registry, deploy one stack — never broad or administrative access.
  5. Verify it's actually enforced, not just configured: try triggering the pipeline from an unapproved fork or branch and confirm the role assumption is denied, then check your cloud audit log for AssumeRoleWithWebIdentity events to confirm no leftover long-lived key is still in use.

The Pushback You'll Hear

"Our pipeline needs this key across multiple jobs and accounts, and OIDC is extra setup we don't have time for." The rebuttal: the trust-policy setup is a one-time cost per job, not an ongoing burden, and you can map separate sub conditions to separate roles for each job just as easily as you'd manage separate static keys — except the credentials expire in minutes instead of sitting there indefinitely, so a single leak stops being a standing compromise.

Tech News

If you run an online store on Drupal's Commerce module, attackers are placing fraudulent orders on sites just like yours right now — no login required. And if your organization runs Oracle's E-Business Suite, the attackers testing a brand-new flaw in it haven't hit real targets yet, but they're already rehearsing on decoys built to look just like yours. Two stories tonight: a Drupal Commerce access-control flaw under active attack across tens of thousands of stores, and an Oracle E-Business Suite bug attackers are quietly probing before anyone's confirmed a real victim.

Start with Drupal. According to Drupal's own security advisory, corroborated by SecurityWeek, BleepingComputer, and reporting on Canada's Cyber Centre bulletin, the open-source Commerce Core module shipped a highly critical access-bypass flaw, CVE-2026-118539, that lets an attacker tamper with orders without ever logging in — on any of the more than forty-two thousand sites running the module, regardless of how it's configured. Drupal's security team published the advisory on October 28th alongside thirty-eight other contributed-project fixes, and the vendor Centarro has already released order-audit checks because reports describe attackers placing fraudulent orders in live stores. Here's my read: an unauthenticated flaw in a commerce platform isn't just a data problem, it's a direct line to a store's money — and the fix here isn't exotic, it's patching to version 3.3.13 or 8.x-2.41 and then actually auditing recent orders, because the patch alone doesn't undo fraud that already happened.

Next up, turning to Oracle. According to the security research firm Defused, corroborated by The Hacker News and Orca Security, Oracle's October Critical Patch Update — released October 20th — fixed CVE-2026-101767, a maximum-severity, 9.8-rated flaw in E-Business Suite's Application Object Library that lets an unauthenticated attacker chain a SQL injection into full remote code execution. One week later, on October 27th, Defused reported attackers already probing honeypots built to look like unpatched E-Business Suite installations — not real victims yet; Oracle hasn't tagged this one as exploited in the wild. My take: that gap between patch day and probing is exactly the window a senior engineer treats as borrowed time, not safety — the attackers testing the lock on a decoy today are testing it on a real door tomorrow.

Tonight's thread: one of these flaws is already being used against real victims, the other is still in rehearsal — and the only difference between them, six months from now, might just be how fast you patched this week.
