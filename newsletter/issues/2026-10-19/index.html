Current Events

Verizon / NICE Systems S3 Exposure

Picture a database holding millions of phone customers' names, addresses, and the PIN codes used to verify their identity on a support call -- sitting in a storage bucket anyone on the internet could simply browse to, no password required. That's what a security researcher found in June 2017, not inside Verizon's own systems, but inside a vendor's. Here's how it actually happened.

NICE Systems is a call-center analytics vendor. Verizon used NICE to process and analyze millions of customer-service interactions. According to UpGuard's own published research, researcher Chris Vickery found an Amazon S3 storage bucket, operated by NICE on Verizon's behalf, configured to allow public access -- no login, no credential, nothing standing between the data and anyone who found the bucket's address.

Root cause, in one sentence: Amazon S3 buckets are private by default, and someone at NICE manually changed that setting to public, so a vendor's own routine configuration choice -- not an attack, not a stolen credential -- is what put the data on the open internet in the first place.

Here's what the exposure actually included: customer names, phone numbers, home addresses, account details, and the detail that should stand out most -- account PINs, the codes Verizon customers use over the phone to prove they are who they say they are. Expose that PIN, and you haven't just leaked personal information, you've handed a scammer the exact credential Verizon's own support line was built to trust. UpGuard estimated as many as 14 million records sat in the bucket; Verizon's own later figure put the affected customer count closer to 6 million. Both the vendor and Verizon confirmed the exposure occurred, and reporting differs on which of those two numbers best describes the true scope.

What contained it, and this is the senior detail worth naming: UpGuard practiced responsible disclosure. It notified Verizon directly on June 13th, 2017, instead of publishing immediately, giving the company a window to act before the exposure became public knowledge. Verizon secured the bucket by June 22nd.

So what does that mean for you? A senior engineer treats a cloud storage bucket's access setting as something to actively verify on a recurring basis, not assume stays correct -- because this incident proves a sensitive dataset's exposure can trace back to nothing more exotic than one manually flipped permission, at a third-party vendor you don't directly control. A senior engineer would also build automated, continuous drift detection that alerts the moment any storage bucket moves from private to public, rather than relying on an outside researcher to notice first -- and would never store an authentication factor like a customer PIN in the same plain, broadly-accessible dataset as the personal information it's meant to protect.

What Held

  • Responsible disclosure gave Verizon a clean window to act. UpGuard notified Verizon directly rather than publishing the finding immediately, which meant the company could secure the bucket before the exposure became public knowledge rather than reacting to a live news story.
  • The fix, once notified, was fast. Verizon and NICE secured the bucket within roughly nine days of UpGuard's report.
  • Say the limit of that out loud. "Secured quickly once notified" describes the response to discovery, not the length of the actual exposure — nothing in public reporting establishes how long the bucket had been sitting open to the internet before UpGuard happened to find it. Naming that gap, rather than letting a fast fix read as an early catch, is the senior move.

Senior Security Advice

Sign and Verify Every Software Release Before It Ships

The Advice

Cryptographically sign every build artifact you ship, publish a way for the next system in line to verify that signature, and make verification a blocking step before anything deploys or installs — never a warning someone can click past.

Why It Matters

Without signing, a system has no way to tell a legitimate release from a tampered one. A package manager, a container runtime, or a deployment pipeline will install whatever bytes arrive, as long as the format checks out — it has no concept of "this isn't really from the vendor." That gap is exactly what makes software supply chain compromise possible: if an attacker gets a foothold in a build server, a CI/CD pipeline, or an update distribution channel, they can insert malicious code once and have it trusted everywhere that artifact gets installed, with no further exploitation needed on each downstream target. The canonical example of this incident class is the SolarWinds compromise, where attackers altered a trusted build process so that malicious code shipped inside an otherwise legitimate, signed update — a reminder that signing has to be paired with build-pipeline integrity, not treated as a silver bullet on its own. NIST's Secure Software Development Framework names this exact gap directly: its PS.2 practice exists specifically so that the people and systems consuming your software "can confirm that the software they acquired is legitimate and has not been tampered with."

How to Implement It

  1. Sign every release artifact — container images, packages, binaries, build manifests — using an established certificate authority or a transparency-backed system like Sigstore/cosign. NIST's SSDF lists exactly this as a notional way to satisfy PS.2: use an established CA for code signing, and post cryptographic hashes for release files on a secured site.
  2. Publish the verification material — the signature, the hash, the public key fingerprint — over a channel separate from the artifact itself, so an attacker who can tamper with the release can't also tamper with the thing used to check it.
  3. Make verification happen automatically at install or deploy time, not as a manual step someone remembers under deadline pressure. On Red Hat Enterprise Linux this is built in: import the vendor's public key with rpm --import, and RPM checks the package's GPG signature before installing it, refusing to trust a package whose signature doesn't match.
  4. Verify the control is actually working, not just configured. Don't trust a green checkmark in a dashboard — run rpm --checksig or rpm -K against a known-good package and confirm you see a clean result, then deliberately try to install or deploy an unsigned or altered artifact and confirm the pipeline rejects it instead of merely logging a warning.
  5. Protect the signing keys like the crown jewels they are. Keep them in an HSM or cloud KMS, never on the build server itself, and rotate them on a schedule with a clear revocation path — a leaked signing key turns your trust mechanism into the attacker's best tool.

The Pushback You'll Hear

"Signing is just another manual step people skip when a release is late." That's true of signing bolted on by hand — it's not true of signing built into the pipeline as code. Wire it into the CI/CD job so every artifact gets signed automatically and the deploy step fails closed on a bad or missing signature, the same way a failing test blocks a merge. At that point skipping it isn't a shortcut anyone can take; the pipeline simply won't ship.

Tech News

A patch note buried in an open-source office tool just turned into active break-ins: Nextcloud's built-in document editor is being used right now to plant web shells on self-hosted servers, and the official fix isn't what most admins think it is. Two stories tonight — that one, and a one-line correction to something I told you about Microsoft's giant October update.

Start with Nextcloud. According to Collabora's own security advisory, confirmed by BleepingComputer and The Hacker News, attackers have been exploiting CVE-2026-110447 — an unauthenticated command-injection flaw in the built-in CODE Server app that handles document editing — to drop web shells onto compromised servers. Here's the part that should get your attention: the bug only fires during a narrow window, specifically when the app's local document server isn't currently running, like during a restart, an upgrade, or after a crash. Attackers have been hitting that window since mid-September, weeks before Collabora's formal advisory landed on October 14th. And Collabora says explicitly that disabling the vulnerable app isn't a real fix — you have to actually upgrade to version 26.4.303 or later, or remove it outright if you're on an end-of-life Nextcloud release. My read: a narrow exploitation window doesn't mean low risk, it means the attacker just needs patience — and a vendor telling you the obvious workaround won't save you is worth repeating to anyone who stopped reading the advisory after the headline.

Next up, a correction. Yesterday I told you Microsoft's October Patch Tuesday fixed 1,411 flaws, including one actively exploited zero-day, without naming it. Here's what's new: according to Security Affairs, that flaw is CVE-2026-96951, a security feature bypass in the Windows Shell that strips the Mark of the Web tag from downloaded files — the marker that tells Windows a file came from the internet and should trigger extra warnings. CISA has since added it to its Known Exploited Vulnerabilities catalog. My take: Mark of the Web isn't glamorous, but it's the trigger that wakes up SmartScreen and Office's Protected View — lose that one tag, and every warning layered on top of it never even fires. It's a reminder that defense-in-depth only works if each layer actually gets the signal the next layer depends on.

Same thread tonight: a documented fix and a documented workaround aren't automatically the real fix — verify what a patch actually closes before you trust it.
