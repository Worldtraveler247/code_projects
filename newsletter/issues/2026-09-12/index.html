Senior Security Advice

Enterprise Password Managers to Kill Password Reuse

The Advice

Roll out an enterprise password manager to every employee and make every account password unique, generated, and stored in it — never memorized, never reused.

Why It Matters

Password reuse is the pattern behind nearly every credential-stuffing campaign: a password that leaks from one breached, unrelated website gets fed into automated tools and tried against corporate logins, VPNs, and cloud consoles until one of them matches. The account itself never has to be "hacked" — the attacker just replays a credential the user already handed away somewhere else. Without a password manager, most people cope with dozens of logins by reusing two or three passwords with minor variations, which means one leaked retail or forum account can become the entry point into payroll, email, or a cloud environment. The incident class this stops is exactly that: large-scale credential-stuffing attacks, where breach dumps from unrelated companies are weaponized against your workforce months or years later.

How to Implement It

  1. Select and centrally provision an enterprise password manager (not a "recommendation" — deploy it via SSO/SCIM to every employee, with browser extensions and mobile apps installed by default).
  2. Run the manager's built-in weak-password and reused-password audit against existing vaults, and force a one-time reset on every account it flags.
  3. Set policy: every non-SSO login gets a unique, manager-generated password of at least 16 characters, and browser-saved passwords are disabled in favor of the managed vault.
  4. Make sure login forms don't fight the tool — confirm paste is allowed in password fields, since NIST's guidance exists specifically to stop sites from blocking password-manager autofill.
  5. Verify it's actually working by pulling the admin dashboard's reused-password count monthly and tracking it to zero — a purchased license with a 40% adoption rate is not a control, it's a line item.

The Pushback You'll Hear

"A password manager is a single point of failure — if the vault gets breached, every credential is exposed." The senior-engineer rebuttal: that risk already exists today, just distributed across dozens of sites you don't control and can't audit. A vault protected by its own strong MFA and zero-knowledge encryption concentrates that risk into one target your team actually defends, monitors, and can rotate out of quickly — instead of leaving it scattered across every third-party site an employee has ever signed up for. CISA pairs this guidance with MFA for exactly this reason: the password manager kills reuse, MFA covers the case where a single credential still gets stolen.

Senior Talk Tracks

Secrets Rotation

Here's a question that separates a junior engineer from a senior one: "when's the last time this API key was rotated?" If the honest answer is "since the day someone created it, two years ago," you've found a real problem, even though nothing about that key looks broken today. That's what secrets rotation is about.

Plain English first. A "secret," in this context, is any credential a system uses to prove itself to another system -- a database password, an API key, a certificate, a token. "Rotation" just means replacing that secret with a new one on a regular schedule, and making sure everything that depended on the old one gets updated to use the new one without breaking.

Here's why it matters in production, and it's not really about any one secret being weak. It's about how long a leaked secret stays useful to an attacker. If you rotate a database credential every ninety days, a secret that leaked eighty days ago is worthless in ten more days, whether or not you ever find out it leaked. If that same credential never rotates, a leak from two years ago might still be valid right now -- and you'd have no way to know without checking every single place it might have ended up.

The senior take, the part a junior usually misses: rotation isn't really a security control by itself. It's a test of whether your systems can survive a credential changing at all. A lot of organizations avoid rotating secrets not because they don't see the value, but because nobody's confident the change won't break something -- some script, some forgotten integration, still hard-coded to the old value. So a senior engineer treats "can we rotate this without an outage" as the real question, and building automated rotation is what forces you to find and fix every place a secret is hard-coded, long before an attacker finds it for you.

Think of it like changing the locks on a house you've handed spare keys to a dozen different people over the years -- the contractor, the old dog-walker, a former roommate. You don't remember who still has a copy, and asking each of them to give it back isn't realistic. So you just change the lock. The old keys stop working, whoever holds them, whether or not you ever find out where they went.

A natural way to bring this up at work is: "do we know how long it would take us to fully rotate our most sensitive credential, end to end, without anything breaking?" That question tends to go quiet fast -- and the silence is the finding.

Key Takeaways

  1. Secrets rotation limits how long a leaked credential stays useful to an attacker, whether or not the leak is ever discovered.
  2. The real value of building automated rotation is that it forces you to find every place a credential is hard-coded, before an attacker does.
  3. An organization that's afraid to rotate a credential because something might break has already found its biggest hidden risk.

Reader Question

"If rotation is so valuable, why don't more organizations just automate it everywhere immediately?"

Honestly, it's because rotating a credential you're not confident about is scarier than leaving it alone — nobody wants to be the person who broke production trying to improve security. So teams put it off, the credential gets older and riskier, and the fear of breaking something grows right along with it. The way out isn't forcing rotation everywhere at once; it's starting with your highest-value credentials, in a test environment first, and treating every hard-coded dependency you find along the way as a bug to fix, not a reason to stop.

Tech News

If you run a Fortinet firewall or a Citrix NetScaler gateway, today matters more than most. One of these fixes has a federal patch deadline that lands today, and the other has been under active attack for a full week. Two stories: a Fortinet flaw hackers are already using to drop a remote-access trojan, and a Citrix NetScaler authentication bypass that lets an attacker walk straight past your login screen.

Start with Fortinet. CISA added CVE-2025-25249 to its Known Exploited Vulnerabilities catalog this week — a heap-based buffer overflow in FortiOS's cw_acd daemon, the background process handling part of the operating system's networking stack. Send it a specially crafted packet, and you can corrupt memory badly enough to run your own code with that daemon's privileges — no login required. It hits a wide swath of FortiOS versions, plus FortiSwitchManager and FortiSASE. Security researchers say attackers are already using it to install something called PivotC2, a remote-access trojan, on compromised devices. CISA's deadline for federal systems is today, September 12th. Here's my read: a firewall is supposed to be the thing standing between the internet and your network. When the firewall itself has an unauthenticated remote-code-execution hole, it's not a weak point in your defenses — it is the exposed front door, and the federal deadline is a floor, not a ceiling. If you're running an affected FortiOS branch anywhere, patch it today, not this week.

Next up, Citrix. NetScaler ADC and NetScaler Gateway — the appliances a lot of companies use for VPN access and remote login — have a critical authentication bypass, CVE-2026-19490, CVSS score 9.3. It affects systems configured as a gateway or an authentication server. The flaw lets an attacker reach an alternate path into the login process that skips the checks a normal login would enforce — so no valid credentials, no multi-factor prompt, nothing. Citrix patched it back in August, but once a working proof-of-concept went public, attackers started exploiting it in the wild starting around September 4th. My take: this is a full week of exposure before most security teams even noticed the shift from "patched" to "actively exploited." If your NetScaler was internet-facing during that window, patching now closes the door, but it doesn't tell you if someone already walked through it — go back and hunt for sessions and admin changes you can't account for.

Through-line: two different vendors, the same lesson — the edge devices guarding your network are exactly what's under fire right now, and closing the hole today doesn't undo whatever happened while it was open. Stay patched, stay paranoid, and I'll see you tomorrow.
