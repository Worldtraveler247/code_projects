Current Events

The Toyota Connected Cloud Misconfiguration

In May 2023, Toyota admitted that a cloud database holding location data on roughly two point one five million connected-car customers in Japan had been sitting open to the public internet -- not for weeks, but for nearly ten years. Here's how it actually happened.

Toyota's T-Connect and Lexus G-Link services let customers track their car's location, and that data lived in a cloud environment managed by a Toyota subsidiary called Toyota Connected Corporation. According to Toyota's own May 12th, 2023 disclosure, back in November 2013 someone configured that cloud database's access setting to public instead of private. Nobody exploited a vulnerability. It was simply set wrong, and nothing ever checked it again.

Here's the chain. From November 6th, 2013, through April 17th, 2023, that database sat reachable from the open internet -- vehicle location history, timestamps, the in-vehicle device ID, and the VIN, for anyone who'd signed up for T-Connect or G-Link since January 2012. In a related window, drive recorder video from corporate customers was also exposed through a separate cloud service the same subsidiary managed. Nobody outside Toyota found this. Toyota found it themselves, in an internal review in April 2023 -- roughly nine and a half years after the setting was first wrong.

Here's the root cause, in Toyota's own words: insufficient dissemination and enforcement of the company's own data handling rules. The policy existed. Nothing was actually checking that live cloud configurations matched it.

I want to flag something honestly here. When Toyota audited every cloud environment that subsidiary managed, they found a second, separate exposure -- roughly two hundred sixty thousand more customers, from February 2015 to May 2023 -- disclosed on May 31st. Two nearly identical failures in the same subsidiary, both found only because Toyota finally went looking.

Here's what held. Toyota's own internal audit is what actually caught this, years too late, but it did happen. Once found, they blocked external access immediately, and Toyota's investigation reported no confirmed evidence of malicious access -- though that's a hard thing to verify after a bucket's been public for a decade, and this script says so plainly rather than taking Toyota's word for it. Toyota then built a real fix: a continuous cloud-configuration monitoring system, not just a one-time cleanup.

Here's what a senior engineer, or a senior ISSO, would change in how they work because of this. A written data-handling policy is worthless without something automatically checking cloud resources against it -- that's what a senior engineer sets up as account-level guardrails like AWS Config rules or S3 Block Public Access, enforced from day one, not discovered in an audit years later. In an AWS lab, that means standing up a bucket, attaching a public-read policy, and proving that account-level Block Public Access actually rejects it outright -- because a control that depends on someone remembering to check by hand is exactly the control that failed here for nine and a half years.

What Held

  • Toyota's own internal audit is what actually caught this. It took nine and a half years, but an internal review — not an external researcher, breach report, or regulator — is what found the exposure and triggered the response.
  • Once found, access was cut off immediately, and Toyota did not sit on the finding: it disclosed publicly within weeks (May 12) rather than quietly patching and staying silent.
  • Toyota proactively widened the review instead of closing the case. Auditing every cloud environment Toyota Connected managed — not just the one already found — is what surfaced the second, related 260,000-customer exposure itself, on May 31, rather than leaving it for an outsider to find later.
  • Toyota built a structural fix, not a one-time cleanup: a continuous cloud-configuration monitoring system plus renewed data-handling training, addressing the actual control gap (no ongoing enforcement) rather than just the one misconfigured setting.

Senior Security Advice

Centralize Secrets in a Manager, Never in Code

The Advice

Every password, API key, and database credential belongs in a centralized secrets manager with automatic rotation - never hardcoded in source code, config files, or infrastructure-as-code templates.

Why It Matters

A hardcoded credential is a secret that never changes and that everyone with repo access can read - including anyone who later clones, forks, or breaches that repository. CISA and the FBI call this out by name in their joint Product Security Bad Practices guidance: hardcoded credentials or secrets in source code for products tied to critical infrastructure are treated as a dangerous, systemic bad practice, not a minor code-quality nit, because they significantly raise national security and economic risk when they leak. NIST SP 800-53's Authenticator Management control, IA-5, points at the same root problem from the identity side - it requires organizations to protect authenticators from unauthorized disclosure and modification, and a credential sitting in plaintext in a git repo or a build artifact fails that requirement the moment it's committed. The incident class this causes is one of the most common breach starting points there is: a secret gets pushed to a public or improperly-scoped repository, a scanner or an attacker finds it within minutes to hours, and it's used to walk straight into a database or a cloud account with no exploit required at all.

How to Implement It

  1. Move every credential - database passwords, API keys, service-account tokens - out of source code and config files and into a dedicated secrets manager (AWS Secrets Manager, HashiCorp Vault, or an equivalent), retrieved at runtime instead of stored at rest in the app.
  2. Turn on automated secret scanning across every repository, including private ones, so a credential that gets committed by mistake is caught and rotated within minutes, not discovered months later.
  3. Enable automatic rotation on every secret the manager supports - AWS Secrets Manager can rotate database credentials on a defined schedule using a managed or Lambda-based rotation function - so a leaked secret has a short shelf life even if it's never spotted.
  4. Grant applications access to secrets through their own scoped identity (an IAM role, a Vault auth method) instead of a shared static key, so pulling a secret is itself an audited, attributable action.
  5. Verify the control is actually working: pull a random sample of repositories and running services quarterly, confirm zero hardcoded secrets turn up in a fresh scan, and confirm each sampled secret's rotation actually fired on schedule rather than silently failing.

The Pushback You'll Hear

"Pulling secrets from a vault at runtime adds latency and a new dependency my app now has to handle." The senior-engineer rebuttal: that dependency is the point - it's an audit trail and a kill switch that a hardcoded string can never give you. A secrets manager lets you revoke or rotate a compromised credential in seconds without a code deploy; a hardcoded key means shipping a new build just to lock the door, and by then the secret has usually already been used.

Senior Talk Tracks

Why Perimeter Defense Died

Let's talk about an idea that used to be the entire foundation of network security, and why senior security engineers now treat it as a dangerous assumption: perimeter defense.

Plain English first. Perimeter defense is the old castle-and-moat model -- you build a strong wall around your network, usually a firewall, and you put all your effort into guarding the one gate in and out. Once someone is inside that wall, whether that's an employee, a server, or an application, the network mostly trusts them by default. For a long time that was the whole security strategy: keep the bad guys outside, trust everyone inside.

Here's why that matters in production, and where it breaks down. Nobody works from inside one office network anymore. People connect from laptops at home, from coffee shops, through a VPN -- a virtual private network that tunnels a remote device into the "trusted" zone. Applications call other applications across cloud accounts that were never one physical network to begin with. So the wall isn't really a wall anymore, it's full of doors.

The senior take, the failure mode a junior usually misses: perimeter defense doesn't fail by someone breaking down the front door. It fails because one employee clicks a phishing link, or one set of VPN credentials gets stolen, and the attacker is now standing inside the walls, where nothing double-checks them again. That's called lateral movement -- once you're trusted at the gate, you can wander to any system inside with almost no further verification. The fix the industry moved to is called zero trust: never trust a request just because of where it's coming from, verify identity and device health on every single request, every time, gate or no gate.

Think of it like old airport security versus today's. It used to be one checkpoint at the front door, and once you were past it, you could walk into any gate, any lounge, no questions asked. Now every sensitive door inside the building checks your badge again, not just the one at the entrance.

A good way to open this at work: "Are we still treating VPN access as the finish line for trust, or are we actually verifying every request past that point?"

Key Takeaways

  1. Perimeter defense assumes anything inside the network boundary is trustworthy, which stopped matching reality once remote work, VPNs, and cross-cloud traffic became normal.
  2. The real failure mode isn't the wall being breached directly — it's one stolen credential letting an attacker move laterally once they're inside, with nothing checking them again.
  3. Zero trust replaces "trust by location" with "verify every request," checking identity and device health continuously instead of once at the gate.

Reader Question

"If we already have a VPN and a firewall, why isn't that enough — why do we need zero trust on top of it?"

Because a VPN and a firewall only control who gets through the front gate, and they say nothing about what happens after someone's already inside — which is exactly where most real breaches play out, through a phished employee or a stolen credential rather than a wall being broken down. Zero trust doesn't replace the firewall, it assumes the firewall will eventually be bypassed and builds verification into every request past that point, so one compromised credential doesn't automatically hand over the rest of the network. I'd frame it to a team as reducing blast radius, not adding paranoia for its own sake.

Tech News

A perfect-ten vulnerability in Microsoft's Azure AI Foundry let anyone on the internet skip authentication entirely and reach backend functions that control your AI workloads — no username or password needed. Microsoft already fixed it on their end, but if you're accountable for what ran on that platform before the patch landed, this is still your incident to investigate. Three stories today: that Azure flaw, fourteen BIND 9 vulnerabilities patched this week, and an actively exploited privilege-escalation bug in a backup plugin a lot of hosting providers run.

Start with Azure. CVE-2026-85889, published by Microsoft's Security Response Center on September 17th, carries a CVSS — Common Vulnerability Scoring System — score of ten out of ten. The root cause, according to Microsoft, is a missing authentication check, Common Weakness Enumeration category 306, on a critical function inside Azure AI Foundry, the company's platform for building and deploying artificial intelligence models. Certain backend routes never validated a session token or an API key, so an unauthenticated attacker could reach functions that manage model deployments and stored data. Microsoft patched it server-side, so there's nothing for customers to install. My take: a perfect-ten score on infrastructure you don't control the patch cycle for is still your risk to assess — pull your Azure AI Foundry activity logs for that window before you assume it's handled.

Next up, the Internet Systems Consortium shipped BIND 9.20.29 and 9.21.26 on September 16th, fixing fourteen flaws in the software that resolves much of the internet's domain name lookups. One of them, CVE-2026-77692, lets an unauthenticated attacker crash the BIND process with a single malformed DNS-over-HTTPS request. Another weakens DNSSEC — Domain Name System Security Extensions — validation enough that a resolver can accept a forged, unsigned answer. My read: DNS is the layer every other control assumes is trustworthy, so a validation bug here undermines everything built on top of it.

Which brings us to Acronis. CISA — the Cybersecurity and Infrastructure Security Agency — added CVE-2026-87886 to its Known Exploited Vulnerabilities catalog on September 16th: insecure default file permissions in Acronis's backup plugin for cPanel and WHM that let a low-privileged, authenticated user escalate straight to root on Linux. Acronis confirmed targeted exploitation, and federal agencies have until September 19th to patch.

All three stories share one thread: a trust boundary that quietly went missing, in an authentication check, a DNS record, or a file permission.
