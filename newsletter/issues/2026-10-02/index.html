Current Events

The Verkada Camera Breach

Here's an incident where the camera company watching everyone else got watched first -- not by a nation-state, but by a hacktivist collective that found one leftover password. Here's how it actually happened.

In March 2021, Verkada ran cloud-connected security cameras for thousands of organizations -- hospitals, schools, police departments, a Tesla factory floor. According to Verkada's own incident report, attackers first reached an internal Jenkins server on March 7th -- a build server Verkada's support team used to run bulk maintenance operations across customer cameras, and one that was reachable from the public internet. Sitting inside a script on that server was a hardcoded "super admin" credential.

That one credential was the whole ballgame. Attackers used it to log into Verkada's customer support web interface with full super-admin privileges, bypassing the normal authorization checks -- including two-factor authentication -- because the credential itself was the backdoor around all of it. That backend had a built-in support feature that could emulate any customer's own session, so once the attackers were in, they weren't limited to one account. According to Bloomberg's original reporting and Verkada's own account, they reached archived and live video from dozens of customer organizations, including classrooms, a psychiatric hospital, and a county jail. The cameras themselves also shipped with a built-in root-access support feature, which meant the same compromise handed attackers code-execution-level access on individual devices too -- not because of a second bug, but because that was simply how the product already worked.

Root cause, in one sentence: an internet-reachable internal support server held a single hardcoded super-admin credential, and that one credential -- not customer-specific, not scoped to a task, never rotated -- was the entire difference between normal support operations and a fleet-wide compromise.

Here's what actually contained this. Verkada learned of the intrusion on March 9th, after the attackers themselves reached out to a journalist -- not through any internal detection. But once notified, the company moved fast: it cut off the attackers' access within about two hours, disabled every internal administrator account as a precaution, and began notifying affected customers within six hours. A subsequent review of Verkada's own logs found no evidence of backdoors or lateral movement into customer networks beyond the video access itself -- meaning the logging the company already had in place, even though nobody was watching it in real time, was still good enough afterward to scope the damage and rule out a worse outcome.

Here's what a senior engineer, or a senior ISSO, would change in how they work because of this. A credential that can impersonate any customer account has no business being hardcoded in a script on a server reachable from the internet -- full stop. In a RHEL 9 lab with Podman, that means externalizing every credential into a secrets store or environment file with restricted permissions, scoping each one to exactly the task it performs, and proving with a simple grep across the codebase that no token like that is sitting in plaintext anywhere a support engineer's script could leak it.

What Held

  • Fast containment once notified. Verkada cut off the attackers' access within roughly two hours of learning about the intrusion, disabled every internal administrator account as a precaution, and began notifying affected customers within six hours — a genuinely fast incident-response execution once the company knew there was a problem.
  • Logging was good enough after the fact, even though nobody was watching it in real time. A post-incident review of Verkada's own logs found no evidence of backdoors or lateral movement into customer networks beyond the video access itself, which is what let the company credibly scope the damage instead of guessing at it.
  • Be honest about the limit of both. Neither control stopped the intrusion or even caught it while it was happening — detection depended entirely on the attackers choosing to contact a reporter. This incident's real lesson is about the missing detection layer, not a control that actually held during the attack itself.

Senior Security Advice

Put a Web Application Firewall in Front of Every Internet-Facing App

The Advice

Every internet-facing web application must sit behind a web application firewall configured with an active managed rule set, not just a network firewall and a prayer.

Why It Matters

A regular network firewall checks which ports and IP addresses are allowed through. It has no idea what's inside the HTTP request riding on that allowed connection. An attacker sending a SQL injection payload, a cross-site scripting attempt, or a malicious file upload to a public login page sails straight past a network firewall, because port 443 is supposed to be open. A web application firewall (WAF) is the layer that actually reads the request itself and blocks the attack pattern before it ever reaches the application code.

Without one, every web app is only as safe as its own code, all the time, with zero room for a mistake. The incident class this prevents is depressingly common and well documented: attackers scanning the open internet for known, unpatched web application vulnerabilities — injection flaws, broken authentication endpoints, vulnerable plugins — and walking straight in because nothing sat between them and the vulnerable code. A WAF doesn't replace secure coding, but it buys time between "a vulnerability exists" and "the vulnerability gets patched," which in a real organization is never zero days.

CIS Critical Security Control 16, Application Software Security, calls for exactly this kind of protective layer in front of web applications as part of a defense-in-depth posture, and its underlying safeguard on deploying web application firewalls specifically requires inspecting all traffic flowing to a web app for common attack patterns. OWASP's own Virtual Patching Cheat Sheet describes the same mechanism from the other direction: a WAF or equivalent enforcement layer can "virtually patch" a known vulnerability by blocking exploit attempts at the network edge while the real code fix is still being developed and tested.

How to Implement It

  1. Put every internet-facing web application behind a WAF — a cloud-native option like AWS WAF, Azure Front Door WAF, or Cloudflare, or a self-hosted option like ModSecurity, depending on where the app actually lives.
  2. Turn on a managed rule set (such as the OWASP Core Rule Set or your provider's equivalent) that covers the OWASP Top 10 attack classes — injection, broken authentication, cross-site scripting — instead of writing every rule from scratch.
  3. Run new rules in detection-only or "count" mode first against real production traffic, review what would have been blocked, then flip to blocking mode once you've confirmed legitimate traffic isn't caught in the net.
  4. Verify the control is actually working, not just deployed: run a safe, authorized test request containing a known attack pattern (for example, a harmless SQL injection string against a non-production path) and confirm in the WAF's own logs that it was inspected and blocked, not silently passed through.
  5. Review WAF logs and blocked-request trends on a recurring basis, and treat a sudden drop in blocked traffic as a signal to check whether the WAF is still actually in the request path — not just evidence that attacks stopped.

The Pushback You'll Hear

"The WAF will block real customers and break the app." The senior-engineer rebuttal: that's exactly why step three exists. No competent rollout flips a new rule set straight to blocking mode. You run it in detection mode first, watch what it would have blocked against real traffic, tune out the false positives, and only then turn on enforcement. A WAF that's never tuned is a liability; a WAF that's never turned on is worse.

Tech News

A federal patching deadline hits this weekend for a Cisco bug that lets an attacker become an administrator without ever logging in — and it's the fifth time this year Cisco's SD-WAN software has been caught this way. Two stories today: that Cisco flaw, and a file-sharing gateway that let an outsider take over the whole appliance with no credentials at all.

Start with Cisco. CVE-2026-76504 is an authentication bypass in Catalyst SD-WAN Manager — the console that configures and monitors a company's wide-area network from one place. According to Cisco's own advisory, a flaw in how the management API handles URI encoding lets an unauthenticated attacker reach it with full administrator privileges. Severity: nine point eight out of ten. CISA added it to the Known Exploited Vulnerabilities catalog on September thirtieth, and federal civilian agencies have until this Saturday, October third, to patch. Here's my read: this is the fifth actively exploited SD-WAN zero-day Cisco has disclosed this year alone. At some point a pattern like that stops being about one bug and starts being about how that product gets built and tested — if you run SD-WAN Manager, don't wait for your next change window.

Next up, Kiteworks. The company's Email Protection Gateway — an appliance a lot of regulated organizations use to filter and secure sensitive email — had a maximum-severity flaw reported through its own bug bounty program. BleepingComputer reports the bug, tracked as CVE-2026-54154, chained three separate weaknesses — a path traversal flaw, a code injection flaw, and a missing authentication check — into one attack that let an outsider run code on the appliance and ultimately take it over completely, no password required. Kiteworks has patched it in version nine point four point one. My take: no single one of those three flaws sounds catastrophic in isolation. Chained together, they are. That's exactly why a senior engineer reviews a vulnerability disclosure for the whole attack path, not just the headline severity score of each individual finding.

Different vendors, same lesson: the systems you trust to sit at your network's edge are the ones that get probed hardest, and patching them has to be the fastest SLA in the building, not the slowest.
