Current Events

The Vanna.AI Prompt-Injection-to-RCE Flaw

Picture an AI tool built to let anyone type a plain-English question and get back a chart of their company's own data -- no SQL required. Now picture that same plain-English question box as the exact place an attacker drops a line of Python that runs on your server. That's what security researchers at JFrog found in an open-source tool called Vanna-dot-AI in 2024. Here's how it actually happened.

Vanna is a text-to-SQL library: you ask it a question in natural language, a large language model turns that question into SQL, Vanna runs the SQL against your database, and then -- by default -- it visualizes the results as a chart using a library called Plotly. According to JFrog's own disclosure and the resulting CVE, CVE-2024-5565, that visualization step is where the flaw actually lived, not the SQL-generation step everyone was watching. Vanna's "ask" function, with its "visualize" option left at its default of True, has the LLM generate Plotly charting code directly from the user's prompt, and then executes that generated code on the host.

Here's the chain, step by step. An attacker doesn't need a password or network access -- they just need to get text into that question box, directly or through any data the LLM ingests. That text can smuggle instructions telling the model to generate, not a chart, but arbitrary Python -- the kind of code that can run shell commands. Vanna then executes exactly what the model handed back, with no distinction between "code the model wrote to draw a chart" and "code an attacker wrote to compromise the host."

Root cause, in one sentence: a feature that was supposed to turn an LLM's output into a chart instead turned that output directly into executed code, and nothing stood in that path to check what it actually was before running it.

What contained it, and this is the senior detail worth naming: JFrog disclosed the flaw responsibly and got it a CVE and a public National Vulnerability Database record, rather than this surfacing first as an active exploit in the wild. Vanna's own response, though, is itself a limit worth saying out loud -- the public GitHub security advisory for this flaw lists no patched software version for the affected releases. Vanna's fix was guidance: documentation warning that this feature can execute arbitrary code, and a recommendation to sandbox it or disable visualization entirely, not a code change that closes the hole by default.

So what does that mean for you? A senior engineer treats any point where an LLM's output gets executed -- as code, as a shell command, as a database query -- as untrusted input, no different from a web form, and never assumes "the AI generated it" means it's safe to run directly. On a RHEL and Podman lab, that means any LLM-integrated agent that can generate and run code does so inside a locked-down, least-privilege container -- read-only root filesystem, no network, capabilities dropped -- so that even a successful prompt injection has nowhere to go.

  • An independent researcher corroborated the finding. Tong Liu's separate discovery of the same bug through Huntr, reported after JFrog's disclosure, is the kind of independent confirmation that gives a vulnerability report more weight.
  • Say the limit of that out loud. Senior Security Advice

Enable auditd and Forward Every Host's Audit Logs to a Central Server

The Advice

Turn on the Linux audit daemon, auditd, on every server you run, and forward its logs off the host to a central log server the moment they're written.

Why It Matters

auditd keeps a kernel-level record of security-relevant events — logons, privilege escalation, account changes, access to sensitive files — that's separate from and more trustworthy than application logs, because it comes straight from the kernel instead of from software an attacker might control. The gap most teams miss is where that record lives. If audit logs sit only on the host that generated them, an attacker who gets root can simply delete the evidence of what they did, and incident responders are left reconstructing a breach with no record of it. DISA's security guidelines for Red Hat Enterprise Linux are explicit about this exact failure mode: audit records have to be off-loaded to a separate system, because information stored in one location is vulnerable to accidental or deliberate deletion. This is a recurring theme in breach post-mortems — incidents where local log tampering extended the unknown dwell time because there was no independent copy of what actually happened on the box.

How to Implement It

  1. Verify auditd is active on every host, not just installed — systemctl status auditd. DISA's STIG for RHEL 10 flags a stopped audit service as a finding on its own, regardless of configuration.
  2. Define what actually gets logged, per NIST SP 800-53's AU-2 control: identify the specific event types that matter for your risk model — logon/logoff, privileged command use, account creation and modification, kernel module loads — rather than logging everything or relying on defaults.
  3. Forward records off the host immediately by pointing rsyslog at a remote log aggregator (the @@ TCP syntax in rsyslog.conf, or audisp-remote on older releases), and set name_format = hostname in auditd.conf so every record can be tied back to the system it came from.
  4. Verify forwarding is actually working, not just configured: trigger a known auditable event on the host — switching to root is a simple one — then go confirm that exact record landed on the central server. A line in a config file proves nothing on its own.
  5. Lock down the central log store itself: write-once retention, access limited to the security team, and no path for a compromised host to reach back and edit what it already shipped. Centralizing logs only helps if the attacker can't follow them there.

The Pushback You'll Hear

"auditd is noisy and burns disk space." The senior-engineer rebuttal: that's a tuning problem, not a reason to leave it off. AU-2 exists precisely so you choose the event types that matter instead of logging blindly, and once records ship off-host immediately, local disk pressure stops being the constraint anyway. A short tuning cycle is a cheap cost. Finding out mid-incident that the only record of what happened was sitting on the box the attacker already owned is not.

Tech News

A firewall's management console just became a root shell for attackers — using nothing more than credentials that already exist on plenty of well-run networks. That's the headline out of Palo Alto Networks this week, and it's not the only administrative interface under fire right now. Two stories tonight: a firewall flaw CISA gave federal agencies just three days to fix, and a backup platform whose own vendor patch didn't actually work the first time.

Start with Palo Alto Networks. According to the company's security advisory, confirmed by BleepingComputer and CSOonline, a code injection flaw in the PAN-OS management interface — tracked as CVE-2026-0322 — lets an attacker who already holds valid, high-privilege credentials and network reach to that interface run code as root on the firewall itself. Palo Alto rates it 8.6 out of 10 and describes exploitation so far as "very limited," but CISA still added it to the Known Exploited Vulnerabilities catalog on October 14th and gave federal agencies until October 17th — three days — to patch. Here's the detail worth sitting with: this isn't an internet-facing bug. The attacker needs credentials and reachability to the management plane first. A senior engineer would read that as proof that "it requires a login" and "it's safe" are two separate claims, because once someone gets those credentials — through phishing, password reuse, or a breach somewhere upstream — the interface built to control the firewall becomes the easiest way to own it completely.

Next up, a backup platform where the first fix didn't hold. According to Bitdefender's technical advisory, backed by BleepingComputer and The Hacker News, attackers have been chaining two flaws in Ahsay's AhsayCBS backup console — an authentication bypass and a separate command-injection bug — to get system-level code execution, then dropping web shells and a disguised cryptocurrency miner on compromised servers since around October 7th. Ahsay shipped a patch on October 10th. Researchers at Huntress found it didn't fully close either hole, and Ahsay had to ship a second hotfix. My take: a backup console deserves more scrutiny than almost any other system you run, because it's often the one place holding your last clean copy of everything else — and a vendor's first patch turning out not to be the real patch is exactly the gap a ransomware crew is built to walk through.

Whether it's a firewall's console or a backup platform's, the systems you trust to control and protect everything else are now the systems attackers go after first. Treat every "patched" claim on an administrative interface as a hypothesis to verify, not a fact to file away.
