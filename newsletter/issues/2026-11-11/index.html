Current Events

The tj-actions/changed-files Supply Chain Compromise

A single compromised GitHub Action quietly rewrote what more than twenty-three thousand software repositories were running, and for a few hours in March of 2025, anyone who knew where to look could read live secrets straight out of public build logs. Here's the story of tj-actions changed-files, and how a trusted name in CI/CD -- that's continuous integration and continuous delivery, the pipelines that build and test code automatically -- became the way in.

tj-actions slash changed-files is a hugely popular GitHub Action, a reusable job that tells a pipeline which files changed in a pull request. Teams reference it with a short version tag, like "v45," instead of a long commit hash, because a tag is easier to read. On March 14th, 2025, the security firm StepSecurity's monitoring tool flagged something it had never seen before: this trusted action reaching out to an unfamiliar website and downloading a script.

Here's the chain, step by step, according to CISA's advisory and the GitHub Security Advisory tracking this as CVE-2025-30066. An attacker first got into a separate, related open-source project months earlier -- reporting traces that access back to around November of 2024, through a maintainer connection shared with tj-actions. From that foothold, the attacker got write access into the tj-actions repository itself and rewrote its Git tags -- those same friendly version labels -- to point at a new, malicious commit. Any pipeline that referenced the tag rather than a fixed commit hash pulled that malicious code automatically, with zero changes on the user's end, the next time it ran. Once running, the malicious code dumped the memory of the build process, searched it for anything that looked like a secret -- API keys, cloud credentials, tokens -- and printed what it found straight into the pipeline's own log output, which on a public repository is visible to anyone.

Root cause, in one sentence: trusting a mutable Git tag as if it were a fixed, verified piece of code let one compromised account rewrite what tens of thousands of pipelines were actually executing, with nothing checking that the code behind that tag was still the code anyone had reviewed.

Here's what actually held. StepSecurity's outbound-traffic monitoring caught the anomaly the same day, because that destination had never shown up in any prior baseline -- that's the detection that triggered the public warning within hours, not weeks. GitHub pulled the compromised action from its Marketplace and restored a clean version. And organizations that had already pinned their workflows to a fixed commit hash, instead of a tag, were never exposed to the tag rewrite at all -- that one habit fully neutralized the attack for them.

So what would a senior engineer change here? A senior engineer never references a third-party Action -- or any external dependency -- by a floating tag; they pin it to its exact commit hash, so the code that runs today is provably the code that was reviewed, no matter what happens to the tag later. On a lab, that's a concrete, checkable habit: scanning your own GitHub Actions workflows for every "uses:" line still pointing at a mutable tag instead of a full commit SHA, and fixing every one you find.

What Held

  • Commit-SHA pinning fully neutralized the attack for anyone using it. Organizations that already referenced the action by a fixed commit hash instead of a floating tag were never affected by the tag rewrite at all — the single cleanest example in this incident of one control making an entire attack path irrelevant.
  • Independent, same-day egress detection. StepSecurity's Harden-Runner caught the anomalous outbound call within hours because the destination had never appeared in any prior traffic baseline, and that detection — not the project's own maintainers — is what surfaced the compromise publicly on March 14th.
  • A fast platform-level takedown. GitHub pulled the compromised action from the Marketplace and restored clean history once notified, cutting off new exposure without requiring every downstream repository to act first.

Senior Security Advice

Require Phishing-Resistant MFA for Privileged and High-Risk Accounts

The Advice

Require phishing-resistant multi-factor authentication — FIDO2/WebAuthn security keys, passkeys, or PKI-based smart cards like PIV/CAC — on every privileged, administrative, and high-risk account, instead of relying on push notifications, SMS codes, or app-based one-time codes.

Why It Matters

Most organizations that say they have "MFA everywhere" are actually running push-notification or one-time-code MFA, and both are phishable. A fake login page can relay a stolen password straight to the real site and simply prompt the victim to approve a push or type in the six-digit code; the attacker captures the session the instant the user complies. This is the mechanic behind a well-documented incident class: adversary-in-the-middle phishing kits and MFA-fatigue attacks, where a user is bombarded with push prompts until they tap "approve" just to make the notifications stop. Once that one approval lands, the attacker has a live, authenticated session — the same outcome as if MFA had never been enabled at all. Phishing-resistant methods close this gap because the authentication is cryptographically bound to the real website's origin; a cloned phishing page simply cannot complete the exchange, no matter how convincing it looks.

How to Implement It

  1. Inventory every account with administrative, financial, or data-export privilege, and every account tied to identity, cloud, or code-signing infrastructure — these go first, not last.
  2. Issue FIDO2 security keys or enable platform passkeys for those accounts; in a DoD or federal environment, PKI-based PIV/CAC authentication serves the same phishing-resistant role and is often already mandated.
  3. Configure the identity provider's conditional access or authentication policy to reject weaker factors — SMS, voice call, and plain push approval — for any account in that privileged tier, not just to offer the strong factor as an option.
  4. Verify enforcement by testing from an account that should be blocked: confirm a login attempt using only a password-plus-push fails outright for a privileged account, and check the sign-in logs to confirm the authentication method actually used matches policy, not just that a factor was "required."
  5. For accounts that cannot yet move to hardware-backed authentication, apply number-matching MFA as a CISA-recommended interim control and put a firm migration date on the exception.

The Pushback You'll Hear

"We already have MFA on everything, so we're covered." Having a second factor enabled and having a phishing-resistant second factor are different controls with very different failure modes. Push and OTP-based MFA still stop basic password-only attacks, but they were never designed to survive a real-time phishing relay, and that's precisely the technique attackers have shifted to because it works against exactly this kind of MFA. The fix isn't more MFA — it's the right kind of MFA on the accounts that matter most.

Tech News

A password bug that's been sitting inside OpenSSH for ten years just got weaponized — and if your Linux boxes run on Alpine or anything else built on musl, you need to hear this tonight. The Cybersecurity and Infrastructure Security Agency, or CISA, confirmed it's being actively exploited, with a federal patch deadline that's already ticking. Two stories today: that OpenSSH bypass, and a second flaw from the same government advisory that hands attackers full admin rights with nothing but a crafted message.

Here's what happened. Researcher Özgün Kültekin at the security firm Wakefield found that OpenSSH's sshd — the piece of software that handles every incoming Secure Shell login — would let someone log into an account that has no password set at all, but only on Linux systems built on the musl C library instead of the more common glibc. Alpine Linux is the best-known example, and Alpine happens to be the default base image for a huge share of container builds. Reporting says this bug has been sitting in that code for roughly a decade; it just never got noticed until now. OpenSSH shipped a fix, version 10.6p2, on November 5th, and CISA added it to the Known Exploited Vulnerabilities catalog on November 9th, with a November 12th deadline for federal agencies — that's basically right now. Here's my read: this is exactly why you patch your dependencies, not just the services sitting on top of them. If you can't patch today, turn off password authentication in your SSH configuration and require keys instead — that one setting closes the hole completely.

Next up — the second flaw in that same CISA advisory, and it's just as serious if you run file-transfer infrastructure.

IBM disclosed CVE-2026-123218 in Aspera Faspex, software enterprises use to move large files securely. According to IBM's own security bulletin, a user who's already logged in with ordinary access can craft one specific message that slips past the application's authorization checks and hands them full administrative control. CISA added this one to the same November 9th catalog update, same November 12th deadline. My take: this is a textbook authorization failure, not an authentication failure — the system correctly identified who the user was, it just failed to check what that user was actually allowed to do next. Those two checks get treated as one control far too often, and attackers count on it.

So here's the through-line tonight: knowing who someone is was never the hard part — proving what they're allowed to do with that identity is.

If you're running Alpine or any musl-based Linux host, confirm you're on OpenSSH 10.6p2. If Aspera Faspex is anywhere in your file-transfer stack, get it patched before Thursday's deadline.
