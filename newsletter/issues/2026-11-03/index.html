Current Events

GitHub Copilot Prompt Injection RCE

An AI coding assistant that can write files to your project folder without asking first sounds convenient -- until someone works out how to make it write the one file that turns off every safety check it has. That's exactly what happened to GitHub Copilot inside Visual Studio, and the fix for it tells you something bigger about what happens when you let an assistant act on your behalf.

GitHub Copilot is Microsoft's AI coding assistant, built into Visual Studio and Visual Studio Code, and it can read a project's files, suggest code, and in some configurations, make changes directly. According to Microsoft's own security advisory, security researchers disclosed CVE-2025-53773 in August of 2025: a flaw that let an attacker's hidden instructions -- planted in a source code comment, a GitHub issue, or even a web page Copilot happened to read while helping with a task -- get treated by Copilot as something to act on, not just text to summarize.

Here's the chain. Those hidden instructions told Copilot to edit one specific file in the project: a configuration file called dot-vscode-slash-settings-dot-json. Buried in there is a setting that controls whether Copilot has to stop and ask you before it runs a command on your machine. Multiple technical write-ups describe attackers flipping that setting to true -- turning on what researchers nicknamed "YOLO mode" -- which switches off every one of those confirmation prompts. Once that setting was live, Copilot would execute follow-on commands without asking permission at all, which is how a text-only prompt injection turned into actual code execution on the victim's own machine.

Root cause, in one sentence: Copilot treated its own safety switch as just another file it was allowed to edit on someone else's say-so, instead of treating that specific setting as something only the human at the keyboard should ever be able to change.

What actually held: Microsoft's fix, shipped in Visual Studio 2022 version 17.14.12, closed the specific path that let an untrusted prompt flip that setting without the user's own action. It's rated high severity, not maximum, precisely because the attacker still needed Copilot to ingest the malicious instruction in the first place -- this wasn't a flaw a stranger could fire at a machine with zero interaction from the user or their tools.

So what does this mean for how a senior engineer treats agentic tools in their own environment? A senior engineer treats any setting that disables a human-in-the-loop confirmation as something that should never be writable by the tool itself -- only by the human, through a separate, protected path. On a RHEL or Podman lab, that means practicing exactly that: locking down a configuration file so the application reading it cannot also be the thing rewriting it.

Control Failures

1 Copilot treated instructions embedded in untrusted content (source comments, issues, web pages) as commands to act on rather than data to summarize. SI-10 — Information Input Validation
2 A security-relevant configuration setting (chat.tools.autoApprove) could be modified by the AI tool itself rather than being restricted to direct user action. CM-3 — Configuration Change Control
3 Once the auto-approve setting was enabled, no secondary control required human confirmation before executing shell commands. AC-3 — Access Enforcement
4 The feature that disables confirmation prompts ("YOLO mode") existed as an available, discoverable setting rather than being restricted by default. CM-7 — Least Functionality
5 No distinction was enforced between code Copilot was asked to write and instructions Copilot found while reading project or web content on the user's behalf. AC-6 — Least Privilege

What Held

  • The attack still required user interaction. Copilot had to actually ingest the malicious content before anything could happen — this kept the flaw at High severity rather than zero-click maximum severity, and let Microsoft ship a targeted fix rather than an emergency out-of-band patch.
  • Microsoft's fix targeted the trust boundary, not just the symptom. Rather than only telling users to disable auto-approve, the patch closed the path that let an untrusted prompt flip that setting in the first place.
  • The flaw was caught and reported before mass exploitation. Public reporting describes no confirmed widespread exploitation in the wild, which is what disclosure-before-abuse is supposed to buy an ecosystem.

Senior Security Advice

Enable CloudTrail in Every Region and Protect the Logs

The Advice

Turn on a multi-Region CloudTrail trail with log file validation in every AWS account, and lock the log bucket down so no one on the team — including the admins — can quietly edit or delete what it records.

Why It Matters

CloudTrail is the record of every API call made in an AWS account: who created a user, who opened a security group, who touched a bucket. Without it turned on everywhere, an attacker who gets into an account during business hours looks identical to an engineer doing their job, because there's no log to tell the difference. Without log file validation and a locked-down destination bucket, an attacker who does get in can simply edit or delete the trail to erase their own tracks — stopping or tampering with cloud audit logging after initial access is a well-documented step attackers take specifically because so many accounts never check whether logging is still running.

The failure mode isn't dramatic until the day it is: a security team investigating a suspicious login discovers CloudTrail was quietly disabled in one region three weeks earlier, and now there's no record of what happened in between. A single-region trail has the same blind spot — anything that happens in a region nobody set up logging in simply never gets written down.

How to Implement It

  1. Create (or confirm) at least one multi-Region trail per account that captures management events, so activity in every region — including ones your team never deliberately uses — gets logged by default.
  2. Turn on log file validation on every trail. This adds digitally signed digest files that hash-chain each log, so any after-the-fact edit or deletion of a log is detectable, not invisible.
  3. Send the logs to a dedicated S3 bucket with versioning on, and write a bucket policy that denies delete and overwrite actions to everyone except a narrow break-glass role — the people running the trail should not be the people who can erase it.
  4. Forward the trail to CloudWatch Logs (or your SIEM) and set a CloudWatch alarm on StopLogging and DeleteTrail API calls, so disabling the trail itself generates an alert instead of silence.
  5. Verify it's actually working, not just configured: run aws cloudtrail get-trail-status and confirm IsLogging is true, check that digest files are landing in the bucket roughly hourly, and use an AWS Config rule (cloudtrail-enabled, cloud-trail-log-file-validation-enabled) to continuously flag any account that drifts out of compliance.

The Pushback You'll Hear

"Logging everything in every region is noisy and racks up cost for events we'll never look at." The rebuttal: management-event logging on a multi-Region trail is inexpensive compared to the cost of an unexplained incident, and you're not paying to read every event by hand — you're paying so the record exists when you need it. If cost is a real constraint, scope down expensive data-event logging (like S3 object-level access) to the buckets that actually need it, but management events stay on everywhere, because that's the layer that shows account takeovers and privilege changes — exactly what you can't afford to lose.

Tech News

If you run a Cisco firewall or an Ivanti VPN appliance, the device sitting at your network's front door just became this week's biggest liability — and in one case, there's still no setting you can change to fully work around it. Two stories tonight: a Cisco firewall flaw that lets an attacker crash the device with no login at all, and two more zero-days piling onto an Ivanti Connect Secure attack chain that was already under active exploitation.

Start with Cisco. According to Cisco's own security advisory, corroborated by Network World and Tech Insider, the company patched CVE-2026-76418 in late October — a flaw in the Remote Access SSL VPN service inside its Secure Firewall ASA and Firepower Threat Defense software. It scores 8.6, needs no valid login at all, and lets an unauthenticated attacker remotely force the device to reboot. Cisco says it's already being exploited in the wild, there's no workaround beyond disabling secondary authentication on the affected tunnel groups, and this is the second Cisco firewall VPN zero-day since August. Here's my read: a denial-of-service bug on a VPN gateway isn't just an inconvenience — that gateway is often the only thing standing between the internet and your internal network, and a device that can be forced to reboot on command is a device an attacker can use to mask a second, quieter move.

Next up, turning to Ivanti. According to Help Net Security's reporting on CISA's own advisory, the agency added two more flaws, CVE-2026-111357 and CVE-2026-118527, to its Known Exploited Vulnerabilities catalog this week. These extend an attack chain first disclosed in October, when a privilege-escalation flaw let an unauthenticated attacker work toward full root access on Connect Secure appliances. Federal agencies had until today to patch one of the two; the other carries a November 13th deadline. My take: when a vendor keeps turning up new members of the same attack chain weeks after the first disclosure, that's usually not a sign the first patch failed — it's a sign the investigation correctly kept digging instead of declaring victory after one fix.

Tonight's thread: the devices built to guard your network's edge are exactly where attackers are spending their time right now, and the fix in both cases is unglamorous — patch on CISA's clock, not your own.
