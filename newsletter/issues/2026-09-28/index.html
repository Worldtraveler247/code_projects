Current Events

The GitLab.com Database Deletion Incident

Here's a story every senior sysadmin should have memorized: how one engineer, at eleven at night, took down one of the internet's biggest code-hosting platforms — and then found out every safety net the company thought it had was already gone. Here's how it actually happened.

On January 31st, 2017, GitLab-dot-com was under unusual load, and an on-call engineer was trying to fix a secondary database that had fallen out of sync with the primary. Replication between the two had already silently broken hours earlier, because write-ahead-log archiving wasn't enabled, so the primary was discarding data the secondary still needed before it could catch up. The engineer's plan was simple: wipe the empty data directory on the out-of-sync secondary, then resync it from the primary. He ran "remove, recursive, force" on what he believed was that secondary host. Within a couple of seconds he realized he was actually connected to the live production primary, and killed the command — but by then, of roughly three hundred gigabytes of production data, only about four and a half gigabytes were left.

Root cause, in one sentence: a single destructive command was one keystroke away from live production, with no confirmation prompt, no peer review, and no clear way to tell which host you were actually on.

Here's the part that made this a career-defining incident instead of just a bad night. When GitLab turned to restore from backup, they found all five of their backup and recovery mechanisms had failed. The scheduled database exports had been silently erroring out for weeks, because they were running against the wrong database version — and the emails warning about it were being silently rejected by a mail-server misconfiguration. There was no real snapshot schedule for the production database. Cloud disk snapshots had never been turned on, to save money. The file-level backups amounted to a few empty bytes. And replication — the one live safety net — was the very thing that had just failed.

What actually held was almost an accident. Hours earlier, an engineer had taken a manual disk snapshot of the database for an unrelated staging refresh. That snapshot, about six hours old, was the only usable copy of anything, and it's what GitLab restored from after roughly eighteen hours of downtime. I want to be honest about that: that wasn't a designed control holding the line — it was luck standing in for one. What was a real control was GitLab's own transparency afterward: a live public incident document updated in real time, and a full engineering postmortem days later, naming every failure without spin.

Here's what a senior engineer, or a senior ISSO, would change in how they work. Any command that can delete production data needs a second set of eyes, or a hard confirmation step, before it runs — full stop. In a RHEL 9 lab with Podman, that means actually writing a backup verification job: take a database backup, then prove on a separate host that you can restore from it on a schedule, instead of trusting that a quiet cron job for months actually means anything.

What Held

  • Application data survived where database data didn't. Git repositories and wikis are stored separately from the PostgreSQL database, so code and wiki content were never touched by the deletion — a real architectural separation, not luck.
  • Be honest about the rest: this was closer to luck than to defense-in-depth. The snapshot that actually saved the data was not a designed backup control — it was one engineer's incidental habit, taken hours earlier for an unrelated reason. Naming that plainly, instead of dressing it up as a working control, is itself the senior read on this incident.
  • GitLab's own transparency and incident-response discipline held. Publishing a live public incident document in real time and a full, unsparing postmortem ten days later is a real organizational control — it's what turned a near-catastrophic data-loss event into a trusted industry case study instead of a cover-up.

Senior Security Advice

Require a Software Bill of Materials for Every App You Ship or Buy

The Advice

Require an accurate, signed Software Bill of Materials for every application you build or buy, and actually check it against known vulnerabilities before that software reaches production.

Why It Matters

Modern software is mostly other people's code. A typical application pulls in dozens of open-source libraries, and each of those pulls in more, several layers deep. If nobody tracks that chain, a team has no way to answer a simple question fast: "do we run the vulnerable component?" That gap is what turned the Log4Shell disclosure in December 2021 into a weeks-long fire drill industry-wide. The flaw wasn't in software most teams wrote — it was buried three or four dependencies down inside a logging library almost nobody could name from memory, and organizations without an inventory of their own components spent days manually grepping build artifacts just to find out if they were exposed. A Software Bill of Materials, or SBOM, is that inventory: a structured, machine-readable list of every component in a piece of software. Executive Order 14028 already requires one for anything sold to the U.S. federal government, and CISA's newly updated 2026 Minimum Elements guidance raises the bar further, now requiring the SBOM itself to carry a digital signature so recipients know it hasn't been tampered with. Without this control, a single newly disclosed vulnerability in a widely used library becomes an open-ended hunt across every application your organization runs.

How to Implement It

  1. Bake SBOM generation into the CI/CD pipeline with a tool like Syft or CycloneDX so an SBOM is produced automatically for every build artifact — never a manual, skippable step.
  2. For purchased or vendored software, make an SBOM a contract requirement before deployment, aligned to CISA's 2026 Minimum Elements — most vendors selling into the federal space already produce one under EO 14028.
  3. Feed every SBOM into a component-tracking tool, such as Dependency-Track or Grype, that continuously matches your inventory against the National Vulnerability Database and CISA's Known Exploited Vulnerabilities catalog, so a new CVE in a library you already shipped triggers an alert without a new scan.
  4. Verify the control is real, not decorative: periodically pull one build's SBOM and manually diff it against the actual dependency tree, confirming transitive dependencies are captured — a signed SBOM that's missing half the components is worse than none, because it creates false confidence.
  5. Store every SBOM centrally, versioned against the release it describes, so when the next Log4Shell-scale event hits, the question "where do we use this component" is a database query that takes minutes, not a manual audit that takes days.

The Pushback You'll Hear

"We don't have time to bolt another compliance artifact onto every build." The senior-engineer rebuttal: SBOM generation is a one-time pipeline step that runs automatically after that, costing seconds per build. Weigh that against the alternative — when the next critical library vulnerability drops, teams without an SBOM spend days manually auditing every application while teams with one answer the exposure question before the incident call even ends.

When a Playbook Should Not Be the Tool

Ansible is a tool that lets you describe the state you want a bunch of servers to be in, written out in a file called a playbook, and it goes and makes every server match that description. Most people who are new to automation treat it like a hammer -- once they learn it, every task in front of them starts looking like a nail. A senior engineer knows that's exactly backwards.

Here's the plain version of the problem. A playbook is built for repeatable, predictable work -- configuring a hundred servers the same way, over and over, forever. It is not built for a one-time, high-stakes, unpredictable situation. Think about an active production outage at two in the morning. Someone suggests writing a quick playbook to fix it across the fleet. That sounds efficient. It's actually dangerous, because you're now debugging your fix and your automation tool at the same time, under pressure, against systems that are already unhealthy.

Here's why that matters in production, and the senior take: a junior engineer sees automation as an unqualified good -- more automation always equals more professional. A senior engineer treats automation as a tool with a specific job, and knows the emergency, one-off, "I need to see exactly what's happening on this one box right now" situation calls for a human at a terminal, not a playbook running across forty servers unsupervised. Automate the boring, repeatable stuff. Keep a human in the loop for anything novel or high-blast- radius, because a playbook does exactly what you tell it, exactly that fast, on every single target -- including your mistakes.

Think of it like a form letter versus a phone call. A form letter is perfect for sending the same renewal notice to ten thousand customers. It is a terrible way to tell one specific customer their account got compromised at midnight. Same idea: right tool, wrong situation, and the cost of getting that choice wrong scales with how many machines are listening.

A natural way to open this at work: "Before we automate this, is it actually the repeatable case, or is this the one-off we should just walk through by hand first?"

Key Takeaways

  1. A playbook is designed for repeatable, predictable, fleet-wide work — not for one-off, high-stakes changes, because it executes uniformly and fast across every target, mistakes included.
  2. Automating a novel or emergency fix under pressure means debugging the fix and the automation tool simultaneously, which is a worse position than just fixing one box by hand first.
  3. The senior instinct isn't "automate everything" — it's "automate the repeatable, keep a human in the loop for anything high blast radius or unproven."

Reader Question

"If automation is supposed to reduce human error, why would you ever choose to do something by hand instead of writing a playbook for it?"

I'd say automation reduces human error specifically for work you've already proven is safe and repeatable — it doesn't remove the risk of a decision that's still novel or untested, it just executes that decision faster and more consistently, mistakes included. My answer would be that for a one-off or emergency change, I want a human validating the fix on one system first, precisely so the automation I eventually write is automating a change I already know works, not the first draft of one I'm still debugging under pressure.

Tech News

There's a hole in one of the most common remote-access appliances in the enterprise world, and right now, nobody outside the vendor has a fix for it. If your organization runs Citrix NetScaler at the network edge, security researchers say attackers are already inside, using it as we speak. Two stories today: an unpatched NetScaler zero-day with no CVE number yet, and a supply-chain worm that infected open-source code packages and started stealing credentials within hours of going live.

Start with NetScaler. Details of two remote-code-execution flaws in Citrix NetScaler ADC and NetScaler Gateway leaked on September 25th, out of a private pre-notification the Dutch national cybersecurity center sent to a small circle of organizations. Security firm watchTowr and independent researcher Kevin Beaumont confirmed the next day that attackers are actively exploiting both flaws in the wild. Here's what makes this different from a routine zero-day: no patch, no official Citrix advisory, no public proof-of-concept — just live attacks against a device sitting at the edge of the network, handling VPN access, load balancing, and user logins all at once. Citrix says a fix is coming early this week, according to SecurityWeek's reporting. Here's my read: even once that patch lands, it only locks the door — it doesn't tell you whether someone already walked through it. A senior engineer's response to a zero-day like this isn't "wait for the patch." It's assume compromise on anything internet-facing right now, and start hunting for what already got in.

Which brings us to the second story. Researchers at Socket and SC World reported this week that someone hijacked legitimate open-source packages published by the AI memory company MemTensor — one on npm, the package manager most JavaScript projects pull code from, and one on PyPI, its Python equivalent — and slipped in a credential-stealing program called sckit. It runs on Windows, Linux, and Mac, and hunts for cloud credentials, source-code access tokens, and anything sitting inside a continuous-integration job. Worse, researchers say it can self-propagate, copying itself into other packages and GitHub projects automatically. My take: this is exactly why a senior engineer treats every third-party package as untrusted code running with your permissions, not a free library — pin your dependency versions, scan before you build, and never let a CI pipeline hold more credentials than the job in front of it needs.

Both stories tonight point at the same gap: trust that isn't verified — whether it's a device sitting at your network edge or a package sitting in your build pipeline — is exactly where attackers go first.
