Current Events

The Storm-0558 Signing Key Breach

In the summer of 2023, a Chinese state-linked hacking group read email out of the U.S. State Department and Commerce Department for weeks, using a Microsoft signing key that should never have worked outside a personal Outlook.com login. Here's how it actually happened.

Microsoft runs two separate trust systems -- one signing key for consumer Microsoft accounts, like Outlook.com, and a completely different one for enterprise Azure Active Directory accounts, like a federal agency's Exchange Online tenant. According to Microsoft's own investigation, a group it tracks as Storm-0558 obtained an inactive Microsoft account consumer signing key. They then hit a validation gap in the API Exchange used to mint access tokens for Outlook Web Access. Microsoft's own account of the root cause is specific: the Exchange authentication team assumed the Azure AD SDK checked which authority had issued a token by default. It didn't, and nobody had added that check explicitly. So a consumer-only key forged tokens that Exchange Online accepted as valid enterprise logins.

Here's the chain. Starting around May 15th, 2023, Storm-0558 used forged tokens built with that stolen key to log into Outlook Web Access and Outlook.com mailboxes at roughly two dozen organizations, without ever touching a password. Microsoft's own systems didn't catch it. The State Department's security operations center found it first, in mid-June, using a custom detection rule built on a premium audit log called MailItemsAccessed -- a log tier that most of the other affected organizations didn't even have at the time, because it sat behind a higher licensing tier.

Here's the root cause in one sentence: an enterprise identity system trusted a token without checking which signing authority actually issued it, because a team building on top of that system assumed a check existed that didn't.

And here's the part that stays open. Microsoft's September 2023 report proposed that the key leaked into a crash dump and then into a compromised engineer's account. The federal Cyber Safety Review Board investigated further and stated, on the record, that Microsoft has no logs or evidence supporting that theory. So as of the Board's April 2024 report, exactly how the key left Microsoft's environment is still not publicly confirmed.

Here's what held. The State Department's own premium logging and a custom detection rule is what actually surfaced this, not Microsoft. Once notified, Microsoft revoked the compromised key within days and fixed the validation gap. And under pressure from CISA and the Review Board, Microsoft made that premium audit-logging tier free for federal customers going forward, closing the visibility gap that let this run for roughly six weeks before anyone caught it.

Here's what a senior engineer, or a senior ISSO, would change in how they work because of this. Never assume a vendor's identity library validates issuer and scope correctly by default -- test it directly. And object-level audit logging that can tell you exactly what an attacker touched can't be treated as an upsell feature; a senior engineer standing up a RHEL-hosted AWS environment would enable detailed, per-object audit logging as a day-one baseline control, not something bolted on after an incident forces the vendor's hand.

What Held

  • The State Department's own premium audit logging and a custom detection rule caught what Microsoft's systems didn't. The "MailItemsAccessed" log and an internally built alert rule is the actual reason this surfaced at all, not vendor-side detection.
  • Microsoft revoked the compromised key within days of notification, cutting off further token forgery using that key across every tenant, not just the ones already known to be affected.
  • CISA and the FBI moved fast on a joint advisory (AA23-193A) giving every other Exchange Online customer concrete logging and detection guidance within a day of public disclosure.
  • Sustained public and regulatory pressure — from CISA and the Cyber Safety Review Board — forced a structural fix, not just a patch: Microsoft made the premium audit-logging tier free for federal customers, closing the exact visibility gap that let this run six weeks undetected.

Senior Security Advice

Bake a Hardening Baseline Into Every Build Image

The Advice

Every server and container image should be built from a CIS Benchmark or DISA STIG hardening baseline, not hardened by hand after the fact, and every image should be scanned against that baseline before it ships.

Why It Matters

A default operating system install is tuned for compatibility, not security: unnecessary services run, permissive file permissions sit untouched, and weak defaults wait to be found. NIST SP 800-53's configuration management family requires exactly this discipline - control CM-2 calls for a documented baseline configuration for each system, and CM-6 requires that baseline reflect the most restrictive mode consistent with operations, with any deviation tracked and approved rather than left to drift. The Center for Internet Security (CIS) and the Defense Information Systems Agency (DISA) publish the actual settings that satisfy that requirement: CIS Benchmarks are consensus-built configuration guides covering operating systems, cloud platforms, containers, and databases, and DISA's Security Technical Implementation Guides (STIGs) are the mandatory hardening standard across the Department of Defense, spanning roughly 500 guides and 20,000 individual settings. Without a baked-in baseline, hardening becomes a manual checklist that one engineer runs once and nobody repeats - and the incident class this causes is the unremarkable one: a box gets built, a hardening step gets skipped or reverted during a later change, and months later that one missed setting - an open management port, a default credential, an unneeded service - is the foothold an attacker actually used.

How to Implement It

  1. Pick the baseline that matches the environment - a CIS Benchmark for general enterprise systems, or the applicable DISA STIG profile for anything touching DoD or federal work - and apply it to the golden image or base container layer, not to servers after they're already running.
  2. Automate the hardening itself with a configuration management tool (Ansible, Chef, or a vendor-provided hardened image) so every new instance launches compliant instead of needing a post-boot fix-up pass.
  3. Scan every build against the baseline using an SCAP-based tool - Red Hat's own documentation for RHEL points to OpenSCAP and the oscap command-line utility for exactly this - and fail the build pipeline if the scan finds a non-compliant setting.
  4. Track and approve any deviation from the baseline explicitly, per CM-6, instead of letting exceptions accumulate silently; an undocumented deviation is really just drift wearing a disguise.
  5. Verify the control is actually working, not just applied once: re-scan running production systems on a recurring schedule (not only at build time) and treat a system that has drifted out of compliance as a finding, the same way an open vulnerability would be tracked and remediated.

The Pushback You'll Hear

"STIGs break things - services stop working after we apply them." The senior-engineer rebuttal: that's what tailoring and testing are for, not a reason to skip hardening entirely. Both CIS Benchmarks and DISA STIGs are designed to be tailored to documented, approved exceptions when a specific setting genuinely conflicts with an operational need - the failure mode isn't hardening breaking things, it's hardening never being applied in the first place and nobody finding out until an audit or an incident does.

Senior Talk Tracks

Error Budgets

Let's talk about something a lot of engineers hear in an SRE meeting and nod along to without really getting: the error budget.

Plain English first. An SLO -- short for service level objective -- is the reliability target a team commits to, something like "this service will work correctly 99.9 percent of the time, measured over a rolling 30 days." That leftover zero-point-one-percent is the error budget: the amount of unreliability the team is officially allowed to spend. For a 99.9 percent target over 30 days, that works out to a little over 43 minutes of downtime or errors before the team has broken its promise.

Here's why that matters in production, and where it gets interesting. Most junior engineers hear "error budget" and assume its whole job is to cap how bad things are allowed to get -- a ceiling on failure. That's only half the idea. The real point of an error budget is to be a currency for risk. If a team still has budget left, that's a green light to ship faster, push a riskier deploy, run an experiment -- because the organization has decided some instability is an acceptable price for moving quickly. But the moment that budget is spent, the deal changes: no new feature launches, no risky deploys, all hands go to reliability work until the budget resets. A team that never runs out of error budget usually isn't a reliability success story -- it's often a sign they're being too cautious and shipping slower than they need to.

Think of it like a household's monthly eating-out budget. Some months you're under budget, so you try the new restaurant that might be a miss. Once you've blown through the budget, you stop taking chances and just cook the meals you know work, until next month resets the number.

A good way to bring this up at work: "Do we actually enforce a feature freeze when we blow through our error budget, or is that number just sitting on a dashboard nobody acts on?"

Key Takeaways

  1. An error budget is simply one minus the SLO (service level objective) — for a 99.9 percent target over 30 days, that's about 43 minutes of allowed downtime or errors.
  2. The error budget's real purpose is to license risk-taking, not just cap failure — spending it on faster releases is the intended use, not a warning sign by itself.
  3. An error budget only changes behavior if running out actually triggers a feature freeze and a shift to reliability work — otherwise it's a vanity metric.

Reader Question

"If a team never comes close to using its error budget, is that actually a good outcome?"

No, I'd treat that as a signal, not a win — if the budget goes unused month after month, the team is probably being overly cautious, shipping too slowly, or setting an SLO looser than what the business actually needs. I'd rather see a team spend most of its budget on deliberate, well-tested risk than sit on a pile of unused reliability margin, because the whole point of the budget is to be spent on moving faster, not hoarded.

Tech News

Cisco just landed two zero-days in CISA's Known Exploited Vulnerabilities catalog inside 48 hours, and one is a maximum-severity bypass in the platform a lot of federal and defense networks use to decide who gets on the network at all. When the system that establishes trust becomes the thing under attack, everything behind it inherits that risk. Coming up: the Cisco identity bypass, a second Cisco zero-day from the same week, and a credential-harvesting campaign hitting exposed developer servers.

Start with CVE-2026-76460, in Cisco Identity Services Engine and its Passive Identity Connector, versions 3.0 through 3.5, carrying a CVSS — Common Vulnerability Scoring System — score of ten out of ten. According to Cisco, insufficient authentication control on an API endpoint lets an unauthenticated attacker send one crafted request and bypass the web management interface entirely. CISA added it to the catalog on September 16th and gave federal agencies three days, until September 19th, to patch. My read: this is the network access control layer deciding which device gets on the network — exactly the identity infrastructure a defense contractor runs at the perimeter. A senior engineer treats a perfect-ten score there as a stop-the-line event, not a ticket in the queue.

Next up, same vendor, same week. CVE-2026-76461, CVSS nine-point-eight, is a SQL injection in Cisco Secure Email Gateway's AsyncOS software. One crafted email triggers it, no login required, and it ends in root command execution. Cisco disclosed it and CISA added it to the catalog the same day, September 14th — meaning it was already being exploited before anyone outside Cisco knew it existed. Two entries from one vendor in a week is a prioritization test: the mail gateway and the identity broker both hand an attacker a foothold with zero credentials, so they jump the queue first.

Which brings us to CVE-2026-39364, CVSS eight-point-two, in the Vite development server that sits on plenty of engineer laptops and continuous-integration runners. Query-parameter tricks let an unauthenticated attacker pull files the server should block. F5 tracked over eight hundred attacks and roughly thirty-two thousand scan events in a month, hunting for environment files, Amazon Web Services and Azure credentials, and Terraform state files. My read: a dev server was never meant to face the internet — this is what happens when a sprint's convenience outlives the sprint, and the file describing your whole cloud footprint becomes public inventory.

All three stories share one failure mode: treating the systems that establish trust — identity, mail, or the build pipeline — as lower priority than what they protect.
