Current Events

The Microsoft Power Apps Portals Data Exposure

In August 2021, researchers found that a single Microsoft feature being off by default had quietly exposed 38 million records across 47 different organizations -- including Microsoft's own payroll data. No hacker broke in. The door had just been left open since the feature shipped. Here's how it actually happened.

Power Apps portals is Microsoft's low-code platform for building public-facing web portals -- job-application sites, COVID contact-tracing forms, customer registration pages -- fast, without writing much custom code. Every portal exposes its underlying data through something called an OData feed, a standard way for other programs to query a list of records. Microsoft built a feature called Table Permissions specifically to restrict who could query that feed. The problem: Table Permissions shipped turned OFF by default. Unless a portal's own administrator remembered to turn it on, the feed answered anonymous requests from anyone who knew the URL, no login required.

Security firm UpGuard found the first exposed portal on May 24th, 2021, and spent the next month quietly checking how widespread the pattern was before reporting the full scope to Microsoft's Security Response Center on June 24th. What they found sitting behind that default-open setting: Social Security numbers from job applicants, COVID-19 vaccination appointment data, employee IDs, and -- inside Microsoft's own portal -- payroll email addresses and IDs for over three hundred thousand people. Root cause, in one sentence: a platform-wide default left a sensitive data feed open to the entire internet, and closing it depended on every single customer administrator noticing and acting, which most of them never did.

Here's what changed the outcome. Microsoft didn't just tell the 47 affected organizations to go fix their own settings. They flipped the platform's default itself -- Table Permissions now ships ON -- so every existing and future portal got the secure configuration without depending on an administrator's memory. That's the senior move here: when a security setting depends on thousands of individual admins opting in correctly, the fix isn't better documentation, it's changing what "default" means.

Here's what a senior engineer, or a senior ISSO, would change in how they work. Any platform you administer that exposes an API by default -- an S3 bucket, a database export, an OData feed -- gets audited for what its out-of-the-box setting actually is, not what the documentation says a careful admin should configure. In a lab with Podman on RHEL 9, that means standing up a toy API that's open by default, proving it leaks data to an anonymous request, and then flipping the default itself rather than telling an imaginary future admin to remember -- because "remember to configure it" is exactly the control that failed here, at scale, across 47 organizations.

What Held

  • UpGuard's methodical, non-malicious research is what actually closed this. No evidence surfaced of prior exploitation by a malicious actor — the exposure was found and reported by researchers checking systematically, not attackers scanning opportunistically.
  • Microsoft fixed the platform, not just the symptom. Rather than asking 47 organizations to individually remediate and hoping every future customer configured things correctly, Microsoft changed what "default" meant for the whole product — the fix protects every portal that will ever be created on the platform, not just the ones already found.
  • The roughly two-month gap between UpGuard's first private notice and its public report gave Microsoft a real head start to investigate and respond before the scope became public knowledge.

Senior Security Advice

Scan Every Container Image for Known Vulnerabilities Before It Deploys

The Advice

Scan every container image for known vulnerabilities in the build pipeline, and block the deploy automatically when a critical vulnerability comes back unpatched.

Why It Matters

A container image is a snapshot of an operating system, a language runtime, and every library your application pulls in, frozen at build time. If any of those layers ship a known vulnerability, that vulnerability rides straight into production the moment the image is deployed, and it usually sits there quietly until someone with a CVE database and a plan finds it first. NIST's Application Container Security Guide calls out vulnerabilities, embedded malware, and untrusted base images as core risks of the image-build stage specifically because those problems are baked in before the container ever runs, not introduced afterward. The incident class this prevents is the one where attackers don't need to write custom exploit code at all: they run mass scans of internet-facing services, fingerprint the software versions, and walk in through a vulnerability that had a patch available for months. An unscanned image isn't a convenience shortcut. It's an unpatched server that nobody thought to check.

How to Implement It

  1. Wire an image scanner (Trivy, Grype, Anchore, or a cloud-native equivalent like Amazon ECR scanning) directly into the CI/CD pipeline so every image gets scanned on every build, not on a manual, occasional basis.
  2. Set a hard gate, not a warning: builds with critical or high-severity vulnerabilities that have an available fix fail the pipeline and cannot be pushed to the registry, aligned with the policy-enforcement approach NIST SP 800-190 recommends for the build stage.
  3. Scan running images on a recurring schedule too, not just at build time, because a clean image today can have a new CVE disclosed against it next week.
  4. Pin and scan base images specifically, since most vulnerabilities in an application image come from the OS and runtime layer underneath your own code, not your code itself.
  5. Verify the control is actually working: intentionally build a test image with a known-vulnerable package pinned in, push it through the pipeline, and confirm the gate blocks it. If it sails through, the scanner isn't wired into the gate, it's just generating reports nobody enforces.

The Pushback You'll Hear

"Scanning slows down our deploys." The senior-engineer rebuttal: a scan that runs in the pipeline adds seconds to minutes to a build; a breach that starts from an unpatched container image running in production costs weeks of incident response and customer trust. The fix for slow scans is caching and parallelizing the pipeline step, not skipping the check. Teams that got this right treat the scan gate the same way they treat a failing unit test: the build doesn't ship until it's green.

Senior Talk Tracks

Model Supply Chain Risk

Let's talk about a mistake teams make with AI models that they'd never make with regular code: trusting a file just because it's popular.

Here's the plain English version. When a team wants to use a machine learning model instead of building one from scratch, they usually download one that's already trained, often from a public hub like Hugging Face -- think of it like a package registry, but for models instead of code libraries. And most teams pick one the same way you'd pick a restaurant: by the star rating and the download count.

Here's why that's a problem in production. A model file isn't just data -- depending on the format, loading it can execute code, the same way certain document formats can. A malicious actor can upload a model that looks completely normal, performs well on the tasks everyone tests it against, and still contains a backdoor -- either literal code that runs when the file loads, or weights that have been subtly poisoned to misbehave only on specific trigger inputs nobody's testing for. That's model supply chain risk: the danger isn't in your code, it's in a file you downloaded and trusted because enough other people downloaded it too.

The senior take, the failure mode a junior usually misses: with regular open-source code, you can at least read the diff, run a static analyzer, or compare it against a known-good version. With model weights, there's no equivalent "read the code" step for most teams -- millions of numbers don't diff into something a human can eyeball for malicious intent. So teams that would never run an unreviewed shell script in production will happily load an unreviewed model file, because it doesn't look like code to them. It is.

Think of it like a professional kitchen. Reading source code is like a health inspector actually walking the kitchen and checking what's being cooked. Downloading a popular pretrained model based on stars and reviews alone is like hiring a chef because of great review scores and never once checking what's actually in the food -- you're trusting reputation for something reputation was never built to verify.

A good way to open this at work: "Before we pull that model into production, where did it come from, and did anyone actually scan it, or are we trusting it because it's popular?"

Key Takeaways

  1. A pretrained model downloaded from a public hub is a supply-chain dependency just like an open-source package, except its contents — millions of numeric weights — can't be read or diffed the way source code can.
  2. Popularity metrics like download counts and star ratings measure adoption, not safety, and treating them as a safety signal is the same mistake as trusting an unreviewed package because it has a lot of stars.
  3. Model files in certain formats can execute code on load, meaning a malicious model isn't just a bad-prediction risk — it can be a direct code-execution risk the moment it's loaded.

Reader Question

"If scanning every model file for malicious code is possible, why doesn't every team just do that and call the risk solved?"

Scanning catches some things — known malicious patterns in certain file formats — but it doesn't catch a model that was poisoned during training itself, where the weights look completely normal and only misbehave on a trigger nobody's tested for. My answer would be that scanning is necessary but not sufficient — it has to be paired with real provenance, meaning you know who trained it and on what, because a scan can tell you a file isn't running a known exploit, but it can't tell you the model wasn't taught to misbehave under specific conditions.

Tech News

If your network security appliance handles single sign-on for your OAuth apps, stop reading and check for a patch — attackers are already using a hole in it to run their own code with no login at all. Two stories today: a critical zero-day in F5's BIG-IP access manager, and a fake password-manager download that's been quietly killing off antivirus software before stealing credentials.

Start with F5. CVE-2026-94127 is a heap-based buffer overflow in BIG-IP Access Policy Manager, or APM — specifically in setups where APM acts as an OAuth authorization server, issuing access tokens to other applications. F5 rates it 9.8 out of 10, and confirmed in a September 22nd advisory that attackers had already weaponized it before the company even shipped a fix. The Cybersecurity and Infrastructure Security Agency, CISA, added it to its Known Exploited Vulnerabilities catalog that same day, with a September 25th deadline for federal systems. Here's the takeaway: this isn't a login page that got breached — it's the appliance that issues the tokens other systems trust, so a senior engineer treats every token that appliance handed out before the patch as potentially forged, not just the appliance itself as fixed.

Which brings us to a fake LastPass Authenticator. Researchers at LastPass and Delphos say attackers built lookalike GitHub pages — impersonating more than 40 companies, LastPass among them — that rank high in search results for terms like "LastPass Authenticator download." The installer is a renamed, legitimate Microsoft debugging tool that sideloads a malicious file, which then drops a signed Windows kernel driver — signed through Microsoft's own hardware compatibility program — to kill off 145 different antivirus and endpoint-detection tools before deploying an infostealer researchers are calling Rapuncel. LastPass itself wasn't breached; its brand was just the bait. My take: a valid Microsoft signature on a driver tells you it passed a compatibility check, not that it's safe to load — treat driver-level kill switches as a category worth watching until code-signing policy catches up with kernel-level malware.

Both stories point at the same lesson: the thing you trust by default — the appliance issuing your tokens, the signature on a driver — is exactly what today's attackers are learning to weaponize.

Patch that F5 appliance today, and if your team touches driver allow-lists, go check what's actually on yours.
