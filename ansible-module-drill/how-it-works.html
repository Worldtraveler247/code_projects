Ansible Module Drill — How It's Built

Thirty-one modules, five rounds each, against a ten-minute clock.

Overview

Reading a module's documentation is not the same as being able to use it under time pressure. Each module opens on a study sheet built from its real ansible-doc page, then the game turns one study routine into five scored rounds: look the module up, write the task, predict what Ansible will report, reverse the task, and read the error from a broken version. A browser cannot run Ansible, so every result is scripted. The design question was therefore how to keep scripted answers honest, and the answer is that as much as possible is taken from Ansible itself and checked by tests.

Tech Stack

HTML CSS JavaScript modules ansible-doc Node test runner
  • HTML and CSS — one page with three views: the board of modules, the study sheet, and the drill.
  • JavaScript modules — the rules live in game.js, which has no screen access, so the same code runs in the browser and in the tests.
  • ansible-doc — the source of every option name, required flag, list of choices, and every example on the study sheet.
  • Node test runner — Node's built-in node --test. No packages to install.

How Each Part Works

specs.js — facts taken from Ansible, not typed by hand

A small tool runs ansible-doc -j for each module and keeps only facts: the option names, their types, choices, defaults, aliases, and which are required. No documentation text is copied. The "tick the required options" question and the documentation panel are both drawn from this file, so they cannot disagree with the installed Ansible. 

node ansible-module-drill/tools/build-specs.mjs

examples.js — the study sheet, copied from ansible-doc

A second tool reads the same ansible-doc -j output and keeps the module's one-line summary, the first sentence of each option's description, and the EXAMPLES section word for word, split into its separate tasks. For each example it records which options are passed to the module, whether as YAML keys, key=value pairs, an args: block or an ad hoc -a string. The study sheet ranks options by that count, so "the most common options" is measured from Ansible's own examples rather than guessed. Examples that call a different module (a debug after a stat, for instance) are kept and marked as supporting tasks. Ansible's documentation is GPL-3.0-or-later and the page says where each example came from. 

node ansible-module-drill/tools/build-examples.mjs

docpages.js — how to read ansible-doc under exam pressure

The first section of every study sheet teaches the two forms of ansible-doc as they appear on a RHEL 9 control node. A third tool runs ansible-doc -s and ansible-doc from ansible-core 2.14, the version RHEL 9 ships, because 2.17 and later print a different layout. It keeps the -s output word for word, and from the full page the line number of each section and option plus the text of the option worth reading. Local paths in the page header are cut back to the part every install shares.

Capturing the real output corrected two things. -s does not mark required options with =; it prints a task skeleton and writes # (required) in the comment, and the = marker belongs to the full page's OPTIONS section. And on 2.14, dnf's name is required while newer releases dropped that, so the sheet says so for that module. 

ANSIBLE_DOC=/path/to/ansible-core-2.14/bin/ansible-doc node ansible-module-drill/tools/build-docpages.mjs

messages.js — error messages recorded from a real run

The last round shows an error and asks which line caused it. Those messages were not written by hand. A second tool builds each broken task, runs it with Ansible against the local machine in check mode, and records what Ansible printed. A bad argument fails during argument validation, before the module does any work, so the run changes nothing.

Recording them exposed three things a hand-written version would have got wrong. The order of the valid choices in a message is the module's order, not the documentation's. A misspelt option that replaces a required one is reported as a missing argument, not an unsupported one. And copy, template and unarchive check their main arguments themselves, with their own wording. 

node ansible-module-drill/tools/capture-faults.mjs

modules.js — one entry per module

Each drill is plain data: the starting state, the task to write, the three predicted results with a reason for each, the task that reverses it, and the faults. Adding a module means adding an entry, not code. 

{
  id: 'user', area: 'users', fqcn: 'ansible.builtin.user',
  given: 'No account named drilluser exists on servera.',
  args: { name: 'drilluser', comment: 'Module drill account', shell: '/bin/bash', state: 'present' },
  predict: STANDARD,   // changed under --check, changed on run 1, ok on run 2
  reverse: { goal: 'Remove the account and its home directory.',
             args: { name: 'drilluser', state: 'absent', remove: true } },
  faults: [{ kind: 'choice', option: 'state', value: 'gone' },
           { kind: 'unsupported', option: 'shell', typo: 'shel' }],
}

The predictions

Most modules follow one pattern: changed under --check, changed on the first run, ok on the second. The drill is most useful where a module breaks it. at does not support check mode, so the task is skipped. unarchive skips a tar archive in check mode. state: restarted reports changed on every run. command is idempotent only with creates or removes. Each of these was read from the module's source, and ten of the file-based drills were also run locally to confirm the three results.

The editor and the checker are shared

The two typing rounds import the Vim-style editor and the line-by-line checker from the Ansible Playbook Trainer unchanged. The play header is already in the file, so the time goes on the module and not on the frame around it. In the reverse round the editor opens with the task you just wrote, and you edit it into its opposite. 

import { createEditor, handleKey } from '../ansible-playbook-trainer/editor.js';
import { check } from '../ansible-playbook-trainer/checker.js';

Scoring

Accuracy comes before pace. A wrong answer, a failed check or a hint is one miss; showing the answer is three. Three stars need no misses inside ten minutes, two stars allow two misses, and finishing earns one. Opening the documentation panel costs nothing, because looking a module up is the habit the drill is meant to build. 

export function stars(misses, seconds) {
  if (misses === 0 && seconds <= PAR_SECONDS) return 3;
  return misses <= 2 ? 2 : 1;
}

Tests

Every module is tested four ways. Its two tasks must use only real options, valid choices and every required option. Both model answers must pass the checker. Each fault must be a real fault: a value that is not a valid choice, a key the module does not accept under any alias, or an option that is truly required. And the recorded message must be the one Ansible prints for that kind of fault. A typo in the data fails the tests instead of reaching the page. 

node --test 'ansible-module-drill/tests/*.test.mjs'

Security

  • Content-Security-Policy — script-src 'self': no inline script and nothing from another site.
  • No innerHTML — everything the player types is put on the page as text, never as markup, and nothing typed is ever executed.
  • No network calls — best scores are kept in the browser's local storage and nowhere else. Stored values are validated when they are read back.
  • No secrets in the practice data — no drill sets a password; the user drill explains that a password belongs in a vault as a hash. URLs use HTTPS on a reserved example domain, and a test enforces both.
  • Safe defaults are the model answers — signature checks stay on, file modes are quoted, and destructive options such as state: absent on a disk carry a warning.

Limits

  • Nothing is executed — the results are scripted. The finish screen lists the commands for repeating each drill on a real lab, and that step is the one that counts.
  • One version — the facts and messages come from ansible-core 2.20, ansible.posix 2.1 and community.general 12.5. An older release may word a message differently or lack a newer option.
  • Two messages are derived — on a systemd host the service module hands its task to systemd, which cannot be reproduced on a Mac, so those two messages are composed from systemd's recorded ones. The debug message is worded as ansible-core 2.14 prints it.
  • One model answer — the checker accepts the keys in any order, but the values must match the work order.
  • Keyboard needed — the two typing rounds are built for a physical keyboard.
