📖 How It's Built

Ansible Module Drill

Pick a module and study it first: what it needs to run, the options it is used with, and every real example from its ansible-doc page. Then drill it: five rounds, ten minutes. Look the module up, write the task, predict what Ansible will report, reverse it, then read the error from a broken version. Thirty-one modules across ten exam objective areas. Nothing is run on a real machine, so the results are scripted; repeat each drill on your lab afterwards.

Modules

How a drill works

Each module opens on a study sheet built from ansible-doc: the required options, the options the real examples use, and every example from the module's EXAMPLES section, word for word. Read it, then press Start the drill. The clock starts then, and the target is ten minutes.

RoundWhat you doWhat it trains
1. Look upPick the module's full name, then tick its required optionsFinding a module with ansible-doc and spotting what is required: # (required) in -s, = on the full page
2. WriteType the task in a Vim-style editor. The play header is already thereRecall of the option names, and placement
3. PredictCall the result of --check, the first run and the second run before you see itIdempotence, and which modules break the pattern
4. ReverseEdit your task so that it undoes itselfThe option that removes, and what it leaves behind
5. BreakRead a real error message and pick the line that caused itReading Ansible's errors under time pressure
  • Three stars: no misses, inside ten minutes. Two stars: two misses or fewer. One star: you finished.
  • A miss is a wrong answer, a failed check with :w, or a hint. Showing the answer costs three.
  • Opening the documentation panel is free. Looking a module up is the habit this drill builds, and it is allowed on the exam.
  • The error messages are real. Each one was recorded from Ansible running the broken task. Your version may word a message slightly differently.

    It prints a task skeleton, not a manual. How to read it:

    • Line 1 - name: is the module's one-line description, ready to use as a task name.
    • Line 2 is the module's short name. Write the full name () in your playbook.
    • Each key six spaces in is an option. Everything after its # is the description, wrapped onto the lines below it.
    • # (required) marks an option the task must set.
    • It does not show types, choices or defaults. For those, use the full page below.
